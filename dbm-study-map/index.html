遙測概念與健康指標

這一章回答兩個地基問題：DBM 支援哪些引擎、標準整合跟 DBM 到底差在哪；接著把資料庫的「生命徵象」拆成九大健康指標，再把三種鏡頭攤開成六種遙測類型逐一深入。讀完這章，後面所有排查動作用的資料來源才有意義。

支援的資料庫引擎

引擎備註
PostgreSQL需要 pg_stat_statements 擴充套件，以及為 Datadog 使用者授予 pg_monitor 角色。
MySQL需要啟用 Performance Schema。自行託管與雲端託管實例的設定步驟有所不同。
SQL Server需要具有特定權限的唯讀登入帳號。預存程序負責處理執行計畫的收集。
Oracle需要特定的 Oracle 套件，以及具有適當授權的專用 Datadog 使用者。
MongoDB支援 Atlas 和自行託管的部署。遙測類型與關聯式引擎有所不同。
考試重點考試是「資料庫引擎無關」的，不會考特定引擎的 SQL 語法或設定細節，只會考「調查工作流程」本身，這套流程在所有支援的引擎中皆相同，僅設定方式有所差異。這份地圖的實作範例全部用 PostgreSQL，呼應 Storedog 實驗環境。

標準整合 vs. DBM：多看到什麼

標準整合是像 Postgres 或 SQL Server 的一般整合，收集「主機層級 / 實例層級」的指標，是資料庫「由外往內看」的視角。DBM 不是取代它，是疊加在標準整合之上，多出查詢層級的一整套遙測。

看得到連線數、SQL 編譯速率、buffer pool 使用率、磁碟 I/O、複寫狀態等彙總數字，能告訴你資料庫「健不健康」。看不到「為什麼」，也就是查詢層級的細節完全是黑盒子。設定簡單，Agent 使用者只需要基本 SELECT 權限。
額外拿到查詢指標（前 200 條正規化查詢的彙總統計）、查詢樣本（某時刻的實際執行快照，保留 15 天）、自動收集的執行計畫、等待事件分析、阻塞查詢洞察、正規化與混淆處理、APM 關聯、DBM Recommendations。代價Agent YAML 要加 dbm: true，需要額外權限（Postgres 要 pg_monitor），且必須直接連到資料庫主機，不能經過 proxy/負載平衡器/連線池。多數工作負載下額外負擔通常低於查詢執行時間的 1%、CPU 的 1%。

九大健康指標：資料庫的生命徵象

可以想成醫生看病人的生命徵象：心跳、血壓、體溫。點開每一項看判讀邏輯：

① 連線數（Connections）▸

多少客戶端連進資料庫、離上限還有多遠。持續攀升可能是連線洩漏，突然暴增可能是流量突發或應用程式設定錯誤，長時間閒置的連線是浪費資源。

② 查詢量與吞吐量（Query Volume and Throughput）▸

每秒處理幾個查詢（讀 vs 寫）。突然下降可能代表上游應用程式壞了，突然暴增可能是某個失控的程序在灌爆資料庫。

③ 查詢延遲（Query Latency）▸

平均、p50、p95、p99、最大值。p95/p99 特別重要，因為平均值會掩蓋離群值，例如平均 10ms、p99 卻 2 秒，代表 1% 的使用者體驗極差。

④ 活動連線與資料庫負載（等待事件分析）▸

不只看「跑了幾個查詢」，而是看查詢當下「在等哪種資源」，四大分類：CPU（搶運算資源，考慮優化查詢或加大實例）、I/O（等磁碟讀寫，可能缺索引或 buffer pool 太小）、鎖/Latch（等其他 session 放開鎖，通常是長交易造成的競爭）、網路（等資料傳輸，可能結果集太大或延遲高）。

⑤ 阻塞查詢（Blocking Queries）▸

一個長交易卡住鎖，可能連鎖造成幾十個查詢被卡住。DBM 能視覺化找出「根源阻塞查詢」和被卡住的查詢，見第 4 章、第 7 章的真實鎖定案例。

⑥ 資源使用率（CPU/記憶體/磁碟/I/O）▸

資料庫的「物理極限」，就算查詢寫得再好，主機沒 CPU、沒記憶體、沒磁碟空間一樣會掛。CPU 持續 >80% 代表快撐不住；記憶體看快取命中率；磁碟空間用完是災難性故障。

⑦ 複寫健康度（Replication Health）▸

複寫延遲（replica 落後主節點多少）、複寫狀態（是否連線中且持續同步）。延遲太高代表讀到舊資料，斷線代表失去容錯後援。

⑧ 資料庫引擎特有的遙測▸

Postgres 看 vacuum 操作（死列持續累積代表 autovacuum 跟不上）；SQL Server 看連線數、系統記憶體、吞吐量；MongoDB 看慢操作、執行計畫、複寫狀態變化。

⑨ DBM Recommendations 本身也是健康訊號▸

不只給原始指標，還主動分析並標出高影響力的阻塞查詢、沒在用的索引、低磁碟空間告警，每個建議都有嚴重程度分級，完整類型表見第 4 章。

綜合判讀的關鍵在於「關聯」單一指標說不了完整的故事：CPU 高 + 某條查詢吃掉大部分資料庫時間 → 那條查詢需要優化；延遲上升 + 鎖等待增加 → 是阻塞問題不是資源問題；連線暴增 + 吞吐量下降 → 是連線飽和不是查詢效率差；I/O 高 + 快取命中率低 → 需要更多記憶體或查詢掃太多資料。

六種遙測類型：三種鏡頭逐一深入

官方文件把資料型態濃縮成三大類，是同一個資料庫的三種不同「鏡頭」；下面六種遙測，是這三種鏡頭實際攤開後的樣子：

Metrics · 衛星視角

主機層級整合指標，回答「資料庫整體狀況如何」，是 dashboard 和門檻告警的基礎。限制：只看得到「發生了什麼」，看不到「是誰造成的」。

Query Metrics · 街景視角

針對每條正規化查詢的彙總效能統計，把資料庫從黑盒子變成可以在查詢層級推理的東西。

Query Samples · 顯微鏡視角

某個時間點實際執行的個別快照。限制：只是有偏誤的抽樣，不是完整紀錄。

典型調查順序：Metrics（「資料庫在承壓」）→ Query Metrics（「這個查詢模式吃掉 40% 資料庫時間」）→ Query Samples（「這一次執行在 3:47 PM 花了 12 秒」）。實際畫面上再加上執行計畫、等待事件、活動工作階段、結構描述，攤開成六種：

遙測類型回答的問題
查詢指標（Query Metrics）哪條查詢最慢 / 最耗資源？
查詢樣本（Query Samples）這一次具體慢在哪？
執行計畫（Explain Plans）資料庫怎麼執行這條查詢的？
等待事件（Wait Events）查詢在等什麼？
活動工作階段（Active Sessions）那個時刻資料庫裡發生了什麼？
結構描述（Schemas）表的結構是否合理？

典型調查順序：查詢指標 → 查詢樣本 → 執行計畫 → 結構描述 → 等待事件 / 活動工作階段。

查詢指標（Query Metrics）：正規化與 query_signature

DBM 將具有相同查詢簽章的所有執行不論參數值為何歸為一組，計算平均延遲、總執行時間、回傳列數、呼叫次數。

什麼是正規化把查詢裡實際帶入的參數值換成佔位符，讓不同參數但邏輯相同的查詢被視為同一條「查詢簽章」： 
SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending'
SELECT * FROM orders WHERE user_id = 55103 AND status = 'shipped'
正規化後都被歸類成同一條查詢簽章：SELECT * FROM orders WHERE user_id = ? AND status = ?。只要結構相同（表名、欄位、運算子、子句排列都一樣），就視為同一條簽章；只要有結構性差異（多一個欄位、`WHERE` 順序不同、多一個 `JOIN`），就是不同簽章，各自彙總。
考試重點篩選時要用 query_signature，不要用 query 欄位。原因：tag 名稱會被截斷到 200 個字元，查詢文字可能很長、`query` 這個 tag 不一定唯一；`query_signature` 是固定長度的雜湊值，才是可靠的辨識依據。
實戰範例：電商結帳頁面突然變慢Query Metrics 依「總執行時間」排序，發現 SELECT * FROM orders WHERE user_id = ? AND status = ? 佔了最多資源：平均延遲 850ms（上週只有 120ms）、每分鐘呼叫 3,200 次、回傳列數平均 4,500 列（上週只有 50 列）。回傳列數暴增暗示可能缺少 `LIMIT` 或索引失效。
保留期限官方文件（Database Monitoring Data Collected、Data Retention Periods）明確列出 Query Metrics 保留 15 個月。

查詢樣本（Query Samples）：從「平均慢」到「這一次為什麼慢」

某個收集時刻擷取的個別查詢執行：確切的查詢文字、持續時間、主機、相關執行計畫，直接連結到 APM 追蹤（見第 3 章）。

實戰範例從查詢指標知道那條查詢「平均」慢，切到查詢樣本，找到一筆執行 2.3 秒、主機 postgres-replica-02、關聯的 APM 追蹤來自 checkout-service 的 /api/v1/checkout。點進追蹤，發現是某使用者有 12,000 筆歷史訂單導致這次特別慢。
考試重點保留期限 15 天，跟 Query Metrics 的 15 個月差了一個量級，這是常考對比點。DBM 是取樣而非全量擷取，某查詢沒出現在樣本裡，很可能是該區間內未被擷取，而非沒有執行。

執行計畫（Explain Plans）：從零拆解每個名詞

執行計畫是查詢規劃器為執行查詢所選擇步驟的表示。整份執行計畫可以想成一份「餐廳出餐流程單」：客人點餐（SQL）只說「我要一份牛排」，廚房內部要自己決定怎麼做，這整套內部決定和步驟，就是執行計畫。

誰在決定怎麼做：查詢規劃器、節點。查詢規劃器就是廚房裡負責「想辦法」的大廚，客人只說想吃什麼，大廚要自己想一套流程，這套流程就是執行計畫；每一行是一個「節點」，動作複雜時好幾個節點疊起來，這也是地圖檢視長得像一棵樹的原因。

Seq Scan（全表掃描）：想像在沒有分類的倉庫裡找東西，只能一箱一箱打開看。

Seq Scan on orders  (cost=0.00..15420.00 rows=4500)
  Filter: (user_id = 98712 AND status = 'pending')

想像倉庫大門貼了一張清單「A 類東西在第 3 排」，看一眼清單就知道去哪拿，這就是 Index Scan（索引掃描）。實際建這張清單：

CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
用 `user_id` 為第一排序依據，相同 `user_id` 的資料再依 `status` 排序，建立時資料庫把每列 `(user_id, status)` 值抓出來排序，組成獨立資料結構（PostgreSQL 預設用 B-tree）分開存放。

為什麼欄位順序要這樣排：`user_id` 的區分度遠高於 `status`（`user_id` 幾乎每個值都不一樣，`status` 通常只有 `pending`、`shipped`、`cancelled` 等少數值），區分度高的欄位放第一位，才能讓「跳到目標位置」這一步盡量縮小範圍。

Index Scan using idx_orders_user_status on orders  (cost=0.42..8.50 rows=3)
成本從 15,420 大幅降到 8.5。

查詢 SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending' 實際執行步驟：① 規劃器發現索引涵蓋 `WHERE` 用到的兩個欄位，選擇 Index Scan；② 在索引裡用二元搜尋（每次對半找）快速定位到 `user_id = 98712` 開始的位置，只需比對 log(N) 次而非 N 次；③ 從那個位置往後讀，因為同一個 `user_id` 的資料在索引裡連續排在一起；④ `status` 是第二排序依據，`pending` 的資料排在一起，不用逐筆檢查；⑤ 索引每筆紀錄附帶指標指向表裡實際那一列，找到符合條件的項目後依指標回表讀出真正資料。整個過程完全沒有看那些不符合條件的 499,997 列。

拿到資料後怎麼加工：Filter（篩選，對應 `WHERE`）、排序 Sort（對應 `ORDER BY`，通常要等所有東西堆到桌上才能開始排）、聯結 Join（`Nested Loop` 清單小時一筆筆去另一份找對應／`Hash Join` 兩份都不小時先把其中一份建成雜湊表／`Merge Join` 兩邊本來就有序時像拉拉鍊一樣對）、彙總 Aggregate（`COUNT`/`SUM`/`GROUP BY`，通常是最後一步）。

cost：不是花多少錢或秒數，比較像大廚心裡對「這個做法麻不麻煩」打的分數，寫法「起步分數..總分數」，是憑經驗猜的，只能跟同一份計畫裡的其他動作比大小，不能跨查詢、跨機器比較。rows：大廚猜「這個動作做完大概留下幾筆」，猜的數字和實際差很多，就是「大廚這次可能選錯做法」的訊號。

如果整份流程有很多動作疊在一起，DBM 會把整份流程畫成一棵樹，用顏色深淺或方塊大小直接告訴你哪個方塊最耗力氣，不用自己一個一個心算比較。

實戰範例對某筆查詢樣本查看執行計畫，看到 Seq Scan，資料庫逐列掃描整張 `orders` 表（50 萬列），地圖檢視顯示這個節點佔了總成本的 98%。修復：建立 `(user_id, status)` 複合索引，成本從 15,420 降到 8.5。
注意並非每個查詢都有執行計畫：有些查詢時間太短無法被取樣附帶計畫，有些結構上不符合條件（例如特定鎖定模式的交易），且收集需要 explain_statement 函式正確設定（見第 2 章）。若查詢樣本沒有相關計畫，先檢查這個函式。

等待事件（Wait Events）：銀行辦事大廳

Analogy把資料庫想成一間銀行的辦事大廳，每個「連線」是一位正在辦事的客戶，客戶辦事的每一刻，不是「正在被服務」就是「在等某件事」。

CPU 等待：查詢正在真正被處理，是正常忙碌，占比一直很高通常代表查詢要處理的資料量或計算量大。鎖定等待（Lock wait）：這條連線想動某筆資料，但已被另一條連線鎖住，例如 Lock:transactionid 代表在等另一整筆交易結束，突增代表有交易卡太久沒結束。I/O 等待：等資料從硬碟讀進記憶體或寫進硬碟，占比高通常代表資料量大或硬碟速度跟不上。閒置（Idle）：連線目前沒有查詢在跑但還占著位置。阻塞（blocking）：鎖定等待的另一面，A 在等 B 放開鎖就說「B 阻塞了 A」，活動連線分頁能直接告訴你「誰在阻塞誰」。

實戰範例見第 4 章、第 7 章的 Lock:transactionid 突增、stop_locks 追查、根因是測試用 LOCK TABLE cronjob 沒被清掉的真實案例。

活動工作階段（Active Sessions）：每 10 秒的快照

資料庫活動連線狀態的定期快照，大約每 10 秒擷取一次，捕捉當前正在執行的查詢、持續時間、等待狀態、哪些連線正在阻塞其他連線。跟等待事件是搭配使用的一組：等待事件告訴你「突增發生了」，活動工作階段告訴你「突增發生時具體在跑什麼」。

Analogy如果等待事件是「這一刻某位客戶在等什麼」的即時廣播，活動工作階段就是保全系統每隔幾秒對整個大廳拍一張照片。因為是「定期拍照存檔」不是持續錄影，兩張照片中間發生的事不會被記錄，但事後還是能一張一張翻回去找到異常當下發生了什麼事。多條連線同時因同一個原因卡住時，能把這些連線串成一條「阻塞鏈」，具體點名是哪一條連線、跑哪一句查詢造成的。

結構描述（Schemas）：表結構是否合理

可以把一張表想成一個檔案櫃，每一列資料是一份格式統一的表單。欄位（column）是每份表單固定會有的一格；資料類型規定這一格只能填什麼（例如 numeric(10,2)）；主鍵絕對不會跟別份表單重複，資料庫預設會自動建立索引；索引是幫忙快速定位資料的清單，索引大小指這份額外清單本身占了多少儲存空間，不是免費的。

考試補充的基礎名詞B-tree（多數資料庫索引預設用的樹狀結構，讓「對半找」的二元搜尋能成立）、覆蓋索引（covering index）（索引本身就包含查詢需要的所有欄位，完全不用回表）、索引膨脹（index bloat）（索引隨資料異動累積大量不再有效的項目，佔用空間變大、查詢變慢，需要定期重建或清理）。表名、欄位名、索引名稱這些結構性資訊不屬於混淆處理範圍，會完整顯示在結構描述頁面。

資料隱私與混淆處理

查詢樣本會擷取實際執行的查詢文字，資料庫裡常存著使用者信箱、付款資訊、個資，Agent 送資料到 Datadog 之前做兩件事：查詢正規化（字面值換成 `?` 佔位符，同時也是離開主機前先拿掉字面值的機制）和參數混淆處理（obfuscation）（另一道保護，預設就會執行，處理正規化沒涵蓋到的情況，例如查詢文字裡的註解）。

資料類型預設是否會被混淆
查詢參數值（綁定的字面值）會
查詢文字中的註解會
表格名稱和欄位名稱不會
索引名稱不會
執行計畫結構不會
主機中繼資料和資料庫標籤不會
考試常考的盲點如果表名、欄位名本身包含敏感資訊（例如表叫 credit_cards），這些名稱本身會被看到；資料庫的 log 若送到 Datadog，可能包含完整 SQL 查詢文字含綁定參數，混淆處理只套用在 DBM 遙測管線，log 走不同路徑；SQL 查詢裡的註解可能被 Agent 收集且不經混淆，這一點在第 3 章的 trace 關聯註解機制裡也要特別留意，因為那個機制本身就是靠 SQL 註解夾帶 trace id。

動手調查前要知道的兩件事

  1. DBM 是取樣（sampling），不是全量擷取。某查詢沒出現在查詢樣本中，很可能是該時間區間內未被擷取，而非沒有執行。
  2. 存在傳播延遲。從查詢執行到指標出現在 DBM 檢視之間有短暫延遲，驗證修復時請等幾分鐘再看更新資料。

Chapter 03 · APM Correlation

APM 與 DBM 關聯

前兩章分別講了六種遙測資料本身、以及怎麼把 DBM 架起來收集這些資料，這一章講另一件事：DBM 收集到的資料庫端遙測，怎麼跟 APM 收集到的應用程式端遙測連在一起。

要解決的問題

沒有關聯時，DBM 和 APM 是兩個獨立的世界。APM 告訴你「這個 API 端點很慢，資料庫那個 span 花了 2 秒」，但不會告訴你「為什麼」慢；DBM 告訴你「這條正規化查詢延遲很高」，但不會告訴你是哪個服務造成的。接起來之後，開發者不需要直接存取資料庫就能理解資料庫效能，DBA 也能理解特定服務的請求流量如何影響資料庫負載。

三層機制：Tracer、Agent、trace ID 注入

這個關聯不是資料庫本身有什麼特別設定，而是應用程式端設定加上 Agent 的 APM 功能共同促成的，跟第 2 章的 Storedog 實驗環境完全對得起來。

backend`、`worker 這類服務會掛載 datadog-tracer-backend.rb 這種初始化檔案，是 dd-trace 函式庫設定檔，負責在 Ruby/Rails 應用程式啟動時自動掛上追蹤功能。裝好之後，Tracer 會自動攔截應用程式呼叫資料庫的動作（例如透過 ActiveRecord 下的 SQL），不需要工程師手動加程式碼。

這是 Postgres 能以「service」身分出現在 APM 裡的根本原因：是應用程式那端在回報「它呼叫了資料庫」，資料庫本身並不知道自己被追蹤。裝好後能在 APM > Software Catalog 找到 Postgres 這個服務。

Agent container 設有 DD_APM_ENABLED=true、DD_APM_NON_LOCAL_TRAFFIC=true，並開了 8126 這個 port，是 Agent 用來接收各服務送過來的 trace 資料的專用通道。應用程式端 Tracer 產生的 span，就是透過這個 port 送給 Agent，再由 Agent 轉送到 Datadog。每個應用程式服務也都設了 DD_AGENT_HOST=datadog，告訴 Tracer 要把資料送去哪個 Agent。

單純有 Tracer 和 APM，只能看到「應用程式呼叫了資料庫、花了多少時間」的 span 層級資訊，要能從 APM 某條 trace 直接連到 DBM 收集到的 Query Samples、Explain Plans 細節，靠的是把 trace ID 注入到 DBM 資料收集裡。

APM tracer 會把 trace 上下文（trace ID、span ID、service name、environment）以 SQL 註解的形式，加在實際查詢文字前面再送出去：

/*dddbs='orders-db',ddps='checkout-service',ddtid='abc123'*/ SELECT * FROM orders WHERE id = ?
資料庫只執行 `SELECT` 那部分（忽略註解，不影響效能），Agent 收集查詢樣本時讀到這段註解，抽出 trace 中繼資料，建立關聯。這也是為什麼 DD_DBM_PROPAGATION_MODE=full 這個環境變數在第 2 章 `postgres`、`backend`、`worker` 等多個服務裡都各自設了一份，因為兩邊都要設才能對得起來。

三種 Propagation Mode

full
完整 trace 資訊
送出完整 trace 資訊（trace ID、span ID、service name、environment），能雙向導航：從 trace span 跳到 DBM 查詢樣本，也能從 DBM 樣本跳回完整 trace。大多數整合建議用這個，也是第 2 章實驗環境實際採用的設定。
service
只送 service name
不含 trace/span ID，能看出是哪個服務造成資料庫負載，但不能跳轉到特定 trace。
disabled
完全不傳送
DBM 和 APM 各自獨立，沒有關聯，回到本章開頭「兩個世界互不相干」的狀態。

啟用關聯需要的四個條件

  • DBM 已設定並收集資料（dbm: true，見第 2 章）。
  • APM 已設定並有 tracing（裝了 Datadog tracing 函式庫，或帶正確屬性的 OpenTelemetry）。
  • Tracer 裡設定了 Propagation Mode（依語言各自設定，或用環境變數 DD_DBM_PROPAGATION_MODE=full）。
  • Unified Service Tagging（DD_SERVICE、DD_ENV、DD_VERSION 都要設，確保 service/env/version 在 APM 和 DBM 兩邊標籤一致）。

跟查詢正規化/混淆處理的關係（重要區分）

第 1 章提到查詢文字送到 Datadog 前會經過正規化與混淆處理，那是保護查詢裡的綁定參數值不外洩的機制。這裡的 trace ID 注入走的是完全不同的路徑：它動的是查詢文字最前面的註解，不是查詢本身的參數，而且註解不會被混淆處理。

考試常考的盲點如果應用程式自己額外在 SQL 裡加了含敏感資訊的註解（例如使用者 ID 或 session token），這些也會被 Agent 收集並送到 Datadog，不經過混淆。混淆處理只涵蓋參數值，不涵蓋 SQL 註解本身。

小結：典型排查流程

Query Metrics vs. Query Samples：什麼時候用哪個

Query Metrics · 趨勢分析師

彙總歷史效能資料，前 200 名正規化查詢，保留 15 個月。回答：「哪個查詢模式吃最多資料庫時間？」「這條查詢這個月變慢了嗎？」「每秒被呼叫幾次？」做不到：看不到具體某一次執行、具體某個時刻發生了什麼。

Query Samples · 事件調查員

某時間點正在跑的查詢個別快照，附執行細節和執行計畫，保留 15 天。回答：「3:47 PM 延遲飆升時在跑什麼？」「是不是全表掃描？」「是誰在跑這條查詢？」

實戰範例：用 Query Metrics 排序找出可疑查詢Storedog 新加了一個「熱門商品排行」小工具，每隔幾秒對 `items` 表跑一次查詢抓最常被下單的前十項商品，這條查詢造成資料庫負擔很重。切到 Query Metrics 分頁，點選 Average Rows 欄位標題排序，`SELECT id, description...` 排在最前面，查詢文字裡的 `?` 佔位符就是正規化的結果。

N+1 查詢問題

不是用一句 `JOIN` 一次拿到所有相關資料，而是應用程式每一筆項目各自跑一次查詢。範例：電商頁面顯示 100 筆訂單清單，每筆要顯示客戶姓名。

有效率（1 個查詢）

SELECT orders.id, orders.total, customers.name
FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE orders.created_at > '2024-01-01'

N+1（101 個查詢）

先跑一個查詢抓所有訂單，接著應用程式對結果跑迴圈，每筆訂單各自跑一次查詢去查客戶姓名，100 筆訂單就是 101 次資料庫來回。

為什麼重要：每個查詢個別看可能很快（2ms），但 101 個加起來超過 200ms，資料量放大到 1 萬筆時會非常嚴重。最麻煩的是 N+1 在開發階段常常不會被注意到，因為測試資料庫列數很少，只有到正式環境資料量變大才會顯現。

DBM 怎麼幫你抓到它APM 裡打開一條慢 trace 會看到火焰圖疊了幾百個細小、幾乎一樣的資料庫 span；DBM Query Metrics 裡這條正規化查詢的 Requests 數異常高，個別執行可能很快（Average latency 低），但 Total time 很高。兩者同時出現就是明確訊號。怎麼修：修法在應用程式碼，不是資料庫本身，常見做法是用 `JOIN` 一次查完、用 eager loading、或批次成一句帶 `WHERE id IN (...)` 的查詢。

調查阻塞：完整實戰範例▸

阻塞是一個查詢卡住鎖，讓另一個需要同一個鎖的查詢等待，嚴重時形成阻塞鏈：A 卡住 B，B 卡住 C。要看主機詳情 → Blocking Queries 分頁（視覺化樹狀圖顯示誰在卡誰）、等待事件分析（鎖/latch 等待占主導代表問題是「競爭」不是「資源耗盡」）、DBM Recommendations（自動偵測並標出高影響力的阻塞者）。

實戰範例：Storedog 的 LOCK TABLE 事件與 stop_locks從 Databases 總覽頁展開 Wait Group Activity 圖表，看到 CPU 等待、閒置、鎖定這幾種等待事件同時存在，這次最需要優先處理的是鎖定事件。切到 Active Connections 分頁，翻幾張快照找到 # WAITERS 欄位有數字、等待分組圖表出現紅色長條的那一筆，展開看到完整 SQL：開發團隊有人在寫更新訂單數量的查詢時語法沒寫好，用了 `LOCK TABLE` 還設成排程 cronjob 定期跑，導致大量其他查詢被卡住。切到 Blocking Queries 分頁，Time Impact 確認這條查詢已讓其他查詢等了超過 15 秒。這條查詢是之前測試某功能時留下的，跟 Storedog 正常運作無關，直接停掉：stop_locks。完整互動式追蹤（含每一步的另一種可能分支）見獨立分頁「架構全覽」。

識別效能退化

實戰案例：把熱門商品查詢真正優化到底

先去程式碼裡看實際查詢邏輯（dbm.py），發現篩選商品的門檻設得太寬，抓的不是真正熱賣商品，而是一個範圍很大的群體。

縮小查詢範圍：把產生篩選門檻的隨機範圍從 `random.randint(1, 7000)` 改成 `random.randint(5000, 7000)`：

SELECT id, description, order_count, last_hour, image_url, NULL AS is_preorder
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}
UNION
SELECT id, description, order_count, last_hour, image_url, is_preorder
FROM preorder_items
WHERE order_count::int > {random.randint(5000, 7000)}

重啟服務、等幾分鐘後回到 Query Metrics 依 Average Rows 排序驗證：查詢樣本成本已下降，方向對了。再看 Traces 分頁，這次耗時比之前（原本超過 225ms）明顯降低。但整體成本還是偏高，回頭看 Explain Plan Map View，排序（Sort）操作依然占了這條查詢總成本的 75%，是下一個要處理的瓶頸。

拿掉 UNION：查詢邏輯用 `UNION` 把 `items` 和 `preorder_items` 兩張表的結果合併。`UNION` 不只是把兩批結果接在一起，還會自動去除重複的列，而要去除重複，資料庫必須先把所有結果排序過一遍，這正是 Map View 裡那個高成本排序節點的來源。

進一步理解：`preorder_items` 裡的商品一旦正式上架，會被標記成 `false`，代表沒必要同時查兩張表再 `UNION` 去重，更好的做法是讓開發團隊調整資料寫入邏輯，把已上架商品直接維護進 `items` 表，查詢端只需要簡化成只查一張表：

SELECT *
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}

重啟服務，回到 Query Metrics 依 Rows per Query 排序驗證，成本比前一次優化又大幅下降，因為現在整條查詢只剩單一個掃描操作，不再需要 `UNION` 去重造成的排序負擔。

這個案例示範的核心觀念DBM 不是只能拿來「找問題」，改完程式碼之後，同一套 Query Metrics、Explain Plans、Query Samples、APM Trace 也能拿來「驗證修復有沒有效」，用實際數字（cost、耗時、rows）取代「感覺應該有變快」的猜測。整趟調查（鎖定問題排除 → 找出高負載查詢 → Explain Plan 鎖定排序瓶頸 → 歷史趨勢確認 → APM Trace 確認實際影響 → 兩輪優化迭代驗證）就是把本章前面每一段診斷框架實際跑過一遍的完整示範，互動版見獨立分頁「架構全覽」。

例如 CPU 連續 5 分鐘 >85%、連線數 >上限 90%、複寫延遲 >30 秒。
變化（Change）
跟前一段時間比變化太大
例如查詢量比上週同時段掉了超過 50%。
異常（Anomaly）
機器學習偵測偏離歷史模式
考慮時段和星期幾的季節性，適合波動明顯、有週期規律的指標。
預測（Forecast）
真正超過門檻前先告警
例如磁碟用量成長速度預估 3 天後會滿。

複合監控（Composite）：用布林邏輯組合多個監控，例如只在「錯誤率高」而且「總請求量夠大」時才告警，避免只有 2 個請求時錯誤率高就誤報。

告警聚合方式：Simple vs. Multi Alert

Simple Alert

跨所有回報來源做彙總，一個或多個群組超標就觸發一次告警，用這種策略能降低通知噪音。

Multi Alert

依你設定的分組參數各自套用告警。例如依 `@db.user` 分組，每個觸發條件的資料庫使用者都各自收到一則告警，粒度更細，但也可能吵很多。

考試重點資料庫監控通常用依 host 分組的 Multi Alert 最合理，你想知道的是「哪一台」主機出問題，不是只知道「某台主機」有事。

什麼是資料庫

資料庫是一套有組織的系統，用來儲存、擷取、管理資料，取代把資訊散落在檔案、試算表、文件裡的做法。

Analogy可以想成一座倉庫：你可以把所有庫存都丟進一個大房間，每次要找東西就整間翻過一遍；或者分類放進標好籤的架子、排、箱子，搭配一套目錄系統告訴你東西確切在哪裡。資料庫就是那個整理好的倉庫。

為什麼不能只用檔案：檔案在遇到「多人同時讀寫不會弄壞」「幾百萬筆紀錄裡有效率地搜尋」「斷電時資料不會寫到一半」「不同種類資料之間的關聯」這些需求時很快就撐不住，資料庫解決了這些問題。

表、列、欄、主鍵、外鍵

資料庫最常見的組織方式是表（table），類似一份試算表：一張表代表一種東西的類型，每一列（row）是一個具體實例，每一欄（column）是一個屬性。每張表通常有一個主鍵（primary key），唯一辨識每一列的欄位；表之間常透過外鍵（foreign key）關聯，一張表裡的某欄位指向另一張表的主鍵。

表/列/欄/索引更完整的實際範例見第 1 章的結構描述段落。

SQL 與 CRUD

SQL（結構化查詢語言）是跟關聯式資料庫溝通的方式，是宣告式語言：你告訴資料庫「你要什麼」，不是「怎麼拿到它」，引擎自己想辦法找最好的執行方式。主要操作對應 CRUD：Create（INSERT）、Read（SELECT）、Update（UPDATE）、Delete（DELETE）。

考試重點DBM 證照考試不需要你「寫」SQL，只考「解讀」，但理解這些語句在做什麼，能幫你看懂 Datadog 裡的正規化查詢和執行計畫。

資料庫管理系統（DBMS）

DBMS 是執行並管理資料庫的軟體，當大家說「Postgres」或「MySQL」時，指的是這套軟體本身，不是資料本身，負責儲存、查詢執行、並發控制、安全性、備份等。

考試重點Datadog DBM 目前支援 PostgreSQL、MySQL、SQL Server、Oracle、MongoDB、Amazon DocumentDB、ClickHouse。考試是引擎無關的，不會考特定引擎知識，但要知道 DBM 支援哪些引擎。

主從架構與連線池

資料庫遵循主從（client-server）模型：資料庫伺服器執行 DBMS 並持有資料，客戶端透過網路連到伺服器，每個連線都會消耗伺服器資源。連線池（透過 PgBouncer、ProxySQL 或應用程式層級）在多個請求之間重複使用連線以降低開銷。

考試重點Datadog Agent 必須直接連到資料庫主機，不能透過連線池或負載平衡器，因為經過 proxy 可能導致 Agent 隨時間看到不同的主機、產生不準確的指標。

自架 vs. 受管資料庫

自架（self-hosted）資料庫跑在你自己掌控的基礎架構上，安裝、修補、備份、擴容都是你的責任。受管（managed）資料庫（AWS RDS、Azure SQL、Google Cloud SQL）由雲端廠商負責運行，你只需要設定和使用。DBM 兩者都支援，但受管常需要特定參數群組或 IAM 角色，自架則需要 Agent 直接用 localhost 或 socket 存取（設定差異見第 2 章）。

查詢的生命週期、複寫、Buffer Pool

查詢的生命週期：解析（語法檢查）→ 規劃/優化（引擎決定「怎麼」執行）→ 執行（實際的資料存取或修改），DBM 在規劃階段（執行計畫）和執行階段（延遲、影響列數、等待事件）分別呈現資料。

複寫：把資料從主節點（writer）複製到一個或多個複本節點（reader），提供高可用性和讀取擴展。要監控：複寫延遲、複寫狀態。

Buffer Pool / Shared Buffers：資料庫把常用資料留在記憶體裡（MySQL/SQL Server 叫 buffer pool，Postgres 叫 shared buffers）避免每次讀磁碟，快取命中率通常 >95% 代表表現良好。

吞吐量、延遲與資源使用率

吞吐量是資料庫每單位時間處理幾個查詢，延遲是每個查詢個別花多久完成，負載升高時兩者常呈反向關聯。資源競爭的核心是 CPU、記憶體、磁碟 I/O、網路，把這些跟查詢指標放在一起監控很重要，CPU 尖峰可能對應到某條特別耗費的查詢，高磁碟 I/O 可能代表缺索引造成全表掃描。

回傳列數 vs. 檢查列數優化良好的查詢只檢查它需要回傳的列數。如果查詢回傳 10 列卻檢查了 1000 萬列，這是強烈訊號，代表在做不必要的工作，通常是缺索引或篩選條件寫得不好，這個比例是判斷查詢效率最實用的指標之一。

索引的進階概念

索引讓資料庫不用掃描整張表就能快速找到列，類似書本後面的索引頁（基礎概念和實際範例見第 1 章）。三個沒在別處出現過的進階術語：

  • B-tree 索引：最常見的索引類型，適合相等和範圍查詢。
  • 涵蓋索引（covering index）：包含查詢需要的所有欄位，引擎完全不需要回頭查表。
  • 索引膨脹（index bloat）：隨著時間因更新和刪除，索引可能變得比需要的更大，拖累效能。

STEP 01 · 從一般健康檢查發現異常

團隊沒有收到任何告警觸發，也沒有使用者回報功能變慢，這次調查純粹是例行的一般健康檢查。從 APM > Database Monitoring 進入 Databases 總覽頁，展開 Summary Graphs 的 Wait Group Activity 圖表，看到資料庫上同時存在 CPU 等待、閒置、鎖定這幾種等待事件，其中鎖定事件的比例明顯偏高，是這次最需要優先處理的訊號。

呼應第 1 章「等待事件」：鎖定等待突增就是一個快速訊號，代表一個或多個查詢正在阻塞其他查詢。

STEP 02 · 翻活動連線快照，找到 # WAITERS

切到 Active Connections 分頁，點選查詢持續時間圖上比較高的尖峰點，查看該時間點的活動連線（每 10 秒一次的 pg_stat_activity 快照）。翻幾張快照後，找到 # WAITERS 欄位有數字、等待分組圖表上出現紅色長條的那一筆，展開看到完整 SQL。

STEP 03 · 揭露真相：一個被遺忘的測試 LOCK TABLE

完整 SQL 顯示：開發團隊有人在寫一條更新訂單數量的查詢時，語法沒寫好，用了 LOCK TABLE，而且還設成排程工作（cronjob）定期跑，導致大量其他查詢被卡住。

STEP 04 · 判斷關卡：這條鎖能不能直接停掉？

停掉一條鎖住的查詢之前，要先判斷它是不是可以被安全中止的東西。

✓ 查明是之前測試某功能時留下的殘留 cronjob，跟 Storedog 正常業務邏輯無關，可以安全停掉 ▼
⇢
✗ 另一種可能：合法的 schema migration如果這條 LOCK TABLE 其實是一個正在進行中的 ALTER TABLE／CREATE INDEX 這類需要排他鎖的合法 DDL，就不該直接 stop_locks 中止它，而應該讓它跑完，並把類似的操作排到低流量時段執行，這正是第 4 章「調查阻塞」提到的判斷原則，也是這一步真正在做的事。

STEP 05 · 用 Blocking Queries 的 Time Impact 量化影響

切到 Blocking Queries 分頁，能看到「造成阻塞的查詢」（Root Blocking Queries）和「正在等待這個阻塞的查詢」（Waiting Queries）兩組圖表。

✓ Time Impact 欄位確認這條 `LOCK TABLE` 查詢已經讓其他查詢等了超過 15 秒，影響確實顯著，值得優先處理 ▼
⇢
✗ 另一種可能：Time Impact 很低如果 Time Impact 只有零點幾秒、且沒有持續發生，代表這條阻塞只是偶發的正常鎖競爭，不需要特別介入處理，繼續觀察即可，不必馬上動用 stop_locks。

STEP 06 · 執行 stop_locks，鎖定事件排除

stop_locks

鎖定問題排除之後，才輪到下一個症狀：熱門商品查詢負擔過重。這一步示範了第 1 章「九大健康指標」裡強調的「單一指標說不了完整的故事」：鎖定事件排除，不代表資料庫已經完全健康，還有下一層問題等著被發現。

STEP 07 · 轉向 Query Metrics，找到下一個高負載查詢

Storedog 新加了一個「熱門商品排行」小工具，每隔幾秒就對 items 表跑一次查詢抓出最常被下單的前十項商品，這條查詢造成資料庫負擔很重、執行時間很長。切到 Query Metrics 分頁，點選 Average Rows 這欄的欄位標題排序整張表，SELECT id, description... 這條查詢排在最前面。

STEP 08 · Explain Plan Map View 鎖定 Sort 瓶頸

點進正規化查詢面板的 Explain Plans 分頁，Plan Operations 表格列出這條查詢會用到的所有操作，成本相當高。往下的 Map View 把整個執行計畫畫成視覺化樹狀圖，直接看出排序（Sort）操作占了最大部分的成本，是這條查詢執行時間過長的主要原因。

STEP 09 · 用 APM Trace 確認實際影響

正規化查詢面板右上角點 View Query Samples，這幾筆樣本成本大約落在 7000 左右，偏高。點進其中一筆，打開 Explain Plan Sample 面板切到 Trace 分頁：是 /get-item 路由的 GET 請求觸發了這條查詢，整個請求耗時約 1.06 秒，其中這條查詢就占了 256ms，拖慢了整個請求四分之一左右的時間。

這一步把「查詢本身效能不好」跟「對呼叫它的服務造成多少實際影響」串起來，是判斷要不要優先處理這條查詢的關鍵證據，呼應第 3 章的 APM-DBM 關聯機制。

STEP 10 · 第一次優化：縮小查詢範圍

去程式碼裡看實際查詢邏輯（dbm.py），發現篩選商品的門檻設得太寬。把產生篩選門檻的隨機範圍從 random.randint(1, 7000) 改成 random.randint(5000, 7000)，收斂成只挑真正銷量最高的一小群，重啟服務、等幾分鐘後回到 Query Metrics 驗證：成本下降，方向對了，但 Map View 顯示 Sort 依然占了 75% 的成本。

STEP 11 · 判斷關卡：Sort 瓶頸的真正來源是什麼？

回頭看查詢邏輯，是用 UNION 把 items 和 preorder_items 兩張表的結果合併起來。

✓ 查明 `UNION` 不只是把兩批結果接在一起，還會自動去除重複的列，而要去除重複，資料庫必須先把所有結果排序過一遍才能比對，這正是那個高成本排序節點的來源 ▼
⇢
✗ 另一種可能：誤判成索引問題如果沒有先去看 Map View 具體是哪個節點在吃成本，很容易誤以為 Sort 瓶頸是「缺索引」，跑去加一個根本無關的索引，實際上索引解決不了 `UNION` 去重造成的排序成本，白費工夫還可能拖慢寫入。

STEP 12 · 第二次優化：拿掉 UNION

preorder_items 裡的商品一旦正式上架，會被標記成 false，代表其實沒有必要同時查兩張表再做 UNION 去重。更好的做法是讓開發團隊調整資料寫入邏輯，把已上架的商品直接維護進 items 表，查詢端只需要簡化成只查一張表。改完重啟服務，回到 Query Metrics 改依 Rows per Query 排序驗證，成本比前一次優化又大幅下降，因為現在整條查詢只剩單一個掃描操作。

STEP 13 · 回饋進 Recommendations 與告警設計

這整趟調查的證據，回頭變成兩件事的輸入：如果這條查詢的退化是慢慢發生而非一次性的程式碼問題，DBM Recommendations 的 Query Load Increase 發現本來就會自動標出來；而這次鎖定事件也提醒團隊，可以針對 Waiting Queries 或 Long Running Queries（見第 5 章）設定 DBM 監控，讓下一次類似的殘留 cronjob 不用等到例行健康檢查才被發現，而是主動告警。
