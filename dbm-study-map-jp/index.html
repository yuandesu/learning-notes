テレメトリー概念と健康指標

この章では 2 つの土台となる問いに答えます。DBM がどのエンジンをサポートしているか、標準統合と DBM は結局どこが違うのか。続いてデータベースの「バイタルサイン」を 9 つの健康指標に分解し、さらに 3 つのレンズを 6 種類のテレメトリータイプへと展開して 1 つずつ掘り下げます。この章を読み終えれば、以降のすべての調査動作で使うデータソースの意味が理解できるようになります。

標準統合 vs. DBM、どこまで多く見えるか

標準統合は Postgres や SQL Server などの一般的な統合で、「ホストレベル / インスタンスレベル」の指標を収集する、データベースを「外から中へ」見る視点です。DBM はそれを置き換えるものではなく、標準統合の上に重ねて、クエリレベルの一式のテレメトリーを追加するものです。

見えるもの接続数、SQL コンパイル速度、buffer pool 使用率、ディスク I/O、複製の状態などの集計数値。データベースが「健全かどうか」を教えてくれます。見えないもの「なぜ」の部分、つまりクエリレベルの詳細は完全にブラックボックスです。設定は簡単で、Agent ユーザーは基本の SELECT 権限だけで済みます。
追加で得られるものQuery Metrics（上位 200 件の正規化されたクエリの集計統計）、Query Samples（ある瞬間の実際の実行スナップショット、保存期間 15 日間）、自動収集される Explain Plans、Wait Events 分析、ブロッキングクエリのインサイト、正規化とオブファスケーション処理、APM 関連付け、DBM Recommendations。代償Agent の YAML に dbm: true を追加する必要があり、追加の権限が必要（Postgres なら pg_monitor）で、さらにデータベースホストへ直接接続する必要があり、proxy／ロードバランサー／コネクションプールを経由できません。ほとんどのワークロードでは追加負荷はクエリ実行時間の 1% 未満、CPU の 1% 未満に収まります。

9 つの健康指標、データベースのバイタルサイン

医師が患者のバイタルサイン、心拍、血圧、体温を診るのと同じイメージです。各項目をクリックして判読ロジックを確認してください。

① 接続数（Connections）▸

何個のクライアントがデータベースに接続しているか、上限までどれくらい余裕があるか。持続的な上昇はコネクションリークの可能性があり、急激な増加はトラフィックの急増またはアプリケーションの設定ミスの可能性があります。長時間アイドル状態の接続はリソースの無駄です。

② クエリ量とスループット（Query Volume and Throughput）▸

1 秒あたり何件のクエリを処理しているか（読み取り vs 書き込み）。急激な減少は上流のアプリケーションが壊れていることを示す可能性があり、急激な増加は暴走したプロセスがデータベースに負荷をかけている可能性があります。

③ クエリレイテンシー（Query Latency）▸

平均、p50、p95、p99、最大値。p95/p99 が特に重要です。平均値は外れ値を覆い隠してしまうためで、例えば平均 10ms でも p99 が 2 秒であれば、1% のユーザー体験が極めて悪いことを意味します。

④ アクティブセッションとデータベース負荷（Wait Events 分析）▸

「何件のクエリが動いたか」だけでなく、クエリがその瞬間「どのリソースを待っているか」を見ます。4 大分類は次のとおりです。CPU（演算リソースの奪い合い、クエリの最適化やインスタンスの増強を検討）、I/O（ディスクの読み書き待ち、インデックス不足や buffer pool のサイズ不足の可能性）、ロック / Latch（他のセッションがロックを解放するのを待つ、通常は長いトランザクションによる競合）、ネットワーク（データ転送待ち、結果セットが大きすぎるか遅延が高い可能性）。

⑤ ブロッキングクエリ（Blocking Queries）▸

1 つの長いトランザクションがロックを握ったままになり、連鎖的に数十件のクエリが詰まることがあります。DBM は「根本原因となるブロッキングクエリ」とブロックされているクエリを視覚的に特定できます。実際のロック事例は第 4 章、第 7 章を参照してください。

⑥ リソース使用率（CPU/メモリ/ディスク/I/O）▸

データベースの「物理的な限界」です。クエリがどれだけ良く書かれていても、ホストに CPU、メモリ、ディスク容量がなければ同様に落ちます。CPU が持続的に 80% を超えると限界が近いことを意味し、メモリはキャッシュヒット率を見ます。ディスク容量を使い切ると致命的な障害になります。

⑦ レプリケーションの健康（Replication Health）▸

レプリケーション遅延（replica がプライマリノードにどれだけ遅れているか）、レプリケーションの状態（接続中で継続的に同期しているか）。遅延が大きすぎると古いデータを読んでいることになり、切断はフェイルオーバーの後ろ盾を失うことを意味します。

⑧ データベースエンジン固有のテレメトリー▸

Postgres は vacuum の動作を見ます（デッドタプルが蓄積し続けているのは autovacuum が追いついていないサイン）。SQL Server は接続数、システムメモリ、スループットを見ます。MongoDB は遅い操作、実行プラン、レプリケーション状態の変化を見ます。

⑨ DBM Recommendations 自体も健康のシグナル▸

生の指標を提供するだけでなく、影響度の高いブロッキングクエリ、使われていないインデックス、ディスク容量不足の警告を能動的に分析してフラグを立てます。各推奨事項には深刻度のランクがあり、完全なタイプ一覧は第 4 章を参照してください。

総合的な判読の鍵は「関連付け」にある単一の指標だけでは全体の話は語れません。CPU が高い + あるクエリがデータベース時間の大部分を消費 → そのクエリの最適化が必要。レイテンシー上昇 + ロック待ちの増加 → リソース問題ではなくブロッキング問題。接続数急増 + スループット低下 → クエリ効率の問題ではなく接続の飽和。I/O が高い + キャッシュヒット率が低い → メモリの追加が必要か、クエリが読みすぎている。

6 種類のテレメトリータイプ、3 つのレンズを 1 つずつ掘り下げる

公式ドキュメントはデータの種類を 3 つの大分類に凝縮していますが、これは同じデータベースを見る 3 つの異なる「レンズ」です。以下の 6 種類のテレメトリーは、この 3 つのレンズを実際に展開したものです。

Metrics · 衛星視点

ホストレベルの統合指標で、「データベース全体の状況はどうか」に答えます。dashboard と閾値アラートの基礎です。限界: 「何が起きたか」しか見えず、「誰が引き起こしたか」は見えません。

Query Metrics · ストリートビュー視点

正規化された各クエリごとの集計パフォーマンス統計で、データベースをブラックボックスからクエリレベルで推論できるものへと変えます。

Query Samples · 顕微鏡視点

ある時点で実際に実行された個別のスナップショットです。限界: あくまで偏りのあるサンプリングであり、完全な記録ではありません。

典型的な調査の順序は、Metrics（「データベースに負荷がかかっている」）→ Query Metrics（「このクエリパターンがデータベース時間の 40% を占めている」）→ Query Samples（「今回の実行は 3:47 PM に 12 秒かかった」）です。実際の画面ではさらに Explain Plans、Wait Events、Active Sessions、Schemas が加わり、6 種類に展開されます。

テレメトリータイプ答える問い
Query Metricsどのクエリが最も遅い / 最もリソースを消費しているか
Query Samples今回具体的にどこが遅かったか
Explain Plansデータベースはこのクエリをどう実行したか
Wait Eventsクエリは何を待っているか
Active Sessionsその瞬間データベース内で何が起きていたか

典型的な調査の順序: Query Metrics → Query Samples → Explain Plans → Schemas → Wait Events / Active Sessions。

Query Metrics、正規化と query_signature

DBM は同じクエリシグネチャを持つすべての実行を、パラメータの値に関わらず 1 つのグループにまとめ、平均レイテンシー、総実行時間、返却行数、呼び出し回数を計算します。

正規化とは何かクエリに実際に代入されたパラメータの値をプレースホルダーに置き換え、パラメータは違ってもロジックが同じクエリを同じ「クエリシグネチャ」として扱います。 
SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending'
SELECT * FROM orders WHERE user_id = 55103 AND status = 'shipped'
正規化後はどちらも同じクエリシグネチャに分類されます。SELECT * FROM orders WHERE user_id = ? AND status = ?。構造が同じであれば（テーブル名、カラム、演算子、句の並びがすべて同じ）同じシグネチャとみなされ、構造的な差異があれば（カラムが 1 つ多い、`WHERE` の順序が違う、`JOIN` が 1 つ多いなど）別のシグネチャとして個別に集計されます。
試験のポイントフィルタリングには query_signature を使い、query フィールドは使いません。理由は、タグ名は 200 文字で切り詰められるためクエリ文が長いと `query` タグは一意にならない可能性がある一方、`query_signature` は固定長のハッシュ値であり、信頼できる識別根拠になるためです。
実戦例、EC サイトのチェックアウトページが突然遅くなったQuery Metrics を「総実行時間」でソートすると、SELECT * FROM orders WHERE user_id = ? AND status = ? が最もリソースを消費していることが判明しました。平均レイテンシー 850ms（先週はわずか 120ms）、1 分あたり 3,200 回呼び出し、返却行数の平均 4,500 行（先週はわずか 50 行）。返却行数の急増は `LIMIT` の欠落かインデックスが効いていない可能性を示唆します。
保存期間公式ドキュメント（Database Monitoring Data Collected、Data Retention Periods）には Query Metrics の保存期間が 15 か月と明記されています。

Query Samples、「平均的に遅い」から「今回なぜ遅いか」へ

ある収集時点で取得された個別のクエリ実行です。正確なクエリ文、実行時間、ホスト、関連する Explain Plan を含み、APM トレースへ直接リンクします（第 3 章参照）。

実戦例Query Metrics からそのクエリが「平均的に」遅いことが分かったら、Query Samples に切り替えて、実行に 2.3 秒かかり、ホストが postgres-replica-02 で、関連する APM トレースが checkout-service の /api/v1/checkout からのものである 1 件を見つけます。トレースをクリックすると、あるユーザーが 12,000 件の過去の注文履歴を持っていたことが今回特に遅かった原因だと分かります。
試験のポイント保存期間は 15 日間で、Query Metrics の 15 か月とは桁が 1 つ違います。これはよく出る比較ポイントです。DBM は全量取得ではなくサンプリングであるため、あるクエリがサンプルに出てこないのは、その期間に取得されなかった可能性が高く、実行されていないという意味ではありません。

Explain Plans、すべての用語をゼロから分解する

Explain Plan は、クエリプランナーがクエリを実行するために選んだ手順の表現です。Explain Plan 全体は「レストランの調理手順書」のようなものだとイメージしてください。お客さん（SQL）は「ステーキを 1 つ」と言うだけで、厨房の中でどう作るかは厨房が自分で決めます。この内部の判断と手順の一式が Explain Plan です。

誰がどうやるか決めるのか、クエリプランナーとノード。クエリプランナーは厨房で「方法を考える」シェフのような存在です。お客さんは食べたいものを言うだけで、シェフが自分で手順を考えます。この手順が Explain Plan であり、各行が 1 つの「ノード」です。動作が複雑になると複数のノードが積み重なり、これが Map View がツリー状に見える理由でもあります。

Seq Scan（全表スキャン）: 分類されていない倉庫の中でモノを探すようなもので、箱を 1 つずつ開けて確認するしかありません。

Seq Scan on orders  (cost=0.00..15420.00 rows=4500)
  Filter: (user_id = 98712 AND status = 'pending')

倉庫の入り口に「A 類のモノは 3 番棚にある」という一覧が貼ってあり、それを一目見るだけでどこに行けばよいか分かる、これが Index Scan（インデックススキャン）です。実際にこの一覧を作ってみます。

CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
`user_id` を第一ソートキーとし、同じ `user_id` のデータをさらに `status` でソートします。作成時にデータベースは各行の `(user_id, status)` の値を取り出してソートし、独立したデータ構造（PostgreSQL のデフォルトは B-tree）を組んで別途保存します。

なぜカラムの順序をこう並べるのか: `user_id` は `status` よりはるかに区分度が高く（`user_id` はほぼすべての値が異なるのに対し、`status` は通常 `pending`、`shipped`、`cancelled` など少数の値しかありません）、区分度の高いカラムを最初に置くことで「目的の位置へ飛ぶ」ステップの範囲をできるだけ絞り込めます。

Index Scan using idx_orders_user_status on orders  (cost=0.42..8.50 rows=3)
コストが 15,420 から 8.5 へと大幅に低下しています。

クエリ SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending' の実際の実行手順は次のとおりです。① プランナーがインデックスが `WHERE` で使われている 2 つのカラムをカバーしていることを見つけ、Index Scan を選択する。② インデックス内で二分探索（毎回半分に絞る）を使って `user_id = 98712` の開始位置を素早く特定する。N 回ではなく log(N) 回の比較で済む。③ その位置から後方へ読み進める。同じ `user_id` のデータはインデックス内で連続して並んでいるため。④ `status` は第二ソートキーなので、`pending` のデータはまとまって並んでおり、1 件ずつ確認する必要がない。⑤ インデックスの各レコードにはテーブル内の実際の行を指すポインタが付いており、条件に合う項目を見つけたらそのポインタでテーブルに戻り実データを読み出す。このプロセス全体で、条件に合わない 499,997 行を一切見ていません。

データを取得した後どう加工するか: Filter（フィルタリング、`WHERE` に対応）、Sort（ソート、`ORDER BY` に対応、通常はすべてのデータがテーブルに揃うまで並べ替えを始められません）、Join（結合、`Nested Loop` はリストが小さいときに 1 件ずつもう一方を探しに行き、`Hash Join` は両方とも小さくないときに片方をハッシュテーブルにまとめ、`Merge Join` は両方が元々ソート済みのときにファスナーのように合わせます）、Aggregate（集計、`COUNT`/`SUM`/`GROUP BY`、通常は最後のステップです）。

cost: かかった金額や秒数ではなく、シェフが心の中で「このやり方はどれくらい面倒か」に付けたスコアのようなものです。表記は「開始スコア..合計スコア」で、経験則に基づく推測にすぎず、同じプラン内の他の動作とだけ比較でき、クエリをまたいだり別のマシンと比較したりはできません。rows: シェフが「この動作が終わったらだいたい何件残るか」を推測した値です。この推測値が実際の値と大きくずれている場合、それは「シェフが今回やり方を間違えたかもしれない」というシグナルです。

プロセス全体に多くの動作が積み重なっている場合、DBM はプロセス全体をツリーとして描画し、色の濃淡やボックスの大きさでどのボックスが最も負荷が高いかを直接教えてくれます。1 つずつ暗算で比較する必要はありません。

実戦例あるクエリサンプルで Explain Plan を確認すると Seq Scan が見つかり、データベースは `orders` テーブル全体（50 万行）を 1 行ずつスキャンしていました。Map View ではこのノードが総コストの 98% を占めていることが表示されています。修正: `(user_id, status)` の複合インデックスを作成し、コストが 15,420 から 8.5 に低下しました。
注意すべてのクエリに Explain Plan があるわけではありません。実行時間が短すぎてサンプリングされずプランが付かないクエリもあれば、構造的に条件に合わないもの（特定のロックモードのトランザクションなど）もあります。また収集には explain_statement 関数が正しく設定されている必要があります（第 2 章参照）。Query Sample に関連する Plan がない場合は、まずこの関数を確認してください。

Wait Events、銀行の窓口ロビー

Analogyデータベースを銀行の窓口ロビーだと考えてください。各「接続」は手続き中の 1 人の顧客で、顧客が手続きをしている各瞬間は、「サービスを受けている最中」か「何かを待っている」かのどちらかです。

CPU 待ち: クエリが実際に処理されている最中であり、正常な忙しさです。この比率がずっと高い場合、通常はクエリが処理するデータ量や計算量が大きいことを意味します。ロック待ち（Lock wait）: この接続があるデータを操作しようとしているが、既に別の接続にロックされている状態です。例えば Lock:transactionid は別のトランザクション全体が終わるのを待っていることを意味し、急増はトランザクションが長時間終わらずに詰まっていることを示します。I/O 待ち: データがディスクからメモリに読み込まれる、またはディスクに書き込まれるのを待っている状態です。比率が高い場合、通常はデータ量が大きいかディスク速度が追いついていないことを意味します。アイドル（Idle）: 接続は現在クエリを実行していないが、まだ枠を占有している状態です。ブロッキング（blocking）: ロック待ちの裏側で、A が B のロック解放を待っているとき「B が A をブロックしている」と言います。Active Connections タブで「誰が誰をブロックしているか」を直接確認できます。

実戦例は第 4 章、第 7 章の Lock:transactionid の急増、stop_locks による追跡調査、根本原因がテスト用の LOCK TABLE の cronjob が消し忘れられていたという実際の事例を参照してください。

Active Sessions、10 秒ごとのスナップショット

データベースのアクティブな接続状態の定期的なスナップショットで、約 10 秒ごとに取得されます。現在実行中のクエリ、実行時間、待機状態、どの接続が他の接続をブロックしているかを捉えます。Wait Events とセットで使うものです。Wait Events は「急増が発生した」ことを教え、Active Sessions は「急増発生時に具体的に何が動いていたか」を教えてくれます。

AnalogyWait Events が「この瞬間、ある顧客が何を待っているか」のライブ放送だとすれば、Active Sessions は警備システムが数秒おきにロビー全体を撮影する写真です。「定期的に撮影して保存」であって連続録画ではないため、2 枚の写真の間に起きたことは記録されませんが、事後でも 1 枚ずつさかのぼって異常発生時に何が起きていたかを見つけられます。複数の接続が同じ理由で同時に詰まっている場合、これらの接続を 1 本の「ブロッキングチェーン」としてつなぎ、どの接続がどのクエリを実行して引き起こしたかを具体的に特定できます。

Schemas、テーブル構造は妥当か

1 枚のテーブルはファイルキャビネットのようなもので、各行のデータは形式が統一された 1 枚の伝票だとイメージしてください。カラム（column）は各伝票に必ずある 1 つの欄です。データ型はこの欄に何を入れられるかを規定します（例えば numeric(10,2)）。主キーは他のどの伝票とも絶対に重複せず、データベースはデフォルトで自動的にインデックスを作成します。インデックスはデータを素早く特定するための一覧で、インデックスサイズはこの追加の一覧自体がどれだけのストレージを占めるかを示し、無料ではありません。

試験で補足される基礎用語B-tree（ほとんどのデータベースのインデックスがデフォルトで使うツリー構造で、「半分に絞る」二分探索を成立させます）、covering index（インデックス自体にクエリが必要とするすべてのカラムが含まれ、テーブルに一切戻る必要がありません）、index bloat（インデックスがデータの更新に伴い、もう有効でない項目を大量に蓄積し、占有スペースが増え、クエリが遅くなり、定期的な再構築やクリーンアップが必要になります）。テーブル名、カラム名、インデックス名といった構造的な情報はオブファスケーションの対象外で、Schemas ページに完全な形で表示されます。

データプライバシーとオブファスケーション処理

Query Samples は実際に実行されたクエリ文を取得します。データベースにはユーザーのメールアドレス、支払い情報、個人情報がよく保存されているため、Agent は Datadog にデータを送る前に 2 つのことを行います。クエリの正規化（リテラル値を `?` プレースホルダーに置き換える、ホストを離れる前にリテラル値を取り除く仕組みでもあります）とパラメータのオブファスケーション処理（obfuscation）（もう 1 段階の保護で、デフォルトで実行され、正規化がカバーしていないケース、例えばクエリ文中のコメントなどを処理します）。

データの種類デフォルトでオブファスケーションされるか
クエリパラメータの値（バインドされたリテラル値）される
クエリ文中のコメントされる
テーブル名とカラム名されない
インデックス名されない
Explain Plan の構造されない
ホストのメタデータとデータベースタグされない
試験でよく出る盲点テーブル名やカラム名自体に機密情報が含まれている場合（例えばテーブル名が credit_cards など）、これらの名前自体は見えてしまいます。データベースの log が Datadog に送られる場合、バインドパラメータを含む完全な SQL クエリ文が含まれる可能性があり、オブファスケーション処理は DBM のテレメトリーパイプラインにのみ適用され、log は別の経路を通ります。SQL クエリ内のコメントは Agent に収集されオブファスケーションを経ない可能性があり、この点は第 3 章の trace 関連付けのコメント機構でも特に注意が必要です。その機構自体が SQL のコメントに trace id を仕込むことで成り立っているためです。

調査を始める前に知っておくべき 2 つのこと

  1. DBM はサンプリング（sampling）であり、全量取得ではありません。あるクエリが Query Samples に出てこないのは、その時間帯に取得されなかった可能性が高く、実行されていないという意味ではありません。
  2. 伝播の遅延が存在します。クエリの実行から指標が DBM の画面に表示されるまでには短い遅延があります。修正の検証をする際は数分待ってから最新のデータを確認してください。

Storedog はこの章の実装例で使う EC アプリケーションで、ユーザーが商品を検索、閲覧、購入できます。アーキテクチャは 1 つの web フロントエンド、1 つのバックエンドサーバー、そして 2 つの PostgreSQL データベースで構成されています。1 つは spree のバックエンド関連データを保存し、もう 1 つは広告、割引コード、商品データを保存します。第 1 章、第 4 章で見たクエリの多くは、この 2 つのデータベースが Storedog のビジネスロジックを処理する際に発生したものです。

Chapter 03 · APM Correlation

APM と DBM の関連付け

前の 2 つの章ではそれぞれ 6 種類のテレメトリーデータ自体と、DBM をどう構築してこれらのデータを収集するかを扱いました。この章では別のことを扱います。DBM が収集したデータベース側のテレメトリーが、APM が収集したアプリケーション側のテレメトリーとどうつながるかです。

解決したい問題

関連付けがない場合、DBM と APM は 2 つの独立した世界です。APM は「この API エンドポイントが遅く、データベースの span が 2 秒かかっている」ことを教えてくれますが、「なぜ」遅いかは教えてくれません。DBM は「この正規化されたクエリのレイテンシーが高い」ことを教えてくれますが、どのサービスが原因かは教えてくれません。つなげることで、開発者はデータベースに直接アクセスしなくてもデータベースのパフォーマンスを理解できるようになり、DBA も特定のサービスのリクエストトラフィックがデータベース負荷にどう影響しているかを理解できるようになります。

3 層の仕組み、Tracer、Agent、trace ID の注入

この関連付けはデータベース自体に何か特別な設定があるわけではなく、アプリケーション側の設定と Agent の APM 機能が組み合わさって実現されているもので、第 2 章の Storedog 実験環境と完全に対応しています。

backend、worker のようなサービスは datadog-tracer-backend.rb のような初期化ファイルをマウントします。これは dd-trace ライブラリの設定ファイルで、Ruby/Rails アプリケーション起動時に自動でトレーシング機能を組み込む役割を担います。導入後、Tracer はアプリケーションがデータベースを呼び出す動作（例えば ActiveRecord 経由の SQL）を自動的にインターセプトし、エンジニアが手動でコードを追加する必要はありません。

これが Postgres が「service」として APM に現れる根本的な理由です。アプリケーション側が「データベースを呼び出した」と報告しているのであって、データベース自体は自分がトレースされていることを知りません。導入後は APM > Software Catalog で Postgres というサービスを見つけられます。

Agent の container には DD_APM_ENABLED=true、DD_APM_NON_LOCAL_TRAFFIC=true が設定されており、8126 という port が開いています。これは Agent が各サービスから送られてくる trace データを受け取るための専用チャンネルです。アプリケーション側の Tracer が生成した span は、この port を通じて Agent に送られ、Agent が Datadog へ転送します。各アプリケーションサービスにも DD_AGENT_HOST=datadog が設定されており、Tracer にどの Agent へデータを送るべきか伝えています。

単に Tracer と APM があるだけでは、「アプリケーションがデータベースを呼び出し、どれだけ時間がかかったか」という span レベルの情報しか見えません。APM のあるトレースから DBM が収集した Query Samples、Explain Plans の詳細へ直接つなげるには、trace ID を DBM のデータ収集に注入する仕組みが必要です。

APM tracer は trace のコンテキスト（trace ID、span ID、service name、environment）を SQL コメントの形式で、実際のクエリ文の先頭に付けて送信します。

/*dddbs='orders-db',ddps='checkout-service',ddtid='abc123'*/ SELECT * FROM orders WHERE id = ?
データベースは `SELECT` の部分だけを実行します（コメントは無視され、パフォーマンスに影響しません）。Agent が Query Sample を収集する際にこのコメントを読み取り、trace のメタデータを抽出して関連付けを作ります。これが、DD_DBM_PROPAGATION_MODE=full という環境変数が第 2 章の `postgres`、`backend`、`worker` など複数のサービスそれぞれに個別に設定されている理由でもあります。両側で設定して初めて対応が取れるためです。

3 種類の Propagation Mode

full
完全な trace 情報
完全な trace 情報（trace ID、span ID、service name、environment）を送信し、双方向のナビゲーションが可能です。trace の span から DBM の Query Sample へジャンプでき、DBM のサンプルから完全な trace へも戻れます。ほとんどの統合でこれが推奨されており、第 2 章の実験環境でも実際に採用されている設定です。
service
service name のみ送信
trace/span ID を含まないため、どのサービスがデータベース負荷を引き起こしたかは分かりますが、特定の trace へジャンプすることはできません。
disabled
一切送信しない
DBM と APM はそれぞれ独立していて関連付けがなく、この章の冒頭の「2 つの世界が互いに無関係」な状態に戻ります。

関連付けを有効にするために必要な 4 つの条件

  • DBM が設定されデータを収集している（dbm: true、第 2 章参照）。
  • APM が設定されており tracing がある（Datadog の tracing ライブラリ、または正しい属性を持つ OpenTelemetry が導入されている）。
  • Tracer に Propagation Mode が設定されている（言語ごとに個別に設定するか、環境変数 DD_DBM_PROPAGATION_MODE=full を使う）。
  • Unified Service Tagging（DD_SERVICE、DD_ENV、DD_VERSION をすべて設定し、service/env/version のタグが APM と DBM の両方で一致するようにする）。

クエリの正規化/オブファスケーション処理との関係（重要な区別）

第 1 章では、クエリ文が Datadog に送られる前に正規化とオブファスケーション処理を経ることに触れました。あれはクエリ内のバインドされたパラメータ値が漏れないようにする仕組みです。ここでの trace ID の注入はまったく別の経路を通ります。動かしているのはクエリ文の一番先頭にあるコメントであり、クエリ自体のパラメータではありません。そしてコメントはオブファスケーション処理されません。

試験でよく出る盲点アプリケーションが独自に機密情報を含むコメント（例えばユーザー ID や session token）を SQL に追加している場合、これらも Agent に収集され Datadog に送られ、オブファスケーションを経ません。オブファスケーション処理はパラメータ値のみを対象とし、SQL コメント自体は対象外です。

まとめ、典型的な調査フロー

Postgres 自体は APM に対応するための特別な設定を一切されておらず、アプリケーションが Tracer を導入し、span を APM が有効な Agent に送信しているだけです。DD_DBM_PROPAGATION_MODE が SQL コメント内の trace ID を使って、これらの span をデータベース側で収集されたクエリデータとつなげています。

Query Metrics vs. Query Samples、いつどちらを使うか

Query Metrics · トレンドアナリスト

過去のパフォーマンスデータを集計したもので、上位 200 件の正規化されたクエリ、保存期間 15 か月。「どのクエリパターンが最もデータベース時間を消費しているか」「このクエリは今月遅くなったか」「1 秒あたり何回呼び出されているか」に答えます。できないこと: 具体的なある 1 回の実行、具体的なある瞬間に何が起きたかは見えません。

Query Samples · 事件調査員

ある時点で実行中だったクエリの個別スナップショットで、実行の詳細と Explain Plan が付き、保存期間 15 日間。「3:47 PM にレイテンシーが急上昇したとき何が動いていたか」「全表スキャンだったか」「誰がこのクエリを実行していたか」に答えます。

実戦例、Query Metrics のソートで疑わしいクエリを見つけるStoredog に新しく「人気商品ランキング」ウィジェットが追加され、数秒ごとに `items` テーブルに対してクエリを実行し最もよく注文される上位 10 商品を取得しています。このクエリがデータベースに重い負荷をかけていました。Query Metrics タブに切り替えて Average Rows 列のヘッダーをクリックしてソートすると、`SELECT id, description...` が先頭に来ます。クエリ文中の `?` プレースホルダーは正規化の結果です。

N+1 クエリ問題

1 つの `JOIN` で関連データを一度に取得するのではなく、アプリケーションが各項目ごとに個別にクエリを実行してしまうパターンです。例: EC ページに 100 件の注文一覧を表示し、各行に顧客名を表示する必要がある場合。

効率的（1 つのクエリ）

SELECT orders.id, orders.total, customers.name
FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE orders.created_at > '2024-01-01'

N+1（101 個のクエリ）

まず 1 つのクエリですべての注文を取得し、その後アプリケーションが結果に対してループを回し、各注文ごとに個別にクエリを実行して顧客名を調べます。100 件の注文なら 101 回のデータベース往復になります。

なぜ重要か: 個々のクエリは速いかもしれません（2ms）が、101 個合計すると 200ms を超え、データ量が 1 万件規模に拡大すると非常に深刻になります。厄介なのは、N+1 は開発段階では気づかれないことが多い点です。テスト用データベースの行数が少ないためで、本番環境でデータ量が増えて初めて顕在化します。

DBM がどうやって発見を助けるかAPM で遅いトレースを開くと、フレームグラフに数百個の細かくほぼ同じデータベース span が積み重なって見えます。DBM の Query Metrics ではこの正規化されたクエリの Requests 数が異常に多く、個々の実行は速いかもしれません（Average latency が低い）が、Total time は高くなっています。両方が同時に現れるのが明確なシグナルです。修正方法はアプリケーションコード側にあり、データベース自体ではありません。よくある対処は `JOIN` で一度に取得する、eager loading を使う、または `WHERE id IN (...)` を使った 1 本のバッチクエリにまとめることです。

レイテンシーの調査 / 負荷の調査 / ブロッキングの調査

レイテンシーの調査、4 つのステップ▸

① データベースが根本原因かどうかを確認する（遅いトレースのフレームグラフを見て、データベース span がリクエスト時間の大部分を占めていればボトルネック）。② Query Metrics を Average latency でソートして最も遅いクエリパターンを見つける、ただし Total time も併せて確認する。③ クエリ詳細を開いて Explain Plans（全表スキャンか、高コストな join/sort か）、Wait Events、Hosts Running This Query、Metrics タブ（ゆっくり上昇しているか急上昇か）を確認する。④ 異なる時点の Explain Plan を比較し、新しいプランが出現した後にパフォーマンスが悪化していればプランの退化である。

負荷の調査、どこを見るか▸

ホスト詳細ページ最上部のアクティブ接続のタイムシリーズグラフでは、待機のグループ別に接続状態を分けて見られます。ほとんどの接続が CPU 待ちであれば演算集約的、ほとんどが I/O 待ちであればディスク集約的、ほとんどがロック待ちであれば競合があることを意味します。Query Metrics を Percent time でソートし、どのクエリパターンがデータベース総時間の最大割合を占めているかを見ます。

ブロッキングの調査、完全な実戦例▸

ブロッキングとは、1 つのクエリがロックを握ったままになり、同じロックを必要とする別のクエリを待たせている状態です。深刻な場合はブロッキングチェーンを形成します。A が B をブロックし、B が C をブロックするといった具合です。確認すべきはホスト詳細 → Blocking Queries タブ（誰が誰をブロックしているかを視覚的なツリー図で表示）、Wait Events 分析（ロック/latch 待ちが主要であれば「リソース枯渇」ではなく「競合」の問題であることを意味する）、DBM Recommendations（影響度の高いブロッカーを自動検出してフラグを立てる）です。

実戦例、Storedog の LOCK TABLE 事件と stop_locksDatabases 総覧ページで Wait Group Activity グラフを展開すると、CPU 待ち、アイドル、ロックといった Wait Events が同時に存在していました。今回最優先で対応すべきはロックイベントです。Active Connections タブに切り替え、何枚かスナップショットをめくって # WAITERS フィールドに数字があり、待機グループのグラフに赤いバーが現れている 1 件を見つけて展開すると、完全な SQL が見えます。開発チームの誰かが注文数量を更新するクエリを書く際に構文を誤り、`LOCK TABLE` を使ってしまい、しかもスケジュールジョブ（cronjob）として定期実行するように設定してしまったため、大量の他のクエリがブロックされていました。Blocking Queries タブに切り替え、Time Impact でこのクエリが他のクエリを 15 秒以上待たせていたことを確認します。このクエリは以前ある機能をテストした際の残骸で、Storedog の正常な業務ロジックとは無関係なため、そのまま停止します。stop_locks。完全なインタラクティブトレース（各ステップの別の可能性を含む）は独立タブの「アーキテクチャ全体像」を参照してください。

パフォーマンスの退化を特定する

パフォーマンスの退化とは、元は良好だったクエリが悪化し始めることを指し、静かに進行し、しばらく蓄積してから明らかな中断を引き起こすことがあります。データベース自体は「現在」の統計状態しか報告しないため、DBM が正規化されたクエリの主要指標を時系列（Metrics タブ）として保存することで、初めて過去のデータと比較できるようになります。

DBM がどう検出するか: Recommendations の「Query Load Increase」として自動的に検出しフラグを立て、クエリのワークロード変化、ユーザーやサービスのアクティビティ急増、schema の変更、直近のデプロイを自動的に関連付けます。

よくある原因: プランの退化、schema の変更（インデックスが削除されると Missing Index としてフラグが立ちます）、データの増加、アプリケーションの変更、インフラの変更。

実戦事例、人気商品クエリを最後まで最適化する

まずコード内の実際のクエリロジック（dbm.py）を確認すると、商品をフィルタする閾値が広すぎ、本当の売れ筋商品ではなく範囲がかなり広い集団を抽出していたことが分かりました。

クエリの範囲を絞る: フィルタ閾値を生成するランダム範囲を `random.randint(1, 7000)` から `random.randint(5000, 7000)` に変更しました。

SELECT id, description, order_count, last_hour, image_url, NULL AS is_preorder
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}
UNION
SELECT id, description, order_count, last_hour, image_url, is_preorder
FROM preorder_items
WHERE order_count::int > {random.randint(5000, 7000)}

サービスを再起動し、数分待ってから Query Metrics に戻り Average Rows でソートして検証しました。Query Sample のコストは下がっており、方向性は正しいです。次に Traces タブを見ると、今回の所要時間は以前（元は 225ms 超）より明らかに減っています。しかし全体のコストはまだ高めで、Explain Plan の Map View に戻ると、Sort 操作が依然としてこのクエリの総コストの 75% を占めており、次に対処すべきボトルネックです。

UNION を取り除く: クエリロジックは `UNION` を使って `items` と `preorder_items` の 2 つのテーブルの結果を結合していました。`UNION` は単に 2 つの結果をつなげるだけでなく、自動的に重複行を除去します。そして重複を除去するには、データベースはまずすべての結果を一度ソートしなければなりません。これがまさに Map View にあった高コストな Sort ノードの出所です。

さらに理解を深めると、`preorder_items` 内の商品は正式に販売開始されると `false` にマークされます。つまり 2 つのテーブルを同時に照会して `UNION` で重複除去する必要は実はなく、より良い方法は開発チームがデータ書き込みロジックを調整し、販売開始済みの商品を直接 `items` テーブルで管理することです。そうすればクエリ側は 1 つのテーブルだけを照会するように簡素化できます。

SELECT *
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}

サービスを再起動し、Query Metrics に戻って Rows per Query でソートして検証すると、コストは前回の最適化からさらに大幅に低下しました。今やクエリ全体が単一のスキャン操作だけになり、`UNION` の重複除去によるソート負荷が不要になったためです。

この事例が示す核心的な考え方DBM は「問題を見つける」ためだけのツールではありません。コードを修正した後、同じ Query Metrics、Explain Plans、Query Samples、APM Trace の一式を使って「修正が効いたかどうかを検証する」こともできます。実際の数値（cost、所要時間、rows）を使い、「体感的に速くなったはず」という推測を置き換えます。一連の調査（ロック問題の解消 → 高負荷クエリの特定 → Explain Plan で Sort ボトルネックを特定 → 過去のトレンドで確認 → APM Trace で実際の影響を確認 → 2 回の最適化イテレーションで検証）は、この章で前述したすべての診断フレームワークを実際に一通り走らせた完全なデモです。インタラクティブ版は独立タブの「アーキテクチャ全体像」を参照してください。

アラートの集約方式、Simple vs. Multi Alert

Simple Alert

すべての報告元を横断して集計し、1 つまたは複数のグループが閾値を超えたら 1 回だけアラートを発火します。この戦略で通知ノイズを減らせます。

Multi Alert

設定したグルーピングパラメータごとに個別にアラートを適用します。例えば `@db.user` でグループ化すると、条件をトリガーした各データベースユーザーがそれぞれアラートを受け取ります。粒度は細かくなりますが、通知が多くなる可能性もあります。

試験のポイントデータベース監視では通常、host でグループ化した Multi Alert が最も理にかなっています。知りたいのは「どのホスト」で問題が起きているかであり、「あるホスト」で何かあったという情報だけでは不十分だからです。

Chapter 06 · Database Fundamentals

データベース基礎知識付録

試験範囲外ではあるものの、DBM の画面を理解するために必須の一般的なデータベース知識です。DBM 専用の内容ではなく、他の章で扱っていない部分だけを残しています。

データベースとは何か

データベースはデータを保存、取得、管理するための組織化されたシステムであり、情報をファイル、スプレッドシート、文書に散らばらせておくやり方に代わるものです。

Analogy倉庫だとイメージしてください。すべての在庫を 1 つの大きな部屋に放り込み、何かを探すたびに部屋全体をひっくり返すこともできますし、ラベル付きの棚、列、箱に分類して収め、目録システムでモノがどこに正確にあるかを教えてもらうこともできます。データベースはあの整理された倉庫です。

なぜファイルだけでは足りないのか: ファイルは「複数人が同時に読み書きしても壊れない」「数百万件のレコードから効率的に検索する」「停電時にデータが書きかけのままにならない」「異なる種類のデータ間の関連付け」といった要求に直面するとすぐに限界を迎えます。データベースはこれらの問題を解決します。

テーブル、行、カラム、主キー、外部キー

データベースの最も一般的な組織方法はテーブル（table）で、スプレッドシートに似ています。1 つのテーブルはあるモノの種類を表し、各行（row）は具体的な 1 つのインスタンス、各カラム（column）は 1 つの属性です。各テーブルには通常主キー（primary key）があり、各行を一意に識別するカラムです。テーブル同士は外部キー（foreign key）で関連付けられることが多く、あるテーブルのあるカラムが別のテーブルの主キーを指します。

テーブル/行/カラム/インデックスのより完全な実例は第 1 章の Schemas の段落を参照してください。

SQL と CRUD

SQL（構造化クエリ言語）はリレーショナルデータベースとやり取りする方法で、宣言型言語です。データベースに「何が欲しいか」を伝えるのであって「どうやって取得するか」ではなく、エンジンが自分で最良の実行方法を考えます。主な操作は CRUD に対応します。Create（INSERT）、Read（SELECT）、Update（UPDATE）、Delete（DELETE）。

試験のポイントDBM の認定試験では SQL を「書く」ことは求められず、「読み解く」ことだけが問われます。ただしこれらの文が何をしているかを理解しておくと、Datadog 内の正規化されたクエリや Explain Plan を理解する助けになります。

データベース管理システム（DBMS）

DBMS はデータベースを実行し管理するソフトウェアです。「Postgres」や「MySQL」と言うとき、指しているのはこのソフトウェア自体であり、データそのものではありません。ストレージ、クエリ実行、並行性制御、セキュリティ、バックアップなどを担当します。

試験のポイントDatadog DBM は現在 PostgreSQL、MySQL、SQL Server、Oracle、MongoDB、Amazon DocumentDB、ClickHouse をサポートしています。試験はエンジンに依存しない形式で、特定エンジンの知識は問われませんが、DBM がどのエンジンをサポートしているかは知っておく必要があります。

クライアントサーバーアーキテクチャとコネクションプール

データベースはクライアントサーバー（client-server）モデルに従います。データベースサーバーが DBMS を実行しデータを保持し、クライアントはネットワーク経由でサーバーに接続します。各接続はサーバーのリソースを消費します。コネクションプール（PgBouncer、ProxySQL、またはアプリケーションレイヤー経由）は複数のリクエスト間で接続を再利用してオーバーヘッドを下げます。

試験のポイントDatadog Agent はデータベースホストへ直接接続する必要があります。コネクションプールやロードバランサーを経由することはできません。proxy を経由すると、Agent が時間の経過とともに異なるホストを見てしまい、不正確な指標が生成される可能性があるためです。

セルフホスト vs. マネージドデータベース

セルフホスト（self-hosted）データベースは自分でコントロールするインフラ上で動作し、インストール、パッチ適用、バックアップ、拡張はすべて自分の責任です。マネージド（managed）データベース（AWS RDS、Azure SQL、Google Cloud SQL）はクラウドベンダーが運用を担当し、設定と利用だけを行えばよくなります。DBM はどちらもサポートしていますが、マネージドは特定のパラメータグループや IAM ロールが必要になることが多く、セルフホストは Agent が localhost や socket で直接アクセスする必要があります（設定の違いは第 2 章参照）。

クエリのライフサイクル、レプリケーション、Buffer Pool

クエリのライフサイクル: 解析（構文チェック）→ プランニング/最適化（エンジンが「どうやって」実行するかを決める）→ 実行（実際のデータアクセスまたは変更）。DBM はプランニング段階（Explain Plan）と実行段階（レイテンシー、影響を受けた行数、Wait Events）でそれぞれデータを表示します。

レプリケーション: データをプライマリノード（writer）から 1 つ以上のレプリカノード（reader）へ複製し、高可用性と読み取りのスケーリングを提供します。監視すべきは、レプリケーション遅延、レプリケーションの状態です。

Buffer Pool / Shared Buffers: データベースはよく使われるデータをメモリ内に保持し（MySQL/SQL Server では buffer pool、Postgres では shared buffers と呼ばれます）、毎回ディスクを読みに行かなくて済むようにします。キャッシュヒット率は通常 95% 超であれば良好なパフォーマンスを意味します。

スループット、レイテンシー、リソース使用率

スループットはデータベースが単位時間あたりに処理するクエリ数、レイテンシーは各クエリが個別に完了するまでにかかる時間です。負荷が上昇すると両者はしばしば反比例の関係になります。リソース競合の核心は CPU、メモリ、ディスク I/O、ネットワークです。これらをクエリ指標と一緒に監視することが重要で、CPU のピークは特定の負荷の高いクエリに対応している可能性があり、高いディスク I/O はインデックス不足による全表スキャンを示している可能性があります。

返却行数 vs. 検査行数よく最適化されたクエリは、返却が必要な行数だけを検査します。あるクエリが 10 行を返すのに 1000 万行を検査していたら、これは強いシグナルであり、不必要な作業をしていることを意味します。通常はインデックス不足かフィルタ条件の書き方が悪いことが原因です。この比率はクエリの効率を判断する最も実用的な指標の 1 つです。

インデックスの発展的な概念

インデックスはデータベースがテーブル全体をスキャンしなくても行を素早く見つけられるようにするもので、本の巻末索引に似ています（基本概念と実例は第 1 章参照）。他の場所で出てこなかった発展的な用語を 3 つ紹介します。

  • B-tree インデックス: 最も一般的なインデックスタイプで、等価検索と範囲検索に適しています。
  • covering index: クエリが必要とするすべてのカラムを含み、エンジンは一切テーブルに戻る必要がありません。
  • index bloat: 時間の経過とともに更新や削除によって、インデックスが必要以上に大きくなり、パフォーマンスを低下させることがあります。

STEP 01 · 一般的な健康チェックで異常を発見

チームはアラートのトリガーを一切受け取っておらず、ユーザーから機能が遅いという報告もありませんでした。今回の調査は純粋に定例の一般的な健康チェックです。APM > Database Monitoring から Databases 総覧ページに入り、Summary Graphs の Wait Group Activity グラフを展開すると、データベース上に CPU 待ち、アイドル、ロックといった Wait Events が同時に存在しており、そのうちロックイベントの割合が明らかに高いことが分かりました。これが今回最優先で対応すべきシグナルです。

第 1 章の「Wait Events」に対応しています。ロック待ちの急増は素早いシグナルであり、1 つまたは複数のクエリが他のクエリをブロックしていることを意味します。

STEP 02 · アクティブ接続のスナップショットをめくって # WAITERS を見つける

Active Connections タブに切り替え、クエリ実行時間のグラフで比較的高いピークをクリックし、その時点のアクティブ接続（10 秒ごとの pg_stat_activity スナップショット）を確認します。何枚かスナップショットをめくった後、# WAITERS フィールドに数字があり、待機グループのグラフに赤いバーが現れている 1 件を見つけ、展開すると完全な SQL が見えます。

STEP 03 · 真相の発覚、忘れられたテスト用の LOCK TABLE

完全な SQL を見ると、開発チームの誰かが注文数量を更新するクエリを書く際に構文を誤り、LOCK TABLE を使ってしまい、しかもスケジュールジョブ（cronjob）として定期実行するように設定してしまったため、大量の他のクエリがブロックされていたことが分かりました。

STEP 04 · 判断ゲート、このロックはそのまま停止してよいか

ロックしているクエリを停止する前に、それが安全に中止できるものかどうかを判断する必要があります。

✓ 以前ある機能をテストした際に残った cronjob であり、Storedog の正常な業務ロジックとは無関係だと判明し、安全に停止できる ▼
⇢
✗ 別の可能性、正当な schema migrationもしこの LOCK TABLE が実際には進行中の ALTER TABLE／CREATE INDEX のような排他ロックを必要とする正当な DDL であった場合、直接 stop_locks で中止すべきではなく、完了するまで待たせた上で、同様の操作を低トラフィック帯に予定するべきです。これはまさに第 4 章「ブロッキングの調査」で触れた判断原則であり、このステップが実際に行っていることでもあります。

STEP 05 · Blocking Queries の Time Impact で影響を定量化する

Blocking Queries タブに切り替えると、「ブロッキングを引き起こしているクエリ」（Root Blocking Queries）と「このブロッキングを待っているクエリ」（Waiting Queries）の 2 組のグラフが見えます。

✓ Time Impact フィールドで、この `LOCK TABLE` クエリが他のクエリを 15 秒以上待たせていたことを確認。影響は確かに大きく、優先対応の価値がある ▼
⇢
✗ 別の可能性、Time Impact が非常に低いもし Time Impact が 1 秒未満で、かつ継続的に発生していない場合、このブロッキングは単発的な正常なロック競合にすぎず、特別に介入する必要はなく、観察を続ければよく、すぐに stop_locks を使う必要はありません。

STEP 06 · stop_locks を実行し、ロックイベントを解消

stop_locks

ロック問題が解消されて初めて、次の症状、人気商品クエリの負荷過剰に取り掛かれます。このステップは第 1 章「9 つの健康指標」で強調した「単一の指標だけでは全体の話は語れない」ことを示しています。ロックイベントの解消は、データベースが完全に健全になったことを意味せず、次の層の問題がまだ発見を待っています。

STEP 07 · Query Metrics に切り替え、次の高負荷クエリを見つける

Storedog に新しく「人気商品ランキング」ウィジェットが追加され、数秒ごとに items テーブルに対してクエリを実行し最もよく注文される上位 10 商品を取得しています。このクエリはデータベースに重い負荷をかけ、実行時間も長くなっていました。Query Metrics タブに切り替え、Average Rows 列のヘッダーをクリックしてテーブル全体をソートすると、SELECT id, description... というクエリが先頭に来ます。

STEP 08 · Explain Plan の Map View で Sort ボトルネックを特定

正規化されたクエリパネルの Explain Plans タブを開くと、Plan Operations テーブルにこのクエリで使われるすべての操作が一覧表示され、コストがかなり高いことが分かります。下にある Map View は Explain Plan 全体を視覚的なツリー図として描画しており、Sort 操作が最大部分のコストを占めていることが直接見て取れます。これがこのクエリの実行時間が長すぎる主な原因です。

STEP 09 · APM Trace で実際の影響を確認する

正規化されたクエリパネル右上の View Query Samples をクリックすると、これらのサンプルのコストはおおよそ 7000 前後で、やや高めです。1 件をクリックし、Explain Plan Sample パネルを開いて Trace タブに切り替えます。/get-item ルートの GET リクエストがこのクエリをトリガーしており、リクエスト全体の所要時間は約 1.06 秒、そのうちこのクエリが 256ms を占めており、リクエスト全体の約 4 分の 1 を遅らせていました。

このステップは「クエリ自体のパフォーマンスが悪い」ことと「それを呼び出しているサービスに実際どれだけの影響を与えているか」をつなげるもので、このクエリを優先対応するかどうかを判断する上で鍵となる証拠です。第 3 章の APM-DBM 関連付けの仕組みに対応しています。

STEP 10 · 1 回目の最適化、クエリの範囲を絞る

コード内の実際のクエリロジック（dbm.py）を確認すると、商品をフィルタする閾値が広すぎることが分かりました。フィルタ閾値を生成するランダム範囲を random.randint(1, 7000) から random.randint(5000, 7000) に変更し、本当に売上上位の小さな集団だけに絞り込みました。サービスを再起動し、数分待ってから Query Metrics に戻って検証すると、コストは下がり方向性は正しかったものの、Map View では Sort が依然として 75% のコストを占めていることが分かりました。

STEP 11 · 判断ゲート、Sort ボトルネックの本当の原因は何か

クエリロジックを見直すと、UNION を使って items と preorder_items の 2 つのテーブルの結果を結合していました。

✓ `UNION` は単に 2 つの結果をつなげるだけでなく、自動的に重複行を除去し、除去のためにデータベースはまずすべての結果を一度ソートして比較しなければならないと判明。これがまさにあの高コストな Sort ノードの出所である ▼
⇢
✗ 別の可能性、インデックス問題と誤判する先に Map View で具体的にどのノードがコストを消費しているかを確認しなければ、Sort ボトルネックを「インデックス不足」だと誤解し、まったく無関係なインデックスを追加してしまいがちです。実際にはインデックスは `UNION` の重複除去によるソートコストを解決できず、無駄骨に終わるどころか書き込みを遅くする可能性さえあります。

STEP 12 · 2 回目の最適化、UNION を取り除く

preorder_items 内の商品は正式に販売開始されると false にマークされます。つまり 2 つのテーブルを同時に照会して UNION で重複除去する必要は実はありませんでした。より良い方法は開発チームがデータ書き込みロジックを調整し、販売開始済みの商品を直接 items テーブルで管理することです。そうすればクエリ側は 1 つのテーブルだけを照会するように簡素化できます。変更後にサービスを再起動し、Query Metrics に戻って Rows per Query でソートして検証すると、コストは前回の最適化からさらに大幅に低下しました。今やクエリ全体が単一のスキャン操作だけになったためです。

STEP 13 · Recommendations とアラート設計へフィードバック

この一連の調査で得られた証拠は、振り返って 2 つのことへの入力になります。もしこのクエリの退化が一度きりのコード問題ではなく徐々に進行するものであれば、DBM Recommendations の Query Load Increase がもともと自動的にフラグを立ててくれます。また今回のロック事件は、チームに Waiting Queries や Long Running Queries（第 5 章参照）に対して DBM のモニターを設定できることも気づかせてくれました。次回同様の残骸 cronjob が、定例の健康チェックまで発見されずに待たされるのではなく、能動的にアラートされるようにするためです。

一連の調査（ロック問題の解消 → 高負荷クエリの特定 → Explain Plan で Sort ボトルネックを特定 → APM Trace で実際の影響を確認 → 2 回の最適化イテレーションで検証 → モニター設計へフィードバック）は、第 4 章全体の診断フレームワークを実際に一通り走らせた完全なデモです。
