Chapter 01 · Foundation

為什麼需要 SIEM

這一章回答一個問題：雲端供應商到底幫你防了什麼、又留了哪些洞讓你自己補？答案決定了你必須自己收集哪些資料，而這正是整條 Cloud SIEM 產線的原料來源。

先講全名：Cloud SIEM 到底是什麼

SIEM 全名是 Security Information and Event Management（安全資訊與事件管理），是資安領域行之有年的一種系統類別，核心工作就是把分散在各系統的紀錄（log/event）集中起來，做關聯分析、找出可能的威脅。Datadog 的 Cloud SIEM 就是這類系統長在 Datadog 平台上的實作：直接沿用你已經送進 Datadog 的 log，即時分析，不用另外接一套獨立的資安系統。

Analogy 把公司裡分散的監視器畫面（各系統的 log）全部接到同一間監控室（SIEM），由同一批人、用同一套規則盯著看，而不是每個部門各自看自己的畫面、各自判斷有沒有異常。

共享責任模型（Shared Responsibility Model）

公有雲的安全從來不是「供應商全包」或「客戶全包」，而是依服務型態分工，且分界線會隨著服務越「代管」而往供應商那邊移動。

Analogy 你租的公寓大樓裝了門禁、監視器、消防系統（供應商負責），但你家裡的門要不要上鎖、貴重物品放哪裡、備用鑰匙給了誰——這些永遠是你自己的責任，大樓管理員不會幫你管。

IaaS · 例如 AWS EC2

IaaS 全名 Infrastructure as a Service（基礎設施即服務）：虛擬機器層級。客戶自己管作業系統、應用程式、網路規則；供應商只管實體機房、硬體、虛擬化層。客戶要負責的範圍最大。

PaaS / 全代管 · 例如 RDS、Lambda

PaaS 全名 Platform as a Service（平台即服務）：供應商連作業系統、patch、底層維運都包了，客戶只要管自己的資料和存取設定。

不管哪種型態，永遠不變

資料、身分（identity）、存取權限（access policy）永遠是客戶的責任，供應商不會幫你管員工的帳號權限設得對不對。

對監控的實際意義 供應商會產生大量安全遙測資料（稽核 log、流量 log、威脅偵測結果），但不會主動幫你送到 SIEM。你要自己決定收集哪些來源、送到哪裡、保留多久——這就是「為什麼需要 SIEM」的答案：供應商給原料，你需要工具把原料集中、正規化、分析。

關鍵 Log 來源五大類

Cloud SIEM 要發揮效果，必須看得到整個環境。點開每一類看範例：

雲端稽核 Log（Cloud audit logs）▸

例如 AWS CloudTrail、GCP Audit Logs、Azure Activity Logs。記錄「誰對雲端環境做了什麼 API（Application Programming Interface，應用程式介面，系統之間互相溝通、下指令的介面）呼叫、什麼管理操作」，是雲端安全監控的地基。
範例：有人用 IAM（Identity and Access Management，身分與存取管理）使用者的憑證呼叫了 DeleteBucket API，CloudTrail 會記下是誰、什麼時候、從哪個 IP。

身分與驗證 Log（Identity and authentication logs）▸

例如 Okta、Auth0、Azure AD。追蹤登入事件、MFA（Multi-Factor Authentication，多因子驗證）挑戰、帳號活動。
專有名詞：Impossible Travel（不可能的移動）——同一個帳號短時間內從相距很遠的兩個地點登入（例如 10 分鐘內先在台北登入、又在紐約登入），物理上不可能真的移動這麼快，代表帳號可能被盜用。

網路流量 Log（Network flow logs）▸

例如 AWS VPC（Virtual Private Cloud，虛擬私有雲） Flow Logs、Azure NSG（Network Security Group，網路安全群組） Flow Logs、GCP VPC Flow Logs。只記錄連線的中繼資料（誰連到誰、哪個 port、多少流量），不記錄封包內容本身。
範例：內部主機突然對外部陌生 IP 大量傳輸資料，可能是資料外洩（data exfiltration）；內部主機間出現異常橫向連線，可能是橫向移動（lateral movement）——攻擊者拿下一台機器後，再用它當跳板攻擊其他內部機器。

SaaS 與協作工具 Log▸

SaaS 全名 Software as a Service（軟體即服務）：不用自己安裝維護，開瀏覽器登入就能用的雲端軟體。例如 Microsoft 365、Google Workspace、Slack、GitHub。追蹤使用者在協作平台和開發工具上的活動。

端點與第三方安全工具 Log▸

例如 CrowdStrike、SentinelOne、Amazon GuardDuty。把專門安全工具本身已經產生的告警和發現（findings）轉送進來，Cloud SIEM 可以把這些現成的判斷結果也納入關聯分析。

Content Pack：把「從零開始」變成「插電即用」

Content Pack 是針對特定 log 來源打包好的一整組安全內容：Detection Rules、Dashboards、Investigator widgets、Workflow Automation / SOAR blueprints（SOAR = Security Orchestration, Automation and Response，安全編排、自動化與應變），有時還包含 parser。

你要自己做自己找資料源接進來 → 自己寫 Detection Rule → 自己刻 Dashboard → 自己建 Workflow → 每一項都要花時間驗證正不正確。
範例：AWS CloudTrail Content Pack啟用並接好 CloudTrail log 之後直接得到：偵測異常 AssumeRole 行為（角色假設異常，常見於權限提升攻擊）的 Detection Rule、CloudTrail 活動儀表板、針對 IAM user / IP 的調查視圖、自動通知或自動回應的 workflow。

另一種偏向威脅情報整合的例子：Recorded Future Content Pack，提供預建偵測規則、log enrichment（豐富化）、整合式 dashboard。

考試重點
  • 常考「這個 Content Pack 依賴哪些資料來源」。
  • 啟用 Content Pack 會自動更新 SIEM Index Filter（把該 Content Pack 需要的 log 來源自動加進 filter，見第 2 章），不用手動另外設定。
  • Content Pack 的核心價值是縮短 time-to-value（從裝好到真正產生價值的時間）。

附註：AWS Org 帳號串接（CloudFormation StackSet）

要把整個 AWS Organization 底下的多個帳號一次接進 Cloud SIEM，Datadog 提供一份 CloudFormation StackSet，靠 Organization 的 trusted access（信任存取） 和 service-managed permissions（服務代管權限），讓管理帳號自動把必要的 IAM role 部署到每個成員帳號裡。

常見部署失敗原因 部署設定裡的 Specify regions（指定區域） 這一步，只能選單一區域。IAM 是 AWS 的全域（global）服務，不分區域，但 StackSet 的部署機制是依「帳號 × 區域」建立 stack instance；如果選了多個區域，Datadog 的樣板會嘗試在多個區域各自建立同名的 IAM role，造成衝突，導致部署在還沒替任何帳號建立好 IAM role 之前就整個失敗。

容易混淆但不是原因的設定：Execution configuration 設成 Active（平行執行）只影響部署的速度/並行度；Deployment targets 設成整個 Organization 而非某個 OU（Organizational Unit，組織單位）只是佈署範圍大小的設定，這兩者都不會直接導致部署整個失敗，只有「多區域選擇」會。

Cloud SIEM 在 Datadog Security 產品線中的定位

Cloud SIEM 只是 Datadog Security 產品線的其中一塊，各自負責安全堆疊的不同層面：

Cloud Security（雲端安全態勢）▸

關注基礎設施的「安全態勢（posture）」——重點是設定本身安不安全，跟 Cloud SIEM 關注的「有沒有被攻擊」是不同層面的問題。底下分三塊：

  • Misconfigurations（設定錯誤）：持續稽核資源設定，對照 CIS（Center for Internet Security，網際網路安全中心）、PCI DSS（Payment Card Industry Data Security Standard，支付卡產業資料安全標準）等合規框架寫好的檢查項目。
    範例某個 S3 bucket 被設成「任何人都能公開讀取」，這是一個設定錯誤，不需要有人真的來偷資料，光是這個設定本身就已經是風險，Misconfigurations 會直接標出來。
  • Identity Risks（身分風險）：偵測 IAM（Identity and Access Management）相關的風險。
    範例某個 IAM 角色被授予了「管理員（admin）」等級的權限，但過去 90 天完全沒被使用過，這就是「權限過大（excessive permissions）」加「沒在用的憑證（unused credentials）」的組合，一旦這組憑證外洩，攻擊者能拿到的權限會遠超過實際需要。
  • Vulnerabilities（弱點掃描）：掃描容器和主機，找出已知的安全漏洞。
    範例某台 EC2 主機上跑的一個開源套件版本，被掃描出對應到一個 CVE（Common Vulnerabilities and Exposures，通用漏洞揭露，業界對已知安全漏洞的統一編號系統），Vulnerabilities 會列出這台主機有這個弱點，即使它現在還沒被拿來攻擊。
Workload Protection（工作負載防護）▸

監控主機和容器上的檔案、網路、程序活動，抓執行期間（runtime，程式實際跑起來的當下）發生的威脅。

App and API Protection（應用程式與 API 防護）▸

偵測並攔截應用層攻擊，例如 SSRF（Server-Side Request Forgery，伺服器端請求偽造）——攻擊者誘騙伺服器代替他發出請求，去存取原本存取不到的內部資源；以及 SQL（Structured Query Language，結構化查詢語言）Injection（SQL 注入）——把惡意 SQL 語法混進輸入欄位，操縱資料庫查詢。同時提供 API 探索與態勢管理。

Code Security（程式碼安全）▸

在開發生命週期中找出自家程式碼和開源相依套件裡的弱點。

產品之間怎麼互相加值 Cloud SIEM 可以拿其他安全產品的資訊來豐富自己的偵測結果。例如第 5 章會提到的 Risk Insights，就是把 Cloud SIEM 的 signal，加上 Cloud Security 的 Misconfigurations 和 Identity Risks 資料，合併算出一個統一的「實體風險分數」，不只看到「發生了什麼」，還能看到「這個實體本身有多危險」。
Chapter 02 · Pipeline

資料怎麼變乾淨

光有 log 送進來還不夠。這一章拆解 log 進來之後要經過哪些加工站，才會變成規則看得懂、查得到的乾淨資料。用同一筆 log 走完整條產線，一步一步看它長什麼樣。

先搞懂 Pipeline 跟 Processor 是什麼關係

在 Datadog 的 Log Management 裡，Pipeline（管線）是一組依序執行的 Processor（處理器），設定在 Logs → Configuration → Pipelines 頁面。每個 processor 只負責一件很小的事，前一站處理完的結果會原封不動傳給下一站，跟工廠產線一樣：原始 log 是原料，processor 是一站一站的加工站，最後輸出的是可供 SIEM 分析的標準化 log。

下面用同一筆 log，走完整條產線的 5 個步驟，一步一步看它實際長什麼樣、每一步用哪個 processor：

Grok Processor 之前，log 通常只是一串非結構化文字，規則沒辦法針對特定欄位比對。

原始 log2020-01-01 12:00:01 google oauth login success by John Doe from 1.2.3.4

Grok Processor：從非結構化字串裡把要的欄位抓出來，就像把一句亂糟糟的話拆成一格一格可用欄位。

名字由來 Grok 這個字來自 1961 年的科幻小說《異鄉異客（Stranger in a Strange Land）》，作者 Robert Heinlein 在書中創造這個詞，意思是「完全地、直覺地理解一件事的本質」，不只是表面知道，而是徹底吃透。日誌處理界（Logstash 最早這樣用，後來 Splunk、Datadog 都沿用同一套慣例）借用這個詞，因為這個 processor 做的事正是「讀懂一句本來雜亂無章的文字，理解裡面每一段代表什麼意義」，所以取名 Grok。

Grok 的實際做法是用預先定義好的樣式（pattern，本質上是包裝過的正規表示式 regex）去比對文字，命中樣式的片段就會被抓出來、貼上欄位名稱。

原始 log 對照 Grok pattern（示意）
%{date("yyyy-MM-dd HH:mm:ss"):timestamp} %{word:evt.name} login %{word:evt.outcome} by %{data:usr.id} from %{ip:network.client.ip}
套用上面這樣的 pattern 到原始文字，就能解析成： 
{
  "usr.id": "John Doe",
  "evt.category": "authentication",
  "evt.name": "google oauth",
  "evt.outcome": "success",
  "network.client.ip": "1.2.3.4"
}
有了這些欄位，規則才能查 evt.outcome:failure 這種條件；如果沒有 Grok 解析，這整句話對規則來說只是一串看不懂結構的文字，沒辦法針對「outcome 是不是失敗」單獨比對。

OCSF Processor：把來源特有的欄位 remap（重新對應）成跨來源一致的標準欄位。

來源背景 OCSF（Open Cybersecurity Schema Framework）是 2022 年由 AWS 和 Splunk 共同發起、捐給開源社群的一套「資安事件資料綱要（schema）」標準，後續 Datadog、CrowdStrike、IBM 等上百家資安廠商陸續加入採用。Schema（綱要）白話講就是「一份規定資料要長什麼樣子的說明書」：規定一個「登入事件」該有哪些欄位、欄位該叫什麼名字、值該是什麼型態，讓所有廠商都照同一份說明書出貨，不再各講各的話。

OCSF 把事件分成不同類別（class），例如第 1 章提過的 Authentication（驗證）、API Activity（API 活動）、Account Change（帳號變更），每個類別底下規定好一組標準屬性名稱。這裡示範「使用者」這個屬性，在 OCSF 裡標準名稱是 actor.user.name，不管來源是 CloudTrail、Okta 還是這裡的 Google OAuth log，Processor 都會把各自原本的欄位對應過去：

GeoIP Processor：根據 IP 位址補上地理位置資訊。

實際怎麼查到地理位置 GeoIP Processor 背後接的是一份IP 位址對照地理區塊的資料庫（例如業界常見的 MaxMind GeoLite2，Datadog 內建維護這類資料庫），裡面記錄了「哪一段 IP 範圍是分配給哪個國家/城市的網路業者」。Processor 拿到一個 IP，就去資料庫裡查它落在哪一段範圍，回傳對應的國家、城市、經緯度。這跟你查詢「這支電話號碼的區碼是哪個城市」的邏輯一樣：不是即時去問誰，而是查一份已知的對照表。
豐富化後多出的欄位
{
  "network.client.ip": "1.2.3.4",
  "country": "Japan",
  "city": "Tokyo"
}
用途：Impossible Travel 偵測（需要先知道每筆登入的地理位置才能算兩地距離）、新國家登入偵測、地圖化顯示攻擊來源。

SIEM Index Filter 決定這筆已經處理乾淨的 log 要不要送進 Cloud SIEM index。

「通過 filter」實際上是什麼意思 SIEM Index Filter 本質上就是一條查詢語法（跟你平常在 Datadog 搜尋 log 用的語法一樣），設定在 Logs → Configuration → Indexes → 該 SIEM index → Index filter 裡。「通過 filter」的意思是：這筆 log 身上帶的欄位/tag，符合這條查詢條件。
範例：一條實際的 filter query 可能長這樣 
source:(cloudtrail OR okta OR github OR guardduty)
這條 filter 的意思是：只要這筆 log 的 source 標籤是 CloudTrail、Okta、GitHub、GuardDuty 其中之一，就算「通過」，會被放行進 SIEM index。如果今天有一筆 log 是 source:my-custom-app，而 filter 裡沒有這個來源，這筆 log 就不會進入 SIEM index，任何 Detection Rule 都看不到它。

怎麼讓一筆 log「通過」：① 手動到 Logs Index Configuration 頁面，把該來源的 source（或其他自訂 tag）加進 filter 查詢條件；② 更省事的做法是啟用對應的 Content Pack（見第 1 章），Datadog 會自動把該 Content Pack 需要的來源加進這條 filter，不用手動編輯查詢語法。

只要通過 filter，log 就會被存進 SIEM index——即使沒有觸發任何 Detection Rule，也還是會被留下來供之後回頭調查。不符合 filter 的 log，完全不會被任何 Detection Rule 看到。

OOTB Pipeline 是唯讀的起點

OOTB（Out-Of-The-Box，開箱即用）：Datadog 已經幫常見來源做好預設 pipeline，例如 AWS CloudTrail pipeline、AWS GuardDuty pipeline，會自動解析常見欄位（eventName、sourceIPAddress、userIdentity）。

重要細節這類 OOTB pipeline 通常唯讀，不能直接改，但可以在它後面串接自訂處理，補上組織特有的解析需求。

Log 保留分層

可以想成資料的「熱度分層」，背後的邏輯是查詢速度跟儲存成本互相拉扯：查得越快的層級，成本越高，所以不會把所有 log 都無限期放在最貴的那一層。

層級適用場景查詢速度
Standard indexing頻繁查詢的熱資料，能負擔較多運算資源最快
Flex Logs不常查、但需要保留且可搜尋，最長 15 個月中等
Log Archives合規/長期儲存，很少查詢最慢（要先還原）
範例：一套典型的分層策略 最近 30 天的 log 放 Standard indexing（分析師天天在查，要快）；30 天到 15 個月的 log 轉存到 Flex Logs（合規或事後鑑識偶爾會查，但不用即時）；超過 15 個月、只是為了滿足法規要求留存的 log，轉進 Log Archives（幾乎不會查，查的時候先花時間還原）。這三層是在 Logs → Configuration → Indexes 裡針對每個 index 設定保留天數/轉存規則。

不管選哪一層，Cloud SIEM 都在資料進來的當下即時分析，威脅偵測不會因為選了便宜的儲存層級而延遲——即時分析發生在 log 剛進來的那一刻，之後要把它歸檔到哪一層只是「事後儲存」的決定，兩者是分開的兩件事。Security Signal 本身保留 15 個月。

Flex Logs 的限制（易忽略考點）

Flex Logs 不支援 Log Monitor，官方表明不會支援，原因兩個：① 查詢速度較慢，Monitor 需要近乎即時掃描，Flex 延遲會讓告警不即時；② 會大量消耗 Flex 的運算資源（Query Pool），Monitor 持續反覆查詢會把額度吃光。Watchdog 也不支援 Flex Logs（同樣需要持續掃描）。

替代方案：先用 Metrics from Logs 把想監控的模式轉成 metric，再對 metric 設 Monitor。一句話記憶：Flex Logs 適合「留著以後回查」，不適合「即時盯著它告警」。

Index 排序：SIEM index 必須排第一

Log 經過 pipeline 之後要決定進哪個 index。一個帳號底下通常設有好幾個 index（例如一般應用程式 log 的 index、稽核用的 index），Cloud SIEM 也有自己專用的 index（例如 cloud-siem-xxxx），而這些 index 在設定頁面裡是有先後順序的。

為什麼順序會影響「收不收得到」 每個 index 都有自己的篩選條件、每日配額（quota）、取樣規則。log 會依照 index 排列的順序被依序檢查，排在前面的 index 如果配額被用完、或設定了排除規則，可能會提早把某些 log 攔下來或丟棄，導致排在後面的 index（包含 SIEM index）根本沒機會再看到這筆 log。
考試重點Cloud SIEM index 必須排在第一位，確保它一定能優先拿到符合條件的 log，不會被其他 index 的配額或排除規則搶先攔截。畫面可能出現警告「The Cloud SIEM index is not in the first」，看到要知道代表 index 順序設定錯誤，需要到 Logs → Configuration → Indexes 頁面手動把 SIEM index 拖到最上面（reorder）。
Chapter 03 · Rule Basics

規則基礎：類型、元件、八種偵測方法

資料乾淨之後，真正的判斷邏輯在這裡發生：signal 是什麼、規則分幾種、共用元件有哪些、又用什麼方法認定「這是異常」。這些是下一章 MITRE 對應和進階調校的地基。

Signal ≠ 原始 log

偵測規則定義 Cloud SIEM 要對即時進來的 log 套用什麼邏輯，符合條件就產生 Security Signal。

Analogylog 是原始證據，規則是偵探的推理邏輯，signal 是偵探破案後寫出的「這裡有問題」報告。

三種規則類型

Real-time rules
log 一進來就持續監控，條件符合馬上產生 signal
範例：規則正在算「5 分鐘內失敗登入次數」，這個累計和監控是即時在跑的。
Scheduled rules
每隔固定時間跑一次查詢，適合抓拉得很長的威脅
範例：DNS（Domain Name System，網域名稱系統） tunneling（把資料藏在 DNS 查詢裡外送）、low-and-slow brute force（故意放慢速度分散嘗試，躲過短時間門檻）。這類攻擊要拉長時間範圍定期回顧才抓得到。
Historical jobs
對歷史資料跑一次性查詢，不是持續監控
用途：backtesting（回測）新規則——「如果這條規則兩個月前就存在，會不會抓到某個已知事件」，驗證規則會不會漏抓或抓太多。

Cloud SIEM 內建幾百條 OOTB 規則，由 Datadog Security Research 團隊持續維護，新規則自動匯入帳號。Rules List 可用 source 篩選規則涵蓋狀況。

OOTB 規則跟自訂規則的關係（容易誤會的細節）
  • OOTB 規則由 Datadog 持續開發，更新自動匯入帳號；自訂規則是使用者自己建立維護的，不會收到 Datadog 的自動更新，要調整只能自己手動改。
  • 兩者是互相獨立的規則，不存在「誰蓋過誰」的優先權機制。就算自訂規則和某條 OOTB 規則針對同一種活動，兩條規則會各自獨立評估、各自可能產生各自的 signal，自訂規則不會自動取代或蓋過 OOTB 規則。
  • 建立一條功能類似的自訂規則，不會讓對應的 OOTB 規則自動被移除，兩者會一起繼續運作，除非使用者自己手動停用其中一條。

規則的五個共用元件

Detection method（偵測方法）▸

定義 Cloud SIEM 怎麼評估 log，共 8 種方法，見下方章節。

Search queries（搜尋查詢）▸

指定要符合哪些 log 條件。

Conditions（觸發條件）▸

決定什麼時候要產生 signal，以及嚴重程度（severity）等級。

Playbook（應變手冊）▸

包含規則名稱、調查用的說明文字、標籤（tag），其中包含 MITRE ATT&CK 對應標籤（見下一章開頭）。

Suppressions（抑制條件）▸

定義哪些狀況下不要產生 signal，用來排除已知誤判，降低 alert fatigue。抑制的是「signal 這一層」，log 本身完全沒被刪除，之後仍可回頭查詢。

Query 類型比對對象作用時機
Suppression querysignal 的屬性signal 已經因規則條件符合而準備產生之後
Data exclusion query原始資料（log/event）的屬性規則還沒評估這筆資料之前

兩者用同一套查詢語法，差別純粹在比對對象；也都只對這一條規則生效，跟能不能跨多條規則無關。

八種偵測方法

點開每張卡看範例：

Threshold
次數超過門檻
範例：5 分鐘內超過 10 次登入失敗。所有人共用同一條固定門檻線。
New Value
從沒出現過的值
範例：某使用者第一次從「從沒登入過的國家」登入。
Anomaly
動態門檻，比自己的歷史
範例：平常每小時 50 次 API 突然變 500 次。每個實體有自己的基準線，跟 Threshold 的固定門檻不同。
Content Anomaly
內容異常，不是次數
範例：某 API 呼叫平常參數模式固定，某次內容結構突然很不一樣，即使次數沒變多。
Impossible Travel
地理位置不合理
同一帳號的存取事件發生在兩地，距離在經過時間內人類不可能移動過去。
Third Party
轉送外部工具告警
例如 Amazon GuardDuty 已產生的告警，轉送進 Datadog 當作 signal 呈現。
Signal Correlation
多個 signal 合併成一個
範例：單獨看「新裝置登入」和「大量下載檔案」都只是低嚴重度提醒，關聯在一起信心度就高很多。
Sequence
有順序的一連串事件
範例：假設角色 → 權限提升 → 存取資料，依序發生且在合理時間內才判定為完整攻擊序列。
Chapter 04 · MITRE & Advanced Tuning

MITRE ATT&CK 與進階調校

規則基礎搞懂之後，這裡看規則怎麼跟業界共同的攻擊手法語言（MITRE ATT&CK）對應，再看三個容易混淆的「擋東西」機制，最後是規則調校與版本比較。

MITRE ATT&CK 從哪來、解決什麼問題

MITRE ATT&CK 全名 Adversarial Tactics, Techniques, and Common Knowledge（對手戰術、技術與常識）。

來源背景 MITRE Corporation 是美國一家非營利研究機構，長期替美國政府經營國防、資安相關的研發中心。2013 年，MITRE 內部一個叫 FMX 的研究計畫開始系統性整理「真實攻擊者到底都做了哪些事」，方法是分析大量真實入侵事件和 APT（進階持續性威脅組織）的活動紀錄，把觀察到的手法歸納分類，2015 年公開發布成 ATT&CK 框架。它要解決的問題是：資安圈長期沒有一套共同語言，同一種攻擊手法，不同廠商、不同分析師可能用完全不同的說法描述，導致經驗沒辦法累積、規則沒辦法互通。ATT&CK 之後，「T1110 是暴力破解」變成業界共識，不管你是哪家公司的分析師，看到這個代號就知道在講什麼。

框架拆兩層：

  • Tactic（戰術）：攻擊者的高層次目標，也就是「為什麼」要做這件事。企業版矩陣（Enterprise Matrix）大致依攻擊生命週期排序，包含 Initial Access（初始入侵）、Execution（執行）、Persistence（持久化）、Privilege Escalation（權限提升）、Defense Evasion（防禦規避）、Credential Access（憑證存取）、Discovery（探索）、Lateral Movement（橫向移動）、Collection（蒐集）、Exfiltration（資料外洩）、Impact（造成影響）等十幾種。
  • Technique（技術）：達成該戰術目標的具體手法，也就是「怎麼做」，每個技術都有一個固定編號，格式是 T####，更細的子技術則是 T####.###。

可以想成 Tactic 是章節標題，Technique 是章節底下的具體招式，一個 Tactic 底下通常對應好幾個 Technique。

範例：一次完整攻擊，怎麼對應到多個 Tactic 單一 Technique 只是攻擊鏈裡的一步，真實攻擊通常橫跨好幾個 Tactic，串起來才是完整故事：

Cloud SIEM 怎麼用它：靠 tag 對應，不是靠額外模組

考試陷阱重點 Detection Rule 跟 MITRE ATT&CK 的對應，是靠在規則上加 tag 完成的，不是靠另外一個獨立模組： 
tactic:credential-access
technique:brute-force
security:attack
signal 產生時，規則身上帶的這些 tag 會直接顯示在 signal 上。題目問「MITRE mapping 是怎麼實現的」，正確答案就是「Detection Rule 的 tags」。
易忽略細節：三個 tag 要配對出現 光加 tactic: 和 technique: 還不夠，規則必須同時帶有 security:attack 這個 tag，MITRE ATT&CK Map 才會把這條規則納入視覺化。如果自訂規則只設了 tactic:/technique: 卻漏了 security:attack，規則本身照樣正常運作、正常產生 signal，就是不會出現在地圖上——這跟規則是不是 OOTB、用哪種偵測方法完全無關，純粹是漏了這個 tag。

MITRE ATT&CK Map：把你帳號裡所有偵測規則畫成一張以 tactic（橫軸）/technique（縱軸，或反過來）為座標的熱圖，顏色越深代表對應到該 technique 的規則數量越多、涵蓋越密集；顏色淺甚至空白，代表「如果攻擊者真的用了這個技術，你可能完全沒有規則會響」。示意如下（僅示意，非真實資料）：

這張圖回答的關鍵問題是「如果攻擊者用了技術 X，我有沒有規則能抓到它？」，用來找出涵蓋率的缺口，決定要優先自訂寫哪些規則來補洞——這個動作直接銜接到第 6 章會教的持續改善循環：定期回看這張圖，是「追新」的具體做法之一。

把這套業界共同語言放在偵測方法之後，是因為上一章的三種規則類型、五個共用元件、八種偵測方法，最終都會被貼上這裡的 tactic/technique tag 分類——回頭對照上一章，才知道每個偵測方法實際上是在防哪一種攻擊手法。

三個易混淆機制：Filter / Rule / Suppression

這三個常被出成情境判斷題，考你分辨「這是哪個機制在起作用」：

機制作用時機作用範圍效果
SIEM Index Filterlog 進 SIEM index之前帳號 / index 層級，影響所有規則不符合的 log 完全不會被任何規則評估
Detection Rule 的 Data Exclusion Querylog 已在 SIEM index，這條規則評估之前單一規則層級這批資料對「這條規則」等於不存在

時序圖：同一筆 log 依序會經過這三個關卡

CHECKPOINT 1
SIEM Index Filter
帳號層級關卡。比對 log 的 source/tag。
沒通過 → log 完全不進 SIEM index，之後兩關都輪不到它，任何規則都看不到。
CHECKPOINT 2
Data Exclusion Query
單一規則的關卡。比對進來的原始資料屬性。
沒通過 → 這條規則直接跳過這筆資料，連累計次數都不算，但 log 仍在 SIEM index，其他規則正常看得到。
CHECKPOINT 3
Suppression Query
單一規則的最後一關。比對即將產生的 signal 屬性。
命中 → signal 被靜音，不進 Signal Explorer；沒命中 → signal 正常產生。
範例：同一個「已知誤判」，用不同關卡處理，結果差很多 情境：服務帳號 backup-bot 每天跑排程備份，固定會先登入失敗一次再重試成功，是團隊已知的誤判來源，規則是「5 分鐘內登入失敗超過 10 次」的 Threshold 規則。

若在規則上設 Data Exclusion Query

設定 -usr.id:backup-bot。backup-bot 的登入失敗 log 對「這條規則」來說從一開始就不存在，完全不計入次數累計。就算它一天登入失敗 100 次，這條規則也永遠不會因為它被觸發。其他規則（例如 Impossible Travel）不受影響，一樣正常評估這筆 log。

若改成設 Suppression Query

設定比對 signal 屬性 usr.id:backup-bot。規則仍然正常累計次數，一旦達到 10 次的門檻，規則邏輯判定「這裡要產生 signal」，只是在最後一刻被 Suppression Query 攔下來，讓這個 signal 不出現在 Signal Explorer。底層 log 和「差一點觸發」的過程完全沒受影響，之後仍可回頭查詢。

兩種做法最後「使用者看不到告警」的結果一樣，但發生的階段完全不同：Data Exclusion 是讓規則從頭到尾當這筆資料不存在；Suppression 是讓規則走完整個判斷流程、真的判定要告警了，才在終點前臨門一腳擋下來。

規則調校、自訂規則與版本比較

認識完偵測方法之後，接下來是怎麼把規則養成適合自己環境的樣子：OOTB 規則是很好的起點，但通常需要依照自己環境調校，可以直接在 OOTB 規則上新增已知誤判的 suppression、調整 severity 等級、更新 playbook 加上組織專屬的調查指引。對於 OOTB 規則沒涵蓋到、但組織特有的威脅，可以用同一套元件和偵測方法建立完全自訂的規則——因為 OCSF 正規化，針對 OCSF 屬性寫的自訂規則能同時適用多個 log 來源，一條寫得好的自訂規則就能提供很廣的涵蓋範圍。

Rule Version History：比較規則新舊版本的設定差異 規則編輯器內建版本歷史功能，調校規則之後（例如把查詢範圍從單一 environment 擴大到多個 environment），可以用 Open Version Comparison 選項，直接把目前版本和先前版本的設定並排比較，用顏色標出差異（紅色代表被移除的設定、綠色代表新增的設定）。

這跟第 6 章會提到的 Datadog Audit Trail 不同：Audit Trail 記錄的是「誰在什麼時候改了規則」這種平台層級的操作事件，Rule Version History 才是規則編輯器裡直接比較兩個版本設定內容差異的工具。
Chapter 05 · Investigation

Signal 產生後怎麼調查

規則觸發之後，你拿到的不是一堆雜亂 log，而是已經整理好的 signal。這一章看四個工具怎麼從「發生了什麼」一路查到「這個實體有多危險」。

Signal 不是原始 log

Analogylog 是散落的證據碎片，signal 是已經把碎片拼起來、附上偵探筆記的案卷。

基本產生流程：log 進來 → 通過 SIEM Index Filter → 套用 Detection Rule → 條件符合 → 產生 signal。

Open→ Under Review→ Archived

把安全資料彙整成「個別實體」（IAM 使用者、S3 bucket、EC2 instance、GitHub repo 等）的統一風險檔案。風險分數根據該實體過去 14 天 內相關 signal 的嚴重程度和頻率計算，若同時啟用 Cloud Security，Misconfigurations 和 Identity Risks 也會納入計分。回答：「我的環境現在哪些實體風險最高？」

Bits AI Security Analyst▸

AI 自動化初步分流：分析觸發的 log 和脈絡、摘要關鍵證據、說明判斷「良性還是可疑」的推理、建議下一步。以 MITRE ATT&CK 為基礎，能跳轉多個 IOC、查歷史資料。不取代分析師判斷，而是加速初步評估，實際效益是更快的 MTTA。
範例：Amazon SNS enumeration signal，Bits AI 判斷 SUSPICIOUS，證據包含帳號盜用指標、匿名代理伺服器基礎設施、系統性 AWS 服務偵察。

威脅情資（Threat Intelligence）與 IOC

IOC（Indicators of Compromise，危害指標）：可觀察到的具體證物，例如 IP、網域、檔案雜湊值、URL，暗示某系統可能已被入侵或被鎖定攻擊。

先搞懂 Feed 是什麼 Feed（情資饋送）可以想成一份持續更新的「已知壞人名單」訂閱：資安研究單位或廠商每天都在觀察全世界的攻擊活動，把發現的惡意 IP、惡意網域整理成一份清單，透過訂閱的方式源源不絕送給你，你的系統就能拿這份清單去比對自己的資料。跟訂閱新聞一樣，feed 的價值在於「持續更新」，不是查一次就結束的靜態名單。
運作機制：threat_intel 屬性是什麼

當進來的 log 裡的 IP 或網域，跟 feed 裡的某一筆已知 IOC 對上時，Cloud SIEM 會在這筆 log 本身上，額外加註一個 threat_intel 屬性，把「這個 IP 是已知威脅、屬於哪一類」的判斷結果直接寫進資料裡：

{
  "network.client.ip": "185.220.101.42",
  "threat_intel": {
    "category": "residential_proxy"
  }
}

這個屬性不是只是顯示用的標籤而已——因為它跟其他欄位一樣是可查詢的資料，Detection Rule 可以直接拿它當查詢條件，例如寫一條規則比對 @threat_intel.category:(malware OR tor)，就能只針對「連線對象本身已知是惡意來源」的事件產生 signal，不用自己維護一份 IP 黑名單。常見分類：malware（惡意軟體）、cryptomining（加密貨幣挖礦）、tor（Tor 匿名網路）、residential proxy（住宅代理伺服器，常被用來偽裝成一般家用網路掩護惡意流量）、scanner（掃描工具）。

內建策展 feed

來自 IPinfo、GreyNoise 等合作夥伴，自動套用在所有 log 上，不需要任何設定。

自帶 feed（Bring your own）

來自商業供應商、產業情資分享組織ISAC（Information Sharing and Analysis Center，資訊分享與分析中心，同產業公司互相交換威脅情資的組織）、或內部管線，存成 reference table，可手動上傳 CSV（Comma-Separated Values，逗號分隔值）檔案，或從雲端儲存定期自動更新。

易忽略細節：一種指標類型一張表 每一種指標類型都需要各自獨立的一張 reference table，例如 IP 位址一張表、網域另一張表，不能把不同類型的指標混在同一張表裡上傳。目前支援的自訂 IOC 匯入方式就是「CSV 進 Reference Table」這一條路徑，沒有獨立的 Threat Intelligence API 可以直接送 JSON，也不是走 STIX（Structured Threat Information eXpression，結構化威脅資訊表達式）/TAXII（Trusted Automated Exchange of Intelligence Information，可信自動化情資交換）——這是業界另一套威脅情資交換標準協定，不是 Datadog 用來匯入自訂 IOC 的方式。
Chapter 06 · Metrics & Continuous Improvement

怎麼衡量與持續改善

偵測和調查只是一半，另一半是把整套運作量化成可以追蹤、可以跟主管報告、可以拿去做合規證據的東西——並形成一個持續變好的迴圈。

一個 signal 的生命線：MTTD / MTTA / MTTR

三個指標都是「Mean Time to ___（平均要花多久時間做到某件事）」的縮寫，各自衡量生命線上不同的一段：

  • MTTD 全名 Mean Time to Detect（平均偵測時間）
  • MTTA 全名 Mean Time to Acknowledge（平均確認時間）
  • MTTR 全名 Mean Time to Resolve（平均解決時間）

儀表板與週報：讓數字被看到

Cloud SIEM Overview 頁面呈現：重要 signal、高風險實體、Content Pack 健康狀態與上手進度、依地理/MITRE tactic 分類的 top signal、MTTD 和誤判率、最新 Security Research Feed。

OOTB 儀表板（例如 CloudTrail 儀表板）可複製自訂；也可依受眾建立主管用、偵測工程師用、營運用的儀表板。

週報摘要：彙整過去七天的告警量、回應時間、重要新問題。每個使用者要個別訂閱，需要 security_monitoring_signals_read 權限。

STEP 01 · Raw log 送達

攻擊者在 5 分鐘內對 IAM 使用者 admin 重複發送失敗登入，這是第 12 次。log 剛送到 Datadog 時是一串未結構化文字：

2026-07-23 03:14:02 aws console login failed by admin from 203.0.113.44

團隊已經啟用 AWS CloudTrail Content Pack，這個來源本來就對應好 OOTB pipeline 和登入失敗偵測規則，不用臨時現接。

STEP 02 · Grok Processor 解析

Grok 用預先定義的樣式，把非結構化文字拆成可查詢的欄位：

{
  "usr.id": "admin",
  "evt.category": "authentication",
  "evt.name": "aws console login",
  "evt.outcome": "failure",
  "network.client.ip": "203.0.113.44"
}

STEP 03 · OCSF Processor 正規化

把來源特有欄位 remap 成跨來源一致的標準欄位：

{
  "actor.user.name": "admin",
  "class_uid": "Authentication",
  "activity_id": "Logon",
  "status_id": "Failure",
  "src_endpoint.ip": "203.0.113.44"
}

不管以後這個來源換成 CloudTrail、Okta 還是別的系統，只要對應到這幾個標準欄位，同一條規則都抓得到。

STEP 04 · GeoIP Processor 豐富化

根據 203.0.113.44 查 IP 地理資料庫，補上地理位置：

{
  ...
  "country": "海外，admin 從未登入過的地區",
  "city": "未知"
}

STEP 05 · 威脅情資比對

Cloud SIEM 拿這個 IP 去比對已知 IOC feed（malware / tor / residential proxy…）。

✓ 這次沒有命中，不加註屬性，log 照常繼續往下走 ▼
⇢
✗ 另一種可能：命中已知 IOClog 會被加上 threat_intel.category（例如 tor、malware），之後規則可以直接拿這個屬性當查詢條件，但不影響這筆 log 繼續往下走。

STEP 06 · SIEM Index Filter

Filter 條件是 source:(cloudtrail OR okta OR github OR guardduty)，這筆 log 的 source 是 cloudtrail。

✓ 符合條件，放行進 SIEM index ▼
⇢
✗ 另一種可能：未通過這筆 log 完全不會進 SIEM index，後面所有步驟都不會發生——這次攻擊會被整個漏掉，任何規則都看不到它。

STEP 07 · 存進 SIEM Index

存進 Standard indexing（近期熱資料，隨時可查）。之後超過 30 天會依保留策略轉存到 Flex Logs，最長可保留 15 個月，這一步不影響即時分析，即時分析發生在剛剛的 ingestion 當下。

STEP 08 · Detection Rule 比對：命中 Threshold

規則「5 分鐘內登入失敗超過 10 次」用的是 Threshold 偵測方法。這是第 12 次失敗。

✓ 超過門檻，規則邏輯判定「這裡要產生 signal」 ▼
⇢
✗ 另一種可能：次數還沒到門檻規則持續累計失敗次數，不會有任何動作，直到累計到 10 次以上或時間窗口重置，這條規則就一直安靜地在背景計數。

STEP 09 · Data Exclusion Query 檢查

這條規則有沒有設定要排除 admin？

✓ 沒有（admin 不是已知的排程機器人帳號），繼續往下走 ▼
⇢
✗ 另一種可能：admin 被設成排除這筆資料對這條規則來說從一開始就不存在，不計入次數累計，後面步驟都不會發生——但其他規則不受影響，log 本身還在 SIEM index。

STEP 10 · 貼上 MITRE ATT&CK Tag

這條規則本身已經預先貼好對應標籤：

tactic:credential-access
technique:brute-force
security:attack

三個 tag 配對出現，等一下產生的 signal 會直接帶著這些標籤，也會被 MITRE ATT&CK Map 這張熱圖納入計算。

STEP 11 · Suppression Query 檢查

有沒有 suppression rule 要靜音這個 signal？

✓ 沒有，繼續產生 ▼
⇢
✗ 另一種可能：命中 suppression例如這個 IP 剛好是已知的內部滲透測試來源，signal 會被靜音、不出現在 Signal Explorer，但底層 log 完全沒被動到，之後仍可回頭查。

STEP 13 · 分析師分流

分析師在 Signals Explorer 看到這個 High severity 的 signal，因為 severity 高、又是 credential-access 的攻擊手法，決定優先處理，把狀態從 Open 標記成 Under Review，正式進入調查。這一段反應時間就是 MTTA 在衡量的東西。

STEP 14 · 深入調查

  • 用 Investigator 追蹤 admin 這個身分還做了什麼、跟哪些服務互動過，確認攻擊者沒有成功登入。
  • Risk Insights 顯示 admin 這個 IAM 使用者的風險分數因為這次事件大幅上升。
  • Bits AI 分析後給出結論：SUSPICIOUS，關鍵證據包含來源 IP 在過去 24 小時對其他帳號也有嘗試（呼應 Signal Correlation）。

Bits AI 只是加速這一步的初步評估，最終判斷仍然是分析師自己做。

STEP 15 · 判定與回應：確認為真實攻擊

綜合證據後，分析師判定這不是誤判，是一次真實的暴力破解攻擊。觸發 Workflow Automation（SOAR）：撤銷 admin 的憑證、隔離相關存取；同時 Notification rule 依 severity=High 已經把這個 signal 路由到 PagerDuty，通知值班人員。

STEP 16 · 結案與衡量

處理完畢，signal 標記為 Archived。整段時間被記錄成三個指標：MTTD（log 送入到 signal 產生）、MTTA（signal 產生到 Under Review）、MTTR（產生到 Archived），會出現在週報和 Cloud SIEM Overview 儀表板上，也是 SOC 2 / PCI DSS 這類合規稽核要求「事件有沒有被追蹤解決」的證據。

STEP 17 · 回饋進持續改善循環

這起事件會變成下一輪持續改善的輸入：分析師可能因此新增一條 Suppression rule 排除已知的滲透測試來源、或重新檢視 MITRE ATT&CK Map 確認 credential-access 這條技術的規則涵蓋是否足夠——回頭影響的正是 STEP 08～11 這幾個判斷關卡。
