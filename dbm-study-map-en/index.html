Chapter 01 · Telemetry & Health

Telemetry Concepts & Health Indicators

This chapter answers two foundational questions: which engines DBM supports, and what actually separates a standard integration from DBM. It then breaks the database's "vital signs" into nine health indicators, and unfolds three lenses into six telemetry types one by one. Once this chapter is done, all the data sources used in later troubleshooting steps will make sense.

Supported Database Engines

EngineNotes
PostgreSQLRequires the pg_stat_statements extension, plus the pg_monitor role granted to the Datadog user.
MySQLRequires Performance Schema to be enabled. Setup steps differ between self-hosted and cloud-hosted instances.
SQL ServerRequires a read-only login with specific permissions. A stored procedure handles execution plan collection.

MongoDBSupports both Atlas and self-hosted deployments. Telemetry types differ from relational engines.
Exam TipThe exam is "database engine agnostic": it will not test engine-specific SQL syntax or configuration details, only the investigation workflow itself, which is identical across all supported engines and differs only in setup. All hands-on examples in this map use PostgreSQL, matching the Storedog lab environment.

Standard Integration vs. DBM: What Extra Do You Get

A standard integration is a general integration like Postgres or SQL Server, collecting "host level / instance level" metrics, an "outside-in" view of the database. DBM does not replace it, it layers a full set of query-level telemetry on top of the standard integration.

You getaggregate numbers such as connection count, SQL compilation rate, buffer pool utilization, disk I/O, and replication status, telling you whether the database is "healthy or not." You don't getthe "why": query-level detail is a complete black box. Setup is simple, and the Agent user only needs basic SELECT privileges.
You additionally getQuery Metrics (aggregate stats for the top 200 normalized queries), Query Samples (actual execution snapshots at a point in time, retained 15 days), automatically collected Explain Plans, Wait Event analysis, blocking query insights, normalization and obfuscation, APM correlation, and DBM Recommendations. The costthe Agent YAML needs dbm: true added, extra privileges are required (Postgres needs pg_monitor), and the connection must go directly to the database host, not through a proxy, load balancer, or connection pool. For most workloads the extra overhead is usually under 1% of query execution time and 1% of CPU.

Nine Health Indicators: The Database's Vital Signs

Think of it like a doctor checking a patient's vital signs: heart rate, blood pressure, temperature. Expand each item to see how to interpret it:

① Connections▸

How many clients are connected to the database, and how far it is from the limit. A steady climb may be a connection leak, a sudden spike may be a traffic burst or an application misconfiguration, and long-idle connections waste resources.

② Query Volume and Throughput▸

How many queries are processed per second (reads vs. writes). A sudden drop may mean an upstream application is broken; a sudden spike may mean some runaway process is flooding the database.

③ Query Latency▸

Average, p50, p95, p99, max. p95/p99 matter especially because the average masks outliers, for example an average of 10ms with a p99 of 2 seconds means 1% of users have a terrible experience.

④ Active Sessions and Database Load (Wait Event Analysis)▸

Instead of only looking at "how many queries ran," look at what resource the query is waiting on at that moment, four broad categories: CPU (competing for compute, consider optimizing the query or scaling up the instance), I/O (waiting on disk reads/writes, possibly a missing index or a buffer pool that's too small), Lock/Latch (waiting for another session to release a lock, usually contention caused by a long transaction), Network (waiting on data transfer, possibly an oversized result set or high latency).

⑤ Blocking Queries▸

A single long transaction holding a lock can cascade into dozens of blocked queries. DBM can visualize the "root blocking query" and the queries stuck behind it; see the real lock incident in Chapter 4 and Chapter 7.

⑥ Resource Utilization (CPU/Memory/Disk/I/O)▸

The database's "physical limit": no matter how well a query is written, the host still goes down without CPU, memory, or disk space. CPU sustained >80% means it's close to its limit; for memory, check the cache hit ratio; running out of disk space is a catastrophic failure.

⑦ Replication Health▸

Replication lag (how far the replica trails the primary) and replication status (whether it's connected and staying in sync). Lag that's too high means you're reading stale data; a disconnect means you've lost your failover backup.

⑧ Database Engine-Specific Telemetry▸

Postgres looks at vacuum operations (a steadily growing dead tuple count means autovacuum can't keep up); SQL Server looks at connection count, system memory, and throughput; MongoDB looks at slow operations, execution plans, and replication status changes.

⑨ DBM Recommendations Themselves Are Also a Health Signal▸

Not just raw metrics: DBM actively analyzes and flags high-impact blocking queries, unused indexes, and low-disk-space warnings, each recommendation carries a severity tier. See the full type table in Chapter 4.

The key to holistic interpretation is "correlation"a single metric never tells the whole story: high CPU + one query eating most of the database's time → that query needs optimizing; rising latency + increased lock waits → it's a blocking problem, not a resource problem; connection spike + falling throughput → it's connection saturation, not poor query efficiency; high I/O + low cache hit ratio → you need more memory, or the query is scanning too much data.

Six Telemetry Types: Unfolding Three Lenses One by One

The official docs condense the data types into three broad categories, three different "lenses" on the same database; the six telemetry types below are what those three lenses look like once unfolded:

Metrics · Satellite View

Host-level integration metrics, answering "how is the database doing overall," and the basis for dashboards and threshold alerts. Limitation: only shows "what happened," not "who caused it."

Query Metrics · Street View

Aggregate performance stats for each normalized query, turning the database from a black box into something you can reason about at the query level.

Query Samples · Microscope View

Individual snapshots of what actually executed at a given moment. Limitation: just a biased sample, not a complete record.

A typical investigation order: Metrics ("the database is under pressure") → Query Metrics ("this query pattern is eating 40% of database time") → Query Samples ("this one execution took 12 seconds at 3:47 PM"). In the actual UI, add Explain Plans, Wait Events, Active Sessions, and Schemas, unfolding into six:

Telemetry TypeQuestion It Answers
Query MetricsWhich query is slowest / most resource-hungry?
Query SamplesWhat specifically was slow this time?
Explain PlansHow did the database actually execute this query?
Wait EventsWhat is the query waiting on?
Active SessionsWhat was happening in the database at that moment?
SchemasIs the table's structure reasonable?

Typical investigation order: Query Metrics → Query Samples → Explain Plans → Schemas → Wait Events / Active Sessions.

Query Metrics: Normalization and query_signature

DBM groups all executions sharing the same query signature regardless of parameter values, computing average latency, total execution time, rows returned, and call count.

What normalization isreplacing the actual parameter values passed into a query with placeholders, so queries with different parameters but identical logic are treated as the same "query signature": 
SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending'
SELECT * FROM orders WHERE user_id = 55103 AND status = 'shipped'
After normalization both are classified under the same query signature: SELECT * FROM orders WHERE user_id = ? AND status = ?. As long as the structure is the same (table name, columns, operators, and clause order all match), it's treated as the same signature; any structural difference (an extra column, a different `WHERE` order, an extra `JOIN`) makes it a different signature, aggregated separately.
Exam TipFilter using query_signature, not the query field. Reason: tag names get truncated to 200 characters, query text can be long and the `query` tag isn't necessarily unique; `query_signature` is a fixed-length hash and the reliable way to identify a query.
Hands-on example: an e-commerce checkout page suddenly gets slowSorting Query Metrics by "total execution time" reveals that SELECT * FROM orders WHERE user_id = ? AND status = ? is consuming the most resources: average latency 850ms (only 120ms last week), 3,200 calls per minute, and an average of 4,500 rows returned (only 50 last week). The spike in rows returned suggests a missing `LIMIT` or a broken index.
RetentionThe official docs (Database Monitoring Data Collected, Data Retention Periods) explicitly list Query Metrics as retained for 15 months.

Query Samples: From "Slow on Average" to "Why Was This One Slow"

An individual query execution captured at a collection moment: the exact query text, duration, host, and associated execution plan, directly linked to the APM trace (see Chapter 3).

Hands-on exampleQuery Metrics tells you that query is slow "on average"; switching to Query Samples finds one execution that took 2.3 seconds on host postgres-replica-02, correlated with an APM trace from /api/v1/checkout on checkout-service. Drilling into the trace reveals a user with 12,000 historical orders, which made this particular execution slow.
Exam TipRetention is 15 days, an order of magnitude less than Query Metrics' 15 months, a commonly tested contrast point. DBM samples rather than capturing everything; a query not showing up in the samples very likely just wasn't captured during that window, not that it didn't execute.

Explain Plans: Unpacking Every Term from Scratch

An execution plan is a representation of the steps the query planner chose to execute a query. The whole thing can be thought of as a "kitchen ticket": the customer's order (SQL) just says "I want a steak," and the kitchen internally decides how to make it, that whole set of internal decisions and steps is the execution plan.

Who decides how it's done: the query planner, and nodes.The query planner is the chef in the kitchen figuring out "how," the customer only says what they want to eat, and the chef has to work out the steps, those steps are the execution plan; each line is a "node," and when the action is complex several nodes stack up, which is also why the Map View looks like a tree.

Seq Scan (sequential scan):imagine looking for something in a warehouse with nothing sorted, you can only open boxes one by one.

Seq Scan on orders  (cost=0.00..15420.00 rows=4500)
  Filter: (user_id = 98712 AND status = 'pending')

Imagine the warehouse door has a list posted, "Category A items are in row 3," one glance at the list tells you where to go, that's Index Scan. Actually building that list:

CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
Using `user_id` as the primary sort key, with rows sharing the same `user_id` then sorted by `status`; when building it, the database pulls out each row's `(user_id, status)` values, sorts them, and stores them separately in their own data structure (PostgreSQL defaults to B-tree).

Why the column order matters:`user_id` has far higher selectivity than `status` (`user_id` is nearly unique per value, while `status` usually only has a handful of values like `pending`, `shipped`, `cancelled`), putting the higher-selectivity column first lets the "jump to the target location" step narrow the range as much as possible.

Index Scan using idx_orders_user_status on orders  (cost=0.42..8.50 rows=3)
Cost dropped dramatically from 15,420 to 8.5.

Actual execution steps for the query SELECT * FROM orders WHERE user_id = 98712 AND status = 'pending': ① the planner sees the index covers both columns used in `WHERE`, and chooses Index Scan; ② binary search within the index (splitting in half each time) quickly locates the position where `user_id = 98712` starts, needing only log(N) comparisons instead of N; ③ it reads forward from that position, since rows with the same `user_id` sit contiguously in the index; ④ `status` is the secondary sort key, so `pending` rows are grouped together and don't need row-by-row checking; ⑤ each index entry carries a pointer to the actual row in the table, and once matching entries are found, the pointer is followed back to the table to read the real data. The entire process never looks at the 499,997 rows that don't match.

What happens to the data after it's fetched:Filter (corresponds to `WHERE`), Sort (corresponds to `ORDER BY`, usually has to wait until everything is piled on the table before it can start sorting), Join (`Nested Loop`, for each row in a small list go find the match in the other set / `Hash Join`, when neither side is small, build a hash table from one side first / `Merge Join`, when both sides are already sorted, zip them together like a zipper), Aggregate (`COUNT`/`SUM`/`GROUP BY`, usually the last step).

cost:not money or seconds spent, more like the chef's internal score for "how much of a hassle is this approach," written as "startup cost..total cost," it's an educated estimate, only comparable against other steps within the same plan, never across queries or machines. rows:the chef's guess at "roughly how many rows this step leaves behind"; when the guess is way off from reality, that's a signal "the chef may have picked the wrong approach this time."

If the whole process stacks up many actions, DBM draws the whole thing as a tree, using color intensity or box size to directly tell you which box is the most expensive, no need to mentally compare each one yourself.

Hands-on exampleLooking at the execution plan for a query sample shows a Seq Scan, the database scanning the entire `orders` table row by row (500,000 rows), and the Map View shows this node accounts for 98% of the total cost. Fix: create a `(user_id, status)` composite index, dropping cost from 15,420 to 8.5.
Notenot every query has an execution plan: some queries are too short to be sampled with a plan attached, some are structurally excluded (for example transactions with certain lock modes), and collection requires the explain_statement function to be correctly set up (see Chapter 2). If a query sample has no associated plan, check that function first.

Wait Events: The Bank Teller Hall

AnalogyThink of the database as a bank teller hall, each "connection" is a customer being served, and at every moment a customer is either "being served" or "waiting on something."

CPU wait:the query is genuinely being processed, this is normal busyness; a consistently high share usually means the query involves a large amount of data or computation. Lock wait:this connection wants to touch a piece of data already locked by another connection, for example Lock:transactionid means waiting for an entire other transaction to finish, and a spike means a transaction has been stuck open too long. I/O wait:waiting for data to be read from disk into memory or written to disk; a high share usually means a large data volume or disk speed can't keep up. Idle:the connection currently has no query running but is still holding a slot. Blocking:the flip side of lock wait, when A is waiting for B to release a lock, we say "B is blocking A"; the Active Connections tab tells you directly "who is blocking whom."

See the real-world case in Chapter 4 and Chapter 7: a spike in Lock:transactionid, tracing it via stop_locks, and the root cause being a test LOCK TABLE cronjob that was never cleaned up.

Active Sessions: A Snapshot Every 10 Seconds

A periodic snapshot of the database's active connection state, captured roughly every 10 seconds, capturing currently executing queries, duration, wait status, and which connections are blocking others. It's used together with Wait Events: Wait Events tell you "a spike happened," Active Sessions tell you "what exactly was running when the spike happened."

AnalogyIf Wait Events is a live broadcast of "what one customer is waiting on right now," Active Sessions is a security system taking a photo of the whole hall every few seconds. Because it's "periodic snapshots on file" rather than continuous recording, whatever happens between two photos isn't recorded, but you can still flip back through them frame by frame to find what happened at the moment of the anomaly. When multiple connections are stuck for the same reason at once, they can be chained into a "blocking chain" that names exactly which connection, running which query, caused it.

Schemas: Is the Table Structure Reasonable

Think of a table as a filing cabinet, where each row is a form with a consistent format. A column is a field every form has; the data type dictates what can go in that field (for example numeric(10,2)); the primary key never repeats across forms, and the database automatically creates an index for it by default; an index is a list that helps locate data quickly, and index size refers to how much storage that extra list itself takes up, it's not free.

Foundational terms the exam addsB-tree (the tree structure most database indexes default to, making "split in half" binary search possible), covering index (the index itself already contains every column the query needs, no need to go back to the table at all), index bloat (an index accumulates a large number of no-longer-valid entries as data changes, taking up more space and slowing queries down, requiring periodic rebuilding or cleanup). Structural information like table names, column names, and index names is not within the scope of obfuscation and shows up in full on the Schemas page.

Data Privacy and Obfuscation

Query Samples capture the actual query text as executed, and databases often store user emails, payment info, and personal data. Before the Agent sends data to Datadog, it does two things: query normalization (literal values replaced with `?` placeholders, and also the mechanism that strips literal values before leaving the host) and parameter obfuscation (another layer of protection, enabled by default, covering cases normalization doesn't reach, such as comments within the query text).

Data TypeObfuscated by Default
Query parameter values (bound literals)Yes
Comments within query textYes
Table and column namesNo
Index namesNo
Execution plan structureNo
Host metadata and database tagsNo
A commonly tested blind spotif the table or column names themselves contain sensitive information (for example a table called credit_cards), those names will be visible as-is; if the database's logs are sent to Datadog, they may contain the full SQL query text including bound parameters, since obfuscation only applies to the DBM telemetry pipeline, logs take a different path; comments within SQL queries may be collected by the Agent without obfuscation, something to watch for particularly in the trace-correlation comment mechanism in Chapter 3, since that mechanism itself relies on carrying the trace ID inside a SQL comment.

Two Things to Know Before Investigating Hands-On

  1. DBM is sampling, not full capture.A query not showing up in Query Samples very likely just wasn't captured during that time window, not that it didn't execute.
  2. There is propagation delay.There's a short delay between a query executing and its metrics appearing in DBM views; wait a few minutes before checking updated data when verifying a fix.
Chapter 02 · Setup & Instrumentation

Infrastructure Integration & Setup

For the six telemetry types from the previous chapter to actually show up on screen, you first have to walk through this entire setup process. This chapter uses the Storedog environment, starting from the most basic Postgres integration, all the way to fully enabling DBM and verifying success, then fills in the breadth the exam covers that a single lab environment can't show.

The Lab Environment: Storedog

Storedog is the e-commerce app used for hands-on examples in this chapter, letting users search, browse, and purchase products. The architecture includes a web frontend, a backend server, and two PostgreSQL databases: one storing spree backend-related data, and the other storing ads, discount codes, and product data. Many of the queries seen in Chapter 1 and Chapter 4 come from these two databases handling Storedog's business logic.

Step One vs. Step Two: How Much You Can See with Infrastructure Integration Alone

Before enabling full DBM, let's first see how much visibility Postgres infrastructure integration and APM alone provide, as a baseline for comparing what DBM adds on top.

Create a read-only user and grant privileges:

CREATE user datadog WITH PASSWORD 'datadog';
GRANT pg_monitor TO datadog;
GRANT SELECT ON pg_stat_database TO datadog;
Creates a user called `datadog`; grants `pg_monitor` so it can read stats and activity info but not modify data; additionally grants read access to `pg_stat_database` (database-wide statistics).

Verify the privileges:

docker exec lab-postgres-1 psql -x -h postgres -U datadog postgres -c \
"select * from pg_stat_database LIMIT(1);" \
&& echo -e "\e[0;32mPostgres connection - OK\e[0m" \
|| echo -e "\e[0;31mCannot connect to Postgres\e[0m"
Successfully querying data confirms the user and privileges are set up correctly. This read-only user is what actually goes into the Agent config's credentials later.

Autodiscovery: how a Docker label lets the Agent connect to the database automatically.Because Storedog has two logical databases, the Agent config carries two sets of connection info:

    com.datadoghq.ad.instances: '[
        {
          "host":"%%host%%", "port":5432,

host: "%%host%%" uses a template variable that the Agent automatically substitutes with the container's actual network address at startup; `relations` lists specific tables via `relation_name`, or covers all matching tables at once via `relation_regex`; `query_samples` turns on query sample collection and allows execution plan collection to also be attempted for parameterized queries; `collection_interval: 1` is a high-frequency setting for lab purposes. These labels already cover DBM-related fields, meaning the environment is pre-paved, but the full functionality behind it isn't officially enabled yet at this step.

What can be seen at this stage:two ready-made dashboards, Postgres - Metrics and Postgres - Overview, are provided automatically (see Chapter 5), and APM (via the Tracer + Agent APM feature, see Chapter 3) records queries and their duration from the "application calling the database" angle, with the Postgres service findable under APM > Software Catalog. Up to this point, only aggregate-level resource metrics are visible, none of the six telemetry types from Chapter 1 yet.

Only a few small changes are needed on top of the original integration: first let the Agent know to connect in DBM mode (dbm: true), then get the database itself ready to be probed for detail (two parameters in postgresql.conf), then create the privileges and helper functions DBM needs inside the database (dbm_setup.sql), and finally restart and verify.

postgresql.conf settings:

shared_preload_libraries = 'pg_stat_statements'
track_activity_query_size = 4096
shared_preload_libraries specifies that `pg_stat_statements` be preloaded at startup; this extension continuously records in the background "how many times each normalized query ran and how long it took," the underlying basis for collecting Query Metrics; `track_activity_query_size` is raised to 4096 to ensure collected query samples don't get truncated. This lives in the database's own config file, a different thing from the Agent-side `dbm: true`, and both sides need DBM turned on for it to actually work.

dbm_setup.sql: grants, schema creation, helper function creation.Run once for each database you want DBM to monitor:

GRANT SELECT ON pg_stat_database TO datadog;
CREATE SCHEMA datadog;
GRANT USAGE ON SCHEMA datadog TO datadog;
GRANT USAGE ON SCHEMA public TO datadog;
GRANT pg_monitor TO datadog;
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

Execution result:

The `ERROR: schema "datadog" already exists` in the middle isn't fatal; in `psql -a` mode a non-fatal error like this just gets skipped while execution continues, because this setup script has been run more than once against the same database.

Restart and verify:docker restart lab-postgres-1, because `shared_preload_libraries` only loads at startup. Right after restarting, at `Total Runs: 1` the DBM-related fields still won't show, which is normal, they need a few runs to appear. Once fully enabled, three new lines should show up:

Database Monitoring Activity Samples: Last Run: 2, Total: 11
Database Monitoring Query Metrics: Last Run: 2, Total: 11
Database Monitoring Query Samples: Last Run: 2, Total: 191
Their appearance means the Agent is genuinely collecting this data, not just infrastructure-integration-level `Metric Samples`.

The Wider Picture: What the Exam Covers That a Single Postgres Lab Doesn't Show

Everything hands-on above is based on "self-hosted Postgres + Docker"; the exam covers wider ground. Below are the parts the lab has no chance to touch, but that need to be understood conceptually.

Self-hosted database
Agent installed directly on the database host
Same as this chapter's lab environment, giving full visibility into the health of the machine actually running the database process, with the Agent granted read-only access.
Cloud-managed (RDS, Azure SQL, Cloud SQL)
Can't install software directly on the managed instance
The Agent has to be installed on a separate host with network access (for example EC2) and configured to connect to each managed instance. System metrics like CPU/memory/disk are collected directly through that cloud provider's Datadog integration.
Kubernetes
Cluster Agent paired with DBM
Cluster checks can run against pods, with the Cluster Agent automatically distributing database instances across a set of Agents to ensure each instance is only checked once.
Basic YAML structure (similar across engines, the same thing as this chapter's `dbm: true`)
init_config:
instances:
  - dbm: true
    host: localhost
    port: 5432
    username: datadog
    password: 'ENC[datadog_user_database_password]'
The config file path is `conf.d/<CHECK_NAME>.d/conf.yaml`. The official recommendation is no more than 30 database instances per Agent.

Database user privileges: cross-engine comparison(common pattern: create a dedicated `datadog` user with only the minimum privileges monitoring needs):

EngineRequired Privileges/Setup
Postgresthe pg_monitor role, `pg_stat_statements` installed, a `datadog` schema with the right grants (matching the `dbm_setup.sql` actually done in this chapter)
MySQL`performance_schema` enabled, various `SELECT` and `REPLICATION CLIENT` grants, the `datadog.explain_statement` stored procedure
SQL ServerVIEW SERVER STATE and VIEW DATABASE STATE privileges, `CONNECT` access to each database, specific driver configuration
Exam Tipengine-specific SQL syntax isn't tested, but understand the concept: the Agent user needs "read access to performance views," and insufficient privileges mean DBM gets no data.
Verifying the setup took effect (full five steps)▸

Step 1:run sudo datadog-agent status; a healthy integration shows under Running Checks with lines for `Database Monitoring Query Metrics`, `Query Samples`. Step 2:use a command-line tool like `psql` (Postgres) or `sqlcmd` (SQL Server) to confirm the credentials, host, and port also connect outside the Agent. Step 3:verify privileges, for example confirming the `datadog` user can query at least one row from `pg_stat_statements`. Step 4:check whether data is coming into the Database Monitoring page in the Datadog UI. Step 5:verify network connectivity to the Datadog endpoints: telnet dbm-metrics-intake.<site> 443, telnet dbquery-intake.<site> 443, common failure causes are proxy settings or a firewall blocking outbound traffic.

DBM-specific data collection relies on four parallel asynchronous jobs inside the Agent: Statement Metrics (queries `pg_stat_statements` etc., collecting aggregate metrics per query), Statement Samples (samples active query snapshots and runs `EXPLAIN`), Activity Monitoring (collects active connections, wait events, blocking queries), Metadata Collection (collects schema info, database configuration, host configuration); each job is scheduled and reports independently, and one failing doesn't necessarily affect the others.

Tunable settings:

SettingDefault / Description
Query Metrics collection interval10 seconds, can be stretched to 30 seconds when the database is busy to reduce overhead
Query Samples collection interval1 second (this is the lab's `collection_interval: 1`), also the basis for how execution plans get collected
Query Activity collection interval1 second, cannot be smaller than the Query Samples collection interval
Reported Hostnameoverrides the hostname shown in the UI, important when the Agent connects through a proxy or runs in a container with a generic hostname
Ignore Databasesexcludes databases you don't want monitored, for example `template0`, `rdsadmin`, `cloudsqladmin`
Schema Collectioncollected every 10 minutes by default, powering the Schema Explorer
Custom Queriesreports custom SQL results as metrics, for monitoring business metrics (queue depth, order count)

Where tags come from:`tags` explicitly set in the Agent config, infrastructure tags automatically collected from the host, global host tags from `datadog.yaml` (requires `propagate_agent_tags: true`), tags derived from the database itself (`db`, `user`, `client`, `query_signature`, `query`), and tags added from the trace context once DBM-APM correlation is enabled (see Chapter 3).

Chapter 03 · APM Correlation

APM and DBM Correlation

The previous two chapters covered the six telemetry types themselves and how to set up DBM to collect them; this chapter covers something else: how the database-side telemetry DBM collects gets linked to the application-side telemetry APM collects.

The Problem Being Solved

Without correlation, DBM and APM are two separate worlds. APM tells you "this API endpoint is slow, that database span took 2 seconds," but not "why" it's slow; DBM tells you "this normalized query has high latency," but not which service caused it. Once connected, developers can understand database performance without directly accessing the database, and DBAs can understand how a specific service's request traffic affects database load.

Three Layers of the Mechanism: Tracer, Agent, Trace ID Injection

This correlation isn't some special setting on the database itself, it's jointly enabled by application-side configuration plus the Agent's APM functionality, matching exactly with Chapter 2's Storedog lab environment.

Services like backend and worker load an init file such as datadog-tracer-backend.rb, a dd-trace library config file responsible for automatically attaching tracing when the Ruby/Rails application starts. Once installed, the Tracer automatically intercepts the application's calls to the database (for example SQL issued through ActiveRecord), with no manual code changes needed from engineers.

This is the fundamental reason Postgres can appear as a "service" in APM: it's the application side reporting "it called the database," the database itself has no idea it's being traced. Once set up, the Postgres service can be found under APM > Software Catalog.

The Agent container has DD_APM_ENABLED=true and DD_APM_NON_LOCAL_TRAFFIC=true set, and opens port 8126, the dedicated channel the Agent uses to receive trace data sent from each service. Spans produced by the Tracer on the application side are sent to the Agent through this port, and the Agent forwards them on to Datadog. Every application service also has DD_AGENT_HOST=datadog set, telling the Tracer which Agent to send data to.

With just a Tracer and APM, you only get span-level information about "the application called the database and it took this long"; being able to jump from an APM trace directly to the Query Samples and Explain Plans detail collected by DBM relies on injecting the trace ID into DBM's data collection.

The APM tracer prepends the trace context (trace ID, span ID, service name, environment) as a SQL comment in front of the actual query text before sending it out:

/*dddbs='orders-db',ddps='checkout-service',ddtid='abc123'*/ SELECT * FROM orders WHERE id = ?
The database only executes the `SELECT` part (the comment is ignored, with no performance impact); when the Agent collects query samples it reads this comment, extracts the trace metadata, and builds the correlation. This is also why the environment variable DD_DBM_PROPAGATION_MODE=full is set individually across multiple services in Chapter 2 such as `postgres`, `backend`, and `worker`, because both sides need it set for things to line up.

Three Propagation Modes

full
Full trace information
Sends complete trace information (trace ID, span ID, service name, environment), enabling two-way navigation: jump from a trace span to a DBM query sample, and also jump from a DBM sample back to the full trace. Recommended for most integrations, and what's actually used in the Chapter 2 lab environment.
service
Only sends service name
No trace/span ID included; you can tell which service caused the database load, but can't jump to a specific trace.
disabled
Nothing sent at all
DBM and APM stay fully independent with no correlation, back to the "two unrelated worlds" state described at the start of this chapter.

Four Conditions Needed to Enable Correlation

  • DBM is configured and collecting data (dbm: true, see Chapter 2).
  • APM is configured with tracing (a Datadog tracing library installed, or OpenTelemetry with the right attributes).
  • Propagation Mode is set in the Tracer (configured per language, or via the environment variable DD_DBM_PROPAGATION_MODE=full).
  • Unified Service Tagging (DD_SERVICE, DD_ENV, DD_VERSION must all be set, ensuring service/env/version tags match on both the APM and DBM sides).

Relationship to Query Normalization/Obfuscation (An Important Distinction)

Chapter 1 mentioned that query text goes through normalization and obfuscation before being sent to Datadog, a mechanism protecting the bound parameter values in a query from leaking. The trace ID injection here follows a completely different path: it touches the comment at the very front of the query text, not the query's own parameters, and comments are not obfuscated.

A commonly tested blind spotif an application adds its own extra comment containing sensitive information to the SQL (for example a user ID or session token), that will also be collected by the Agent and sent to Datadog, unobfuscated. Obfuscation only covers parameter values, not the SQL comment itself.

Summary: The Typical Investigation Flow

Postgres itself has absolutely no special configuration to work with APM; it's the application installing a Tracer and sending spans to an Agent with APM enabled, and DD_DBM_PROPAGATION_MODE then uses the trace ID inside the SQL comment to connect those spans to the query data collected on the database side.

The N+1 Query Problem

Instead of using a single `JOIN` to get all related data at once, the application runs one query per item. Example: an e-commerce page displays a list of 100 orders, and each needs to display the customer's name.

Efficient (1 query)

SELECT orders.id, orders.total, customers.name
FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE orders.created_at > '2024-01-01'

N+1 (101 queries)

One query runs first to grab all orders, then the application loops over the results, running a separate query for each order to look up the customer's name, 100 orders means 101 round trips to the database.

Why it matters:each individual query might be fast (2ms), but 101 of them add up to over 200ms, and it gets much worse once the data volume scales to 10,000 rows. The trickiest part is that N+1 often goes unnoticed during development, since the test database has few rows, only showing up once production data volume grows.

How DBM helps you catch itopening a slow trace in APM shows a flame graph stacked with hundreds of tiny, nearly identical database spans; in DBM Query Metrics, this normalized query's Requests count is abnormally high, with individual executions possibly fast (low Average latency) but Total time high. Both showing up together is a clear signal.How to fix it: the fix lives in the application code, not the database itself, common approaches are using a `JOIN` to fetch everything at once, eager loading, or batching into a single query with `WHERE id IN (...)`.

Investigating Latency / Investigating Load / Investigating Blocking

Investigating latency: four steps▸

① Confirm whether the database is the root cause (look at the slow trace's flame graph; if the database span accounts for most of the request time, it's the bottleneck); ② sort Query Metrics by Average latency to find the slowest query pattern, but also check Total time; ③ drill into query details for Explain Plans (a full table scan? expensive joins/sorts?), wait events, Hosts Running This Query, and the Metrics tab (a slow climb or a sudden jump); ④ compare execution plans across different points in time, if performance got worse after a new plan appeared, that's plan degradation.

Investigating load: where to look▸

The active connections timeline at the top of the host details page can be broken down by wait group; if most connections are waiting on CPU that means compute-intensive, mostly waiting on I/O means disk-intensive, mostly waiting on locks means contention; sort Query Metrics by Percent time to see which query pattern takes up the largest share of total database time.

Identifying Performance Degradation

Performance degradation is when a once-fine-performing query starts getting worse, and it can happen quietly, building up over time before causing an obvious disruption. The database itself only reports "current" statistical state; DBM stores key metrics as time series for normalized queries (the Metrics tab), which is what lets you compare against historical data.

How DBM detects it:automatically detected and flagged as "Query Load Increase" in Recommendations, automatically correlating changes in query workload, spikes in user or service activity, schema modifications, and recent deploys.

Common causes:plan degradation, schema changes (a dropped index gets flagged as Missing Index), data growth, application changes, infrastructure changes.

Hands-On Case Study: Fully Optimizing the Trending Products Query

Start by checking the actual query logic in the code (dbm.py), and find that the threshold used to filter products is set far too wide, pulling in a broad group rather than genuinely best-selling items.

Narrowing the query scope:changing the random range that generates the filter threshold from `random.randint(1, 7000)` to `random.randint(5000, 7000)`:

SELECT id, description, order_count, last_hour, image_url, NULL AS is_preorder
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}
UNION
SELECT id, description, order_count, last_hour, image_url, is_preorder
FROM preorder_items
WHERE order_count::int > {random.randint(5000, 7000)}

After restarting the service and waiting a few minutes, going back to Query Metrics sorted by Average Rows confirms it: the query sample cost has dropped, the right direction. Checking the Traces tab, this time's duration is noticeably lower than before (it used to exceed 225ms). But the overall cost is still on the high side; going back to the Explain Plan Map View, the Sort operation still accounts for 75% of this query's total cost, the next bottleneck to tackle.

Removing the UNION:the query logic uses `UNION` to merge results from the `items` and `preorder_items` tables. `UNION` doesn't just concatenate the two result sets, it also automatically removes duplicate rows, and to remove duplicates, the database has to sort all the results first, exactly the source of that high-cost sort node in the Map View.

Digging further: once a product in `preorder_items` officially goes live, it gets flagged `false`, meaning there's no real need to query both tables and then `UNION` to deduplicate. A better approach is having the dev team adjust the data write logic so that products already live are maintained directly in the `items` table, so the query side can simplify down to querying just one table:

SELECT *
FROM items
WHERE order_count::int > {random.randint(5000, 7000)}

After restarting the service, going back to Query Metrics sorted by Rows per Query confirms it: cost dropped substantially again compared to the previous optimization, because the whole query now consists of a single scan operation, no longer needing the sort overhead caused by `UNION` deduplication.

The core idea this case demonstratesDBM isn't only for "finding problems." After the code is changed, the same set of Query Metrics, Explain Plans, Query Samples, and APM Trace tools can also be used to "verify whether the fix actually worked," replacing the guess that it "feels like it should be faster" with real numbers (cost, duration, rows). The entire investigation (clearing the locking problem → finding the high-load query → pinning the sort bottleneck with the Explain Plan → confirming with historical trends → confirming real impact with an APM Trace → two rounds of optimization and verification) is a complete demonstration of running every diagnostic step earlier in this chapter for real; see the interactive version on the separate "Architecture Overview" tab.

Alert Grouping: Simple vs. Multi Alert

Simple Alert

Aggregates across all reporting sources, firing one alert when one or more groups cross the threshold; this strategy reduces notification noise.

Multi Alert

Exam Tipfor database monitoring, a Multi Alert grouped by host is usually the most sensible choice; what you want to know is "which" host has a problem, not just that "some" host does.

Chapter 06 · Database Fundamentals

Database Fundamentals Appendix

General database knowledge outside the exam scope but necessary for understanding what's shown in DBM, not DBM-specific content, only covering what hasn't already been discussed in other chapters.

What Is a Database

A database is an organized system for storing, retrieving, and managing data, replacing the practice of scattering information across files, spreadsheets, and documents.

Analogythink of it as a warehouse: you could dump all your inventory into one big room and have to search the whole room every time you need something, or you could sort it onto labeled shelves, rows, and boxes with a catalog system telling you exactly where things are. A database is that organized warehouse.

Why files alone don't cut it:files quickly break down when facing needs like "many people reading and writing at once without corruption," "efficiently searching across millions of records," "data not getting written halfway during a power outage," and "relationships between different kinds of data." Databases solve these problems.

Tables, Rows, Columns, Primary Keys, Foreign Keys

The most common way to organize a database is a table, similar to a spreadsheet: a table represents one type of thing, each row is a specific instance, and each column is an attribute. Every table usually has a primary key, a column that uniquely identifies each row; tables are commonly related through a foreign key, where a column in one table points to another table's primary key.

See the Schemas section in Chapter 1 for a fuller hands-on example of tables/rows/columns/indexes.

SQL and CRUD

SQL (Structured Query Language) is how you communicate with a relational database, a declarative language: you tell the database "what you want," not "how to get it," and the engine figures out the best way to execute it itself. The main operations map to CRUD: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE).

Exam Tipthe DBM certification exam doesn't require you to "write" SQL, only to "interpret" it, but understanding what these statements do helps you make sense of normalized queries and execution plans in Datadog.

Database Management System (DBMS)

A DBMS is the software that runs and manages a database; when people say "Postgres" or "MySQL," they mean this software itself, not the data, and it's responsible for storage, query execution, concurrency control, security, backups, and more.

Exam TipDatadog DBM currently supports PostgreSQL, MySQL, SQL Server, Oracle, MongoDB, Amazon DocumentDB, ClickHouse. The exam is engine-agnostic and won't test engine-specific knowledge, but you should know which engines DBM supports.

Client-Server Architecture and Connection Pooling

Databases follow a client-server model: the database server runs the DBMS and holds the data, clients connect to the server over the network, and every connection consumes server resources. Connection pooling (via PgBouncer, ProxySQL, or at the application layer) reuses connections across multiple requests to reduce overhead.

Exam Tipthe Datadog Agent must connect directly to the database host, not through a connection pool or load balancer, because going through a proxy can cause the Agent to see different hosts over time, producing inaccurate metrics.

Self-Hosted vs. Managed Databases

Self-hosted databases run on infrastructure you control yourself, installation, patching, backups, and scaling are all your responsibility. Managed databases (AWS RDS, Azure SQL, Google Cloud SQL) are operated by the cloud provider, and you only need to configure and use them. DBM supports both, but managed instances often require specific parameter groups or IAM roles, while self-hosted requires the Agent to access via localhost or a socket directly (see Chapter 2 for setup differences).

Query Lifecycle, Replication, Buffer Pool

Query lifecycle:parse (syntax check) → plan/optimize (the engine decides "how" to execute) → execute (the actual data access or modification); DBM presents data separately for the planning stage (execution plans) and the execution stage (latency, rows affected, wait events).

Replication:copying data from a primary node (writer) to one or more replica nodes (readers), providing high availability and read scaling. What to monitor: replication lag, replication status.

Buffer Pool / Shared Buffers:the database keeps frequently used data in memory (called buffer pool in MySQL/SQL Server, shared buffers in Postgres) to avoid reading from disk every time; a cache hit ratio usually >95% indicates good performance.

Throughput, Latency, and Resource Utilization

Throughput is how many queries the database processes per unit of time, latency is how long each individual query takes to complete; the two are often inversely related as load rises. Resource contention centers on CPU, memory, disk I/O, and network, and it's important to monitor these alongside query metrics: a CPU spike may correspond to a particularly expensive query, and high disk I/O may indicate a missing index causing a full table scan.

Rows returned vs. rows examineda well-optimized query only examines the rows it needs to return. If a query returns 10 rows but examines 10 million, that's a strong signal it's doing unnecessary work, usually a missing index or a poorly written filter condition; this ratio is one of the most practical indicators of query efficiency.

Advanced Indexing Concepts

An index lets the database quickly find rows without scanning the whole table, similar to the index page at the back of a book (basic concepts and hands-on examples in Chapter 1). Three advanced terms not covered elsewhere:

  • B-tree index: the most common index type, suited to equality and range queries.
  • Covering index: contains every column a query needs, so the engine never has to go back to the table.
  • Index bloat: over time, updates and deletes can cause an index to grow larger than necessary, dragging down performance.

Echoes "Wait Events" in Chapter 1: a spike in lock waits is a quick signal that one or more queries are blocking others.

STEP 02 · Flipping Through Active Connection Snapshots to Find # WAITERS

Switching to the Active Connections tab and clicking a higher spike on the query duration chart shows the active connections at that moment (a pg_stat_activity snapshot taken every 10 seconds). After flipping through a few snapshots, the one with a number in the # WAITERS column and a red bar on the wait group chart is found, and expanding it reveals the full SQL.

STEP 03 · The Truth Revealed: A Forgotten Test LOCK TABLE

The full SQL reveals: someone on the dev team wrote a query to update order quantities with bad syntax, using LOCK TABLE, and even set it up as a scheduled cronjob running periodically, causing a large number of other queries to get stuck.

STEP 04 · Decision Point: Can This Lock Just Be Stopped?

Before stopping a locked query, you first need to determine whether it's something that can be safely terminated.

✓ Confirmed it's a leftover cronjob from testing some feature earlier, unrelated to Storedog's normal business logic, and safe to stop ▼
⇢
✗ Another possibility: a legitimate schema migrationif this LOCK TABLE were actually a legitimate DDL operation in progress, like an ALTER TABLE or CREATE INDEX that needs an exclusive lock, it should not be terminated directly with stop_locks, it should be allowed to finish, and similar operations should be scheduled for low-traffic periods instead, exactly the judgment principle mentioned in "Investigating blocking" in Chapter 4, and what this step is really about.

STEP 05 · Quantifying Impact with Blocking Queries' Time Impact

Switching to the Blocking Queries tab shows two sets of charts: "queries causing blocking" (Root Blocking Queries) and "queries waiting on this block" (Waiting Queries).

✓ The Time Impact column confirms this `LOCK TABLE` query has already made other queries wait more than 15 seconds, a genuinely significant impact worth prioritizing ▼
⇢
✗ Another possibility: Time Impact is very lowif Time Impact is only a fraction of a second and not persistent, this blocking is just occasional normal lock contention, not requiring special intervention; continued observation is enough, no need to reach for stop_locks right away.

STEP 06 · Running stop_locks, Locking Incident Cleared

stop_locks

Only once the locking problem is cleared does the next symptom come into view: the trending products query overloading the database. This step demonstrates what "Nine Health Indicators" in Chapter 1 emphasizes, that a single metric never tells the whole story: clearing a locking incident doesn't mean the database is now fully healthy, there's another layer of problem waiting to be found.

STEP 07 · Turning to Query Metrics, Finding the Next High-Load Query

Storedog recently added a "trending products" widget that runs a query against the items table every few seconds to grab the top ten most-ordered products; this query is putting heavy load on the database and taking a long time to run. Switching to the Query Metrics tab and sorting the whole table by the Average Rows column header, the SELECT id, description... query sits at the very top.

STEP 08 · Explain Plan Map View Pinpoints the Sort Bottleneck

Drilling into the normalized query panel's Explain Plans tab, the Plan Operations table lists every operation this query uses, and the cost is quite high. The Map View further down draws the whole execution plan as a visualized tree, directly showing the Sort operation accounting for the largest share of the cost, the main reason this query's execution time is too long.

STEP 09 · Confirming Real Impact with an APM Trace

Clicking View Query Samples in the top right of the normalized query panel shows these samples with costs around 7000, on the high side. Drilling into one and opening the Explain Plan Sample panel, switching to the Trace tab: a GET request on the /get-item route triggered this query, with the whole request taking about 1.06 seconds, of which this query accounted for 256ms, roughly a quarter of the entire request's time.

This step ties "the query itself performs poorly" together with "how much real impact it has on the service calling it," the key evidence for deciding whether to prioritize this query, echoing the APM-DBM correlation mechanism from Chapter 3.

STEP 10 · First Optimization: Narrowing the Query Scope

Checking the actual query logic in the code (dbm.py) finds the threshold used to filter products is set far too wide. Changing the random range that generates the filter threshold from random.randint(1, 7000) to random.randint(5000, 7000) narrows it down to only the genuinely best-selling group; after restarting the service and waiting a few minutes, going back to Query Metrics confirms it: cost dropped, the right direction, but the Map View shows Sort still accounts for 75% of the cost.

STEP 11 · Decision Point: What's the Real Source of the Sort Bottleneck?

Looking back at the query logic, it uses UNION to merge results from the items and preorder_items tables.

✓ Confirmed `UNION` doesn't just concatenate the two result sets, it also automatically removes duplicate rows, and to remove duplicates the database must sort all the results first to compare them, exactly the source of that high-cost sort node ▼
⇢
✗ Another possibility: mistaking it for an indexing problemwithout first checking the Map View to see specifically which node is consuming the cost, it's easy to mistakenly assume the Sort bottleneck is "a missing index," and go add a completely unrelated index; in reality an index can't solve the sort cost caused by `UNION` deduplication, wasting effort and possibly even slowing down writes.

STEP 12 · Second Optimization: Removing the UNION

Once a product in preorder_items officially goes live, it gets flagged false, meaning there's actually no need to query both tables and then UNION to deduplicate. A better approach is having the dev team adjust the data write logic so that products already live are maintained directly in the items table, so the query side can simplify down to querying just one table. After making the change and restarting the service, going back to Query Metrics sorted by Rows per Query confirms it: cost dropped substantially again compared to the previous optimization, because the whole query now consists of a single scan operation.

STEP 13 · Feeding Back into Recommendations and Alert Design

The evidence from this whole investigation feeds back into two things: if this query's degradation had happened gradually rather than as a one-time code issue, DBM Recommendations' Query Load Increase would have flagged it automatically anyway; and this locking incident also reminds the team that DBM monitors can be set up against Waiting Queries or Long Running Queries (see Chapter 5), so the next similar leftover cronjob doesn't have to wait for a routine health check to be discovered, but instead triggers a proactive alert.

The entire investigation (clearing the locking problem → finding the high-load query → pinning the sort bottleneck with the Explain Plan → confirming real impact with an APM Trace → two rounds of optimization and verification → feeding back into monitor design) is a complete demonstration of running the whole diagnostic framework from Chapter 4 for real.
