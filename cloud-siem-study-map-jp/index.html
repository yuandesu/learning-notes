Chapter 01 · Foundation

なぜ SIEM が必要か

この章では 1 つの問いに答えます。クラウドプロバイダーは実際何を守ってくれていて、どこに自分で埋めるべき穴が残っているのか。この答えが「自分でどのデータを集めるべきか」を決め、それこそが Cloud SIEM の生産ライン全体の原材料になります。

まず正式名称から：Cloud SIEM とは何か

SIEM の正式名称は Security Information and Event Management（セキュリティ情報およびイベント管理）で、セキュリティ分野で長年使われてきたシステムのカテゴリです。中核となる仕事は、各システムに散らばった記録（log/event）を 1 か所に集約し、相関分析を行って潜在的な脅威を見つけ出すことです。Datadog の Cloud SIEM は、このカテゴリのシステムが Datadog プラットフォーム上に実装されたものです。すでに Datadog に送られている log をそのまま活用してリアルタイムに分析するので、別途独立したセキュリティシステムを接続する必要はありません。

Analogy 社内に散らばった監視カメラの映像（各システムの log）を、すべて 1 つの監視室（SIEM）に集約し、同じ人員が同じルールで見張るイメージです。各部署がそれぞれ自分の画面だけを見て、異常があるかどうかを個別に判断するのとは違います。

共有責任モデル（Shared Responsibility Model）

パブリッククラウドのセキュリティは、決して「プロバイダーが全部引き受ける」でも「顧客が全部引き受ける」でもなく、サービスの形態によって役割が分かれています。しかもサービスが「マネージド」であるほど、その境界線はプロバイダー側に寄っていきます。

Analogy 借りているマンションにはオートロックや監視カメラ、消防設備が備わっています（これはプロバイダーの責任）。しかし自分の部屋の鍵をかけるかどうか、貴重品をどこに置くか、合鍵を誰に渡すかは、常に自分自身の責任です。管理人が代わりに管理してくれるわけではありません。

IaaS · 例：AWS EC2

IaaS の正式名称は Infrastructure as a Service（インフラストラクチャーアズアサービス）で、仮想マシン層にあたります。顧客が OS、アプリケーション、ネットワーク設定を自分で管理し、プロバイダーは物理データセンター、ハードウェア、仮想化層のみを管理します。顧客が負う責任範囲が最も大きい形態です。

PaaS / フルマネージド · 例：RDS、Lambda

PaaS の正式名称は Platform as a Service（プラットフォームアズアサービス）で、プロバイダーが OS やパッチ、基盤の運用まですべて引き受けます。顧客は自分のデータとアクセス設定だけを管理すればよくなります。

どの形態でも変わらないこと

データ、アイデンティティ（identity）、アクセス権限（access policy）は常に顧客の責任です。従業員のアカウント権限が適切に設定されているかどうかを、プロバイダーが代わりに管理してくれることはありません。

監視における実際の意味 プロバイダーは大量のセキュリティテレメトリデータ（監査 log、トラフィック log、脅威検知結果）を生成しますが、自分から SIEM に送ってはくれません。どの情報源を収集し、どこに送り、どれだけ保持するかは自分で決める必要があります。これこそが「なぜ SIEM が必要か」への答えです。プロバイダーは原材料を提供するだけで、その原材料を集約し、正規化し、分析するツールが必要なのです。

主要な Log ソース 5 大分類

Cloud SIEM が効果を発揮するには、環境全体を見渡せる必要があります。各分類をクリックして例を見てみましょう。

クラウド監査 Log（Cloud audit logs）▸

例：AWS CloudTrail、GCP Audit Logs、Azure Activity Logs。「誰がクラウド環境に対してどんな API（Application Programming Interface，アプリケーション間の通信・命令のためのインターフェース）呼び出しや管理操作を行ったか」を記録する、クラウドセキュリティ監視の土台です。
例：誰かが IAM（Identity and Access Management，アイデンティティとアクセス管理）ユーザーの認証情報で DeleteBucket API を呼び出すと、CloudTrail は誰が、いつ、どの IP から実行したかを記録します。

アイデンティティおよび認証 Log（Identity and authentication logs）▸

例：Okta、Auth0、Azure AD。ログインイベント、MFA（Multi-Factor Authentication，多要素認証）チャレンジ、アカウント活動を追跡します。
専門用語：Impossible Travel（不可能な移動）。同じアカウントが短時間のうちに遠く離れた 2 つの地点からログインする（例：10 分以内に台北でログインした直後にニューヨークでログインする）と、物理的にそれほど速く移動することは不可能なため、アカウントが乗っ取られている可能性を示します。

ネットワークトラフィック Log（Network flow logs）▸

例：AWS VPC（Virtual Private Cloud，仮想プライベートクラウド） Flow Logs、Azure NSG（Network Security Group，ネットワークセキュリティグループ） Flow Logs、GCP VPC Flow Logs。接続のメタデータ（誰が誰に接続したか、どのポートか、通信量はどれくらいか）のみを記録し、パケットの中身は記録しません。
例：内部ホストが突然外部の見知らぬ IP に大量のデータを送信した場合、データ漏えい（data exfiltration）の兆候かもしれません。内部ホスト間に異常な横方向の接続パターンが現れた場合は横方向移動（lateral movement）の可能性があります。これは攻撃者が 1 台のマシンを乗っ取った後、それを踏み台にして他の内部マシンを攻撃する手法です。

SaaS およびコラボレーションツール Log▸

SaaS の正式名称は Software as a Service（ソフトウェアアズアサービス）で、自分でインストール・保守しなくても、ブラウザからログインするだけで使えるクラウドソフトウェアです。例：Microsoft 365、Google Workspace、Slack、GitHub。コラボレーションプラットフォームや開発ツール上のユーザー活動を追跡します。

エンドポイントおよびサードパーティセキュリティツール Log▸

例：CrowdStrike、SentinelOne、Amazon GuardDuty。専門のセキュリティツールがすでに生成したアラートや発見事項（findings）を転送してくることで、Cloud SIEM はこれらの既存の判断結果も相関分析に組み込むことができます。

Content Pack：「ゼロから作る」を「即つながる」に変える

Content Pack は特定の log ソース向けにパッケージ化された一式のセキュリティコンテンツです。Detection Rules、Dashboards、Investigator widgets、Workflow Automation / SOAR blueprints（SOAR = Security Orchestration, Automation and Response，セキュリティオーケストレーション・自動化・対応）が含まれ、時には parser も含まれます。

自分でやるべきことデータソースを探して接続 → Detection Rule を自分で書く → Dashboard を自分で作る → Workflow を自分で構築する。どの項目も正しいかどうか検証する時間が必要です。
例：AWS CloudTrail Content Pack有効化して CloudTrail log を接続するだけで、異常な AssumeRole 動作（ロールの想定が異常なパターンで、権限昇格攻撃でよく見られる）を検知する Detection Rule、CloudTrail アクティビティダッシュボード、IAM user / IP 向けの調査ビュー、自動通知や自動対応の workflow が一度に手に入ります。

もう 1 つ、脅威インテリジェンス寄りの例として Recorded Future Content Pack があり、事前構築済みの検知ルール、log enrichment（エンリッチメント）、統合ダッシュボードを提供します。

試験のポイント
  • 「この Content Pack はどの情報源に依存するか」がよく問われます。
  • Content Pack を有効化すると SIEM Index Filter が自動更新されます（その Content Pack に必要な log ソースが自動的に filter に追加されます、第 2 章参照）。手動で別途設定する必要はありません。
  • Content Pack の中核的な価値は time-to-value（導入してから実際に価値を生むまでの時間）を短縮することです。

補足：AWS Org アカウント連携（CloudFormation StackSet）

AWS Organization 配下の複数アカウントを一括で Cloud SIEM に接続するには、Datadog が提供する CloudFormation StackSet を使います。Organization の trusted access（信頼されたアクセス）と service-managed permissions（サービス管理型権限）を利用して、管理アカウントが必要な IAM role を各メンバーアカウントへ自動的にデプロイします。

よくあるデプロイ失敗の原因 デプロイ設定の Specify regions（リージョン指定）ステップでは、リージョンを 1 つだけ選択できます。IAM は AWS のグローバル（global）サービスでありリージョンに依存しませんが、StackSet のデプロイ機構は「アカウント × リージョン」ごとに stack instance を作成します。複数リージョンを選択すると、Datadog のテンプレートが複数のリージョンでそれぞれ同名の IAM role を作成しようとして衝突が発生し、どのアカウントにも IAM role を作り終える前にデプロイ全体が失敗します。

紛らわしいですが原因ではない設定：Execution configuration を Active（並列実行）にすることはデプロイの速度・並列度にのみ影響します。Deployment targets を特定の OU（Organizational Unit，組織単位）ではなく Organization 全体に設定することも、単にデプロイ範囲の大きさの設定にすぎません。どちらもデプロイ全体の失敗には直結せず、原因になるのは「複数リージョンの選択」だけです。

Datadog Security 製品ラインにおける Cloud SIEM の位置づけ

Cloud SIEM は Datadog Security 製品ラインの一部にすぎず、それぞれがセキュリティスタックの異なるレイヤーを担当しています。

Cloud Security（クラウドセキュリティポスチャー）▸

インフラの「セキュリティポスチャー（posture）」に注目します。重点は設定そのものが安全かどうかで、Cloud SIEM が注目する「攻撃を受けたかどうか」とは別のレイヤーの問題です。以下の 3 つに分かれます。

  • Misconfigurations（設定ミス）：リソース設定を継続的に監査し、CIS（Center for Internet Security）や PCI DSS（Payment Card Industry Data Security Standard，クレジットカード業界データセキュリティ基準）といったコンプライアンスフレームワークで定められたチェック項目と照合します。
    例ある S3 bucket が「誰でも公開読み取り可能」に設定されていた場合、これは設定ミスです。実際にデータを盗む人がいなくても、この設定そのものがすでにリスクであり、Misconfigurations はそれを直接指摘します。
  • Identity Risks（アイデンティティリスク）：IAM（Identity and Access Management）関連のリスクを検知します。
    例ある IAM ロールに「管理者（admin）」レベルの権限が付与されているものの、過去 90 日間まったく使われていない場合、これは「権限過剰（excessive permissions）」と「未使用の認証情報（unused credentials）」の組み合わせです。この認証情報が漏えいすれば、攻撃者が得られる権限は実際の必要量をはるかに超えてしまいます。
  • Vulnerabilities（脆弱性スキャン）：コンテナやホストをスキャンし、既知のセキュリティ脆弱性を見つけます。
    例ある EC2 ホストで動いているオープンソースパッケージのバージョンが、ある CVE（Common Vulnerabilities and Exposures，共通脆弱性識別子。業界共通の既知脆弱性の番号体系）に該当するとスキャンで判明した場合、Vulnerabilities はまだ実際に攻撃に使われていなくても、そのホストにこの脆弱性があることを一覧に表示します。
Workload Protection（ワークロード保護）▸

ホストやコンテナ上のファイル、ネットワーク、プロセスの活動を監視し、runtime（プログラムが実際に動いている最中）に発生する脅威を検知します。

App and API Protection（アプリケーションおよび API 保護）▸

アプリケーション層の攻撃を検知・遮断します。例えば SSRF（Server-Side Request Forgery，サーバーサイドリクエストフォージェリ）は、攻撃者がサーバーを騙して代わりにリクエストを発行させ、本来アクセスできない内部リソースにアクセスする手法です。また SQL（Structured Query Language，構造化問い合わせ言語）Injection（SQL インジェクション）は、悪意のある SQL 構文を入力フィールドに混入させてデータベースクエリを操作する手法です。あわせて API のディスカバリーとポスチャー管理も提供します。

Code Security（コードセキュリティ）▸

開発ライフサイクルの中で、自社コードとオープンソース依存パッケージの脆弱性を見つけます。

製品同士がどう価値を高め合うか Cloud SIEM は他のセキュリティ製品の情報を使って、自身の検知結果をより豊かにできます。例えば第 5 章で触れる Risk Insights は、Cloud SIEM の signal に Cloud Security の Misconfigurations と Identity Risks のデータを組み合わせ、統合された「実体リスクスコア」を算出します。これにより「何が起きたか」だけでなく、「この実体自体がどれだけ危険か」まで見えるようになります。
Chapter 02 · Pipeline

データはどうきれいになるか

log が送られてくるだけでは足りません。この章では、log が届いた後にどんな加工工程を経て、ルールが理解でき検索できるきれいなデータになるのかを分解します。同じ 1 件の log で生産ライン全体を通し、1 ステップずつどう変わっていくかを見ていきます。

まず Pipeline と Processor の関係を理解する

Datadog の Log Management では、Pipeline（パイプライン）は順番に実行される Processor（プロセッサー）の集まりで、Logs → Configuration → Pipelines ページで設定します。各 processor はごく小さな仕事を 1 つだけ担当し、前の工程で処理された結果はそのまま次の工程に渡されます。工場の生産ラインと同じで、生の log が原材料、processor が 1 つずつの加工ステーションであり、最終的に出力されるのは SIEM が分析できる標準化された log です。

以下では同じ 1 件の log を使って、生産ライン全体の 5 つのステップを順番にたどり、各ステップでどの processor を使い、実際にどう変わるかを見ていきます。

Grok Processorを通す前の log は、通常ただの非構造化テキストの連なりで、ルールは特定のフィールドに対して照合できません。

生の log2020-01-01 12:00:01 google oauth login success by John Doe from 1.2.3.4

Grok Processor：非構造化文字列から必要なフィールドを抜き出します。ぐちゃぐちゃな文章を使える形のフィールドに 1 つずつ切り分けるようなイメージです。

名前の由来 Grok という単語は、1961 年の SF 小説『異星の客（Stranger in a Strange Land）』に由来します。著者 Robert Heinlein がこの作品でこの語を創り、「あることの本質を完全に、直感的に理解する」という意味を持たせました。表面的に知っているだけでなく、徹底的に会得することを指します。ログ処理の世界（最初に Logstash がこの呼び方を使い、その後 Splunk や Datadog も同じ慣習を踏襲しました）がこの語を借用したのは、この processor がまさに「本来ごちゃごちゃした文字列を読み解き、各部分が何を意味するかを理解する」ことをしているからで、それで Grok と名付けられました。

Grok の実際の仕組みは、あらかじめ定義されたパターン（pattern、実体はラップされた正規表現 regex）で文字列を照合し、パターンに一致した部分を抜き出してフィールド名を付けるというものです。

生の log と Grok pattern の対応（イメージ）
%{date("yyyy-MM-dd HH:mm:ss"):timestamp} %{word:evt.name} login %{word:evt.outcome} by %{data:usr.id} from %{ip:network.client.ip}
上記のようなパターンを生のテキストに適用すると、次のように解析されます。 
{
  "usr.id": "John Doe",
  "evt.category": "authentication",
  "evt.name": "google oauth",
  "evt.outcome": "success",
  "network.client.ip": "1.2.3.4"
}
これらのフィールドがあって初めて、ルールは evt.outcome:failure のような条件を検索できます。Grok による解析がなければ、この文章全体はルールにとって構造の分からない文字列の連なりでしかなく、「outcome が failure かどうか」を単独で照合することはできません。

OCSF Processor：ソース固有のフィールドを、ソースをまたいで統一された標準フィールドに remap（再マッピング）します。

背景 OCSF（Open Cybersecurity Schema Framework）は 2022 年に AWS と Splunk が共同で立ち上げ、オープンソースコミュニティに寄贈した「セキュリティイベントデータスキーマ（schema）」の標準です。その後 Datadog、CrowdStrike、IBM など数百社のセキュリティベンダーが順次採用しました。Schema（スキーマ）とは平たく言えば「データがどんな形であるべきかを定めた仕様書」です。1 つの「ログインイベント」にどんなフィールドが必要か、フィールド名は何と呼ぶべきか、値はどんな型であるべきかを定め、すべてのベンダーが同じ仕様書に沿って出荷することで、各社バラバラに語ることがなくなります。

OCSF はイベントを異なるクラス（class）に分類します。例えば第 1 章で触れた Authentication（認証）、API Activity（API アクティビティ）、Account Change（アカウント変更）などで、各クラスの下に標準属性名のセットが定められています。ここでは「ユーザー」という属性を例にとると、OCSF での標準名は actor.user.name です。ソースが CloudTrail であれ Okta であれ、ここでの Google OAuth log であれ、Processor はそれぞれ元のフィールドをこれにマッピングします。

GeoIP Processor：IP アドレスに基づいて地理位置情報を追加します。

実際にどうやって地理位置を調べるか GeoIP Processor の裏側にあるのはIP アドレスと地理的な区画を対応させたデータベースです（業界でよく使われる MaxMind GeoLite2 などで、Datadog 内部でこの種のデータベースを保守しています）。「どの IP 範囲がどの国・都市のネットワーク事業者に割り当てられているか」が記録されています。Processor は IP を受け取ると、そのデータベースでどの範囲に該当するかを調べ、対応する国、都市、緯度経度を返します。これは「この電話番号の市外局番がどの都市か」を調べるのと同じロジックです。誰かにリアルタイムで問い合わせるのではなく、既知の対応表を参照しているだけです。
エンリッチメント後に追加されるフィールド
{
  "network.client.ip": "1.2.3.4",
  "country": "Japan",
  "city": "Tokyo"
}
用途：Impossible Travel 検知（各ログインの地理位置を先に知らないと 2 地点間の距離を計算できません）、新しい国からのログイン検知、攻撃元の地図表示。

SIEM Index Filterが、この処理済みの log を Cloud SIEM index に送るかどうかを決定します。

「filter を通過する」とは実際どういう意味か SIEM Index Filter は本質的にクエリ構文（普段 Datadog で log を検索するのと同じ構文）であり、Logs → Configuration → Indexes → 該当する SIEM index → Index filter に設定します。「filter を通過する」とは、この log が持つフィールド/tag がこのクエリ条件に一致することを意味します。
例：実際の filter query はこんな形になります 
source:(cloudtrail OR okta OR github OR guardduty)
この filter の意味は、この log の source タグが CloudTrail、Okta、GitHub、GuardDuty のいずれかであれば「通過」とみなされ、SIEM index に送られるということです。もし source:my-custom-app という log があり、filter にこのソースが含まれていなければ、この log は SIEM index に入らず、どの Detection Rule からも見えません。

1 件の log を「通過」させる方法：① 手動で Logs Index Configuration ページに行き、そのソースの source（または他のカスタム tag）を filter のクエリ条件に追加する。② より手間が少ない方法は、対応する Content Pack（第 1 章参照）を有効化することです。Datadog がその Content Pack に必要なソースを自動的にこの filter に追加してくれるので、手動でクエリ構文を編集する必要がありません。

filter を通過しさえすれば、log は SIEM index に保存されます。たとえどの Detection Rule も発火しなくても、後から遡って調査できるよう残されます。 filter に一致しない log は、どの Detection Rule からもまったく見えません。

OOTB Pipeline は読み取り専用の出発点

OOTB（Out-Of-The-Box，すぐに使える状態）：Datadog はよく使われるソース向けにあらかじめデフォルトの pipeline を用意しています。例えば AWS CloudTrail pipeline、AWS GuardDuty pipeline は、よくあるフィールド（eventName、sourceIPAddress、userIdentity）を自動的に解析します。

重要な詳細この種の OOTB pipeline は通常読み取り専用で直接編集できませんが、その後段にカスタム処理を接続して、組織固有の解析ニーズを補うことができます。

Log の保持階層

データの「温度による階層分け」と考えることができ、背後にあるロジックは検索速度とストレージコストの綱引きです。速く検索できる階層ほどコストが高いため、すべての log を最も高価な階層に無期限に置いておくことはしません。

階層適した用途検索速度
Standard indexing頻繁に検索するホットデータ向け、より多くの計算リソースを許容できる最速
Flex Logs頻繁には検索しないが保持し検索可能にしておく必要がある、最長 15 か月中程度
Log Archivesコンプライアンス/長期保存向け、ほとんど検索しない最遅（先に復元が必要）
例：典型的な階層化戦略 直近 30 日の log は Standard indexing に置く（アナリストが毎日検索するので速さが必要）。30 日から 15 か月の log は Flex Logs に移す（コンプライアンスや事後調査でたまに検索するが即時性は不要）。15 か月を超え、法規制の保持要件を満たすためだけの log は Log Archives に移す（ほとんど検索せず、検索する際は復元に時間がかかる）。この 3 階層は Logs → Configuration → Indexes で各 index ごとに保持日数・移行ルールを設定します。

どの階層を選んでも、Cloud SIEM はデータが入ってきた瞬間にリアルタイムで分析します。安価なストレージ階層を選んだからといって脅威検知が遅れることはありません。リアルタイム分析は log が届いたその瞬間に発生し、その後どの階層にアーカイブするかは「事後のストレージ」の決定であり、両者は別の話です。Security Signal 自体は 15 か月保持されます。

Flex Logs の制限（見落としがちな試験ポイント）

Flex Logs は Log Monitor をサポートせず、公式に今後もサポートしないと明言されています。理由は 2 つあります。① 検索速度が比較的遅く、Monitor はほぼリアルタイムのスキャンが必要なため、Flex の遅延がアラートの即時性を損なう。② Flex の計算リソース（Query Pool）を大量に消費し、Monitor が繰り返しクエリを実行すると割り当てを使い切ってしまう。Watchdog も Flex Logs をサポートしません（同様に継続的なスキャンが必要なため）。

代替案：先に Metrics from Logs で監視したいパターンを metric に変換し、その metric に対して Monitor を設定します。一言でまとめると、Flex Logs は「残しておいて後で調べる」のに向いており、「リアルタイムで監視してアラートを出す」のには向いていません。

Index の順序：SIEM index は必ず 1 番目に

Log は pipeline を経た後、どの index に入るかが決まります。1 つのアカウントには通常複数の indexがあります（例えば一般的なアプリケーション log 用の index、監査用の index など）。Cloud SIEM 専用の index（例：cloud-siem-xxxx）もあり、これらの index は設定画面の中で順序が決まっています。

なぜ順序が「受信できるかどうか」に影響するのか 各 index には独自のフィルター条件、1 日あたりの割り当て（quota）、サンプリングルールがあります。log は index の並び順に従って順番にチェックされ、前方に並んでいる index の割り当てを使い切っていたり除外ルールが設定されていたりすると、一部の log を先に遮断・破棄してしまうことがあります。その結果、後方に並んでいる index（SIEM index を含む）はその log を見る機会すら得られません。
試験のポイントCloud SIEM index は必ず 1 番目に置く必要があります。これにより、条件に一致する log を他の index の割り当てや除外ルールに先取りされることなく、優先的に受け取れることが保証されます。画面に「The Cloud SIEM index is not in the first」という警告が出ることがあり、これは index の順序設定が誤っていることを示します。Logs → Configuration → Indexes ページで手動で SIEM index を一番上にドラッグ（reorder）する必要があります。
Chapter 03 · Rule Basics

ルールの基礎：種類、コンポーネント、8 つの検知方法

データがきれいになった後、実際の判定ロジックがここで発生します。signal とは何か、ルールにはいくつ種類があるか、共通コンポーネントは何か、そしてどんな方法で「これは異常だ」と判定するのか。これらは次章の MITRE マッピングと応用チューニングの土台になります。

Signal ≠ 生の log

Detection rule は、Cloud SIEM がリアルタイムで入ってくる log に対してどんなロジックを適用するかを定義し、条件に一致すると Security Signal を生成します。

Analogylog は生の証拠、ルールは探偵の推理ロジック、signal は探偵が事件を解決した後に書く「ここに問題がある」という報告書です。

3 種類のルールタイプ

Real-time rules
log が入ってきたら継続的に監視し、条件が一致すればすぐに signal を生成
例：あるルールが「5 分間のログイン失敗回数」を計算している場合、この集計と監視はリアルタイムで動いています。
Scheduled rules
一定間隔でクエリを実行、長く続く脅威を捕まえるのに向いている
例：DNS（Domain Name System，ドメインネームシステム） tunneling（データを DNS クエリに隠して送信する手法）、low-and-slow brute force（わざと速度を落として試行を分散させ、短時間のしきい値を回避する手法）。この種の攻撃は時間範囲を長く取って定期的に振り返らないと捕まえられません。
Historical jobs
過去データに対して 1 回限りのクエリを実行、継続的な監視ではない
用途：新しいルールの backtesting（バックテスト）。「このルールが 2 か月前から存在していたら、ある既知のインシデントを捕まえられたか」を検証し、ルールに見逃しや過検知がないかを確認します。

Cloud SIEM には数百の OOTB ルールが組み込まれており、Datadog Security Research チームが継続的に保守し、新しいルールは自動的にアカウントに取り込まれます。Rules List では source でフィルターしてルールのカバレッジ状況を確認できます。

OOTB ルールとカスタムルールの関係（誤解しやすい詳細）
  • OOTB ルールは Datadog が継続的に開発し、更新は自動的にアカウントへ取り込まれます。カスタムルールはユーザー自身が作成・保守するもので、Datadog からの自動更新を受け取ることはありません。調整したい場合は自分で手動変更するしかありません。
  • 両者は互いに独立したルールであり、「どちらが優先されるか」という仕組みは存在しません。カスタムルールとある OOTB ルールが同じ種類の活動を対象にしていても、2 つのルールはそれぞれ独立して評価され、それぞれ別々に signal を生成する可能性があります。カスタムルールが OOTB ルールを自動的に置き換えたり上書きしたりすることはありません。
  • 機能が似たカスタムルールを作成しても、対応する OOTB ルールが自動的に削除されることはありません。ユーザーが手動でどちらかを無効化しない限り、両方とも動き続けます。

ルールの 5 つの共通コンポーネント

Detection method（検知方法）▸

Cloud SIEM がどのように log を評価するかを定義します。全 8 種類あり、下の章を参照してください。

Search queries（検索クエリ）▸

どの log 条件に一致させるかを指定します。

Conditions（トリガー条件）▸

いつ signal を生成するか、また重大度（severity）のレベルを決定します。

Playbook（対応手順書）▸

ルール名、調査用の説明文、タグ（tag）を含み、その中に MITRE ATT&CK 対応タグも含まれます（次章冒頭を参照）。

Suppressions（抑制条件）▸

どんな状況でsignal を生成しないかを定義し、既知の誤検知を除外して alert fatigue（アラート疲れ）を減らします。抑制されるのは「signal のレイヤー」であり、log 自体はまったく削除されず、後から遡って検索できます。

Query の種類照合対象作用するタイミング
Suppression querysignal の属性ルール条件が一致し、signal を生成しようとした後
Data exclusion query生データ（log/event）の属性ルールがこのデータを評価する前

両者は同じクエリ構文を使い、違いは純粋に照合対象だけです。どちらもこのルール 1 つにのみ適用され、複数のルールにまたがるかどうかとは無関係です。

8 つの検知方法

各カードをクリックすると例が見られます。

Threshold
回数がしきい値を超える
例：5 分間で 10 回を超えるログイン失敗。全員が同じ固定のしきい値ラインを共有します。
New Value
これまで出現したことのない値
例：あるユーザーが初めて「これまでログインしたことのない国」からログインする。
Anomaly
動的なしきい値、自分自身の履歴と比較
例：普段は 1 時間に 50 回の API 呼び出しが、突然 500 回になる。各実体は自分自身のベースラインを持ち、Threshold の固定しきい値とは異なります。
Content Anomaly
内容の異常であり、回数ではない
例：ある API 呼び出しの普段のパラメータパターンは固定なのに、ある回だけ内容の構造が急に大きく変わる。回数自体は増えていなくても該当します。
Impossible Travel
地理的位置が不合理
同一アカウントのアクセスイベントが 2 つの地点で発生し、その距離が経過時間内に人間が移動できる範囲を超えている。
Third Party
外部ツールのアラートを転送
例：Amazon GuardDuty がすでに生成したアラートを Datadog に転送し、signal として表示します。
Signal Correlation
複数の signal を 1 つに統合
例：「新しいデバイスからのログイン」と「大量のファイルダウンロード」を個別に見ると低重大度の注意喚起にすぎませんが、関連付けると信頼度が大きく高まります。
Sequence
順序のある一連のイベント
例：ロールの想定 → 権限昇格 → データアクセスが、順番どおりかつ妥当な時間内に発生して初めて、完全な攻撃シーケンスと判定されます。
Chapter 04 · MITRE & Advanced Tuning

MITRE ATT&CK と応用チューニング

ルールの基礎が分かったところで、ルールが業界共通の攻撃手法言語（MITRE ATT&CK）とどう対応するかを見ていきます。続いて混同しやすい 3 つの「せき止める」仕組みを見て、最後にルールのチューニングとバージョン比較を扱います。

MITRE ATT&CK はどこから来て、何を解決するか

MITRE ATT&CK の正式名称は Adversarial Tactics, Techniques, and Common Knowledge（対手の戦術・技術・共通知識）です。

背景 MITRE Corporation はアメリカの非営利研究機関で、長年アメリカ政府のために国防・セキュリティ関連の研究開発センターを運営してきました。2013 年、MITRE 内部の FMX という研究プロジェクトが「実際の攻撃者が具体的に何をしているのか」を体系的に整理し始めました。手法としては、大量の実際の侵入事件と APT（Advanced Persistent Threat，高度で持続的な脅威組織）の活動記録を分析し、観測された手口を分類してまとめ、2015 年に ATT&CK フレームワークとして公開しました。解決しようとした問題は、セキュリティ業界に長らく共通言語が存在しなかったことです。同じ攻撃手法でも、ベンダーやアナリストによってまったく異なる言い方で説明されることがあり、経験の蓄積やルールの相互運用ができませんでした。ATT&CK 以降、「T1110 はブルートフォース」というのが業界の共通認識になり、どこの会社のアナリストでも、この番号を見れば何を指しているか分かるようになりました。

フレームワークは 2 層に分かれます。

  • Tactic（戦術）：攻撃者の高次の目標、つまり「なぜ」それをするのかです。Enterprise Matrix はおおよそ攻撃のライフサイクルに沿って並んでおり、Initial Access（初期アクセス）、Execution（実行）、Persistence（永続化）、Privilege Escalation（権限昇格）、Defense Evasion（防御回避）、Credential Access（認証情報アクセス）、Discovery（探索）、Lateral Movement（横方向移動）、Collection（収集）、Exfiltration（データ持ち出し）、Impact（影響）など十数種類があります。
  • Technique（技術）：その戦術の目標を達成するための具体的な手法、つまり「どうやって」です。各技術には固定の番号が付けられており、形式は T####、より細かいサブ技術は T####.### です。

Tactic を章のタイトル、Technique をその章の中の具体的な技だと考えると分かりやすく、1 つの Tactic には通常複数の Technique が対応します。

混同しやすい 3 つの仕組み：Filter / Rule / Suppression

この 3 つはよくシナリオ判断問題として出題され、「これはどの仕組みが働いているのか」を見分けさせます。

仕組み作用するタイミング作用する範囲効果
SIEM Index Filterlog が SIEM index に入る前アカウント / index レベル、すべてのルールに影響条件に一致しない log はどのルールからも評価されない
Detection Rule の Data Exclusion Querylog はすでに SIEM index にあるが、このルールが評価する前単一ルールレベルこのデータは「このルール」にとって存在しないのと同じ

覚え方Filter は「SIEM に入れるかどうか」を管理し、Rule（Data Exclusion を含む）は「このルールが見えるかどうか」を管理し、Suppression は「条件に一致した後、通知するかどうか」を管理します。

タイムライン：同じ 1 件の log が順番にこの 3 つの関門を通過する

CHECKPOINT 1
SIEM Index Filter
アカウントレベルの関門。log の source/tag と照合。
不通過 → log はまったく SIEM index に入らず、以降の 2 つの関門にすら回らず、どのルールからも見えません。
CHECKPOINT 2
Data Exclusion Query
単一ルールの関門。入ってきた生データの属性と照合。
不通過 → このルールはこのデータを完全にスキップし、回数の集計にも含めません。ただし log は SIEM index に残り、他のルールからは普通に見えます。
CHECKPOINT 3
Suppression Query
単一ルールの最後の関門。生成されようとしている signal の属性と照合。
一致 → signal がミュートされ Signal Explorer に表示されない。不一致 → signal は通常どおり生成される。
例：同じ「既知の誤検知」でも、どの関門で処理するかで結果が大きく変わる シナリオ：サービスアカウント backup-bot が毎日スケジュールバックアップを実行し、決まって最初のログインが失敗してから再試行で成功します。これはチームが既知の誤検知源として把握しており、ルールは「5 分間で 10 回を超えるログイン失敗」の Threshold ルールです。

ルールに Data Exclusion Query を設定した場合

-usr.id:backup-bot と設定します。backup-bot のログイン失敗 log は「このルール」にとって最初から存在しないことになり、回数の集計にはまったくカウントされません。たとえ 1 日に 100 回ログインに失敗しても、このルールがそれによってトリガーされることは永遠にありません。他のルール（例えば Impossible Travel）は影響を受けず、この log を普通に評価し続けます。

Suppression Query に変更した場合

signal の属性 usr.id:backup-bot に一致させる設定をします。ルールは通常どおり回数を集計し、10 回のしきい値に達するとルールロジックは「ここで signal を生成すべき」と判定します。ただ最後の瞬間に Suppression Query がそれを止め、この signal は Signal Explorer に表示されません。下層の log と「あわや発火するところだった」という経緯はまったく影響を受けず、後からいつでも遡って検索できます。

2 つのやり方は最終的に「ユーザーにアラートが見えない」という結果は同じですが、それが起きる段階はまったく異なります。Data Exclusion はルールに最初から最後までこのデータが存在しないと思わせるものであり、Suppression はルールに判定プロセス全体を最後まで進めさせ、本当にアラートを出すと判定した後で、ゴール直前で止めるものです。

ルールのチューニング、カスタムルール、バージョン比較

検知方法を理解したところで、次はルールを自分の環境に合った形に育てる方法です。OOTB ルールは良い出発点ですが、通常は自分の環境に合わせたチューニングが必要です。OOTB ルールに対して、既知の誤検知の suppression を直接追加したり、severity レベルを調整したり、playbook に組織固有の調査手順を追記したりできます。OOTB ルールがカバーしていない、組織特有の脅威に対しては、同じコンポーネントと検知方法を使って完全なカスタムルールを作成できます。OCSF による正規化のおかげで、OCSF 属性に対して書かれたカスタムルールは複数の log ソースに同時に適用できるため、うまく書かれた 1 つのカスタムルールで広いカバレッジを提供できます。

Rule Version History：ルールの新旧バージョンの設定差分を比較する ルールエディターにはバージョン履歴機能が組み込まれています。ルールをチューニングした後（例えばクエリの範囲を単一の environment から複数の environment に拡大した場合）、Open Version Comparison オプションを使って、現在のバージョンと以前のバージョンの設定を並べて比較でき、差分は色で示されます（赤は削除された設定、緑は追加された設定）。

これは第 6 章で触れる Datadog Audit Trail とは異なります。Audit Trail が記録するのは「誰がいつルールを変更したか」というプラットフォームレベルの操作イベントであり、Rule Version History はルールエディター内で 2 つのバージョンの設定内容の差分を直接比較するツールです。
Chapter 05 · Investigation

Signal が生成された後、どう調査するか

ルールが発火した後、あなたが手にするのは雑然とした log の山ではなく、すでに整理された signal です。この章では 4 つのツールが「何が起きたか」から「この実体はどれくらい危険か」まで、どうたどり着くのかを見ていきます。

Signal は生の log ではない

Analogylog は散らばった証拠の断片で、signal はすでにその断片をつなぎ合わせ、探偵のメモを添えた事件記録です。

基本的な生成フロー：log が入ってくる → SIEM Index Filter を通過する → Detection Rule を適用 → 条件に一致 → signal を生成。

Signal には 2 つの重要な状態フィールドがあります。Severity（Critical / High / Medium / Low / Info）とトリアージ状態です。

Open→ Under Review→ Archived

特定のユーザーに担当者として割り当てることができ、15 か月保持されます。任意の signal をクリックするとサイドパネルが開きます。

4 つの調査ツール、浅いものから深いものへ

Signals Explorer▸

signal を閲覧・検索・フィルター・関連付けするインターフェースで、severity、source、rule、tag、時間範囲、その他任意の属性でフィルターできます。調査の出発点です。

Investigator▸

グラフ形式のインターフェースで、実体間の関係と攻撃経路（Attack Path）を追跡します。攻撃者がある足がかりから一連の行動を経て、最終的に目的を達成するまでの経路全体です。「このアイデンティティは何をしたか？どのサービスとやり取りしたか？ロールが想定された後何が起きたか？成功したか？」に答えます。AWS、GCP、Azure、Datadog、Kubernetes に対応しています。

Risk Insights▸

セキュリティデータを「個々の実体」（IAM ユーザー、S3 bucket、EC2 instance、GitHub repo など）ごとの統合リスクプロファイルにまとめます。リスクスコアはその実体に関連する過去 14 日間の signal の重大度と頻度から算出され、Cloud Security も有効化していれば Misconfigurations と Identity Risks もスコアに組み込まれます。「今、自分の環境でどの実体のリスクが最も高いか？」に答えます。

Bits AI Security Analyst▸

AI による自動初期トリアージ：トリガーとなった log と文脈を分析し、重要な証拠を要約し、「良性か疑わしいか」の判断の推論を説明し、次のステップを提案します。MITRE ATT&CK を土台にしており、複数の IOC を横断的に確認し、過去のデータを検索できます。アナリストの判断に取って代わるものではなく、初期評価を加速するもので、実際の効果はより速い MTTA です。
例：Amazon SNS enumeration の signal に対して、Bits AI は SUSPICIOUS と判断し、証拠にはアカウント乗っ取りの兆候、匿名プロキシインフラ、AWS サービスに対する組織的な偵察が含まれていました。

脅威インテリジェンス（Threat Intelligence）と IOC

IOC（Indicators of Compromise，侵害指標）：観測可能な具体的な証拠で、例えば IP、ドメイン、ファイルハッシュ値、URL などがあり、あるシステムがすでに侵害されているか、標的にされている可能性を示唆します。

まず Feed とは何かを理解する Feed（インテリジェンスフィード）は継続的に更新される「既知の悪者リスト」の購読のようなものだと考えられます。セキュリティ研究機関やベンダーは日々世界中の攻撃活動を観測し、発見した悪意のある IP やドメインをリストにまとめ、購読を通じて絶え間なく届けてくれます。あなたのシステムはそのリストを使って自分のデータと照合できます。ニュースの購読と同じで、feed の価値は「継続的に更新される」ことにあり、1 度調べたら終わりの静的なリストではありません。
仕組み：threat_intel 属性とは何か

入ってきた log の IP やドメインが、feed の中のある既知の IOC と一致すると、Cloud SIEM はその log 自体に threat_intel 属性を追加し、「この IP は既知の脅威で、どのカテゴリに属するか」という判定結果をデータに直接書き込みます。

{
  "network.client.ip": "185.220.101.42",
  "threat_intel": {
    "category": "residential_proxy"
  }
}

この属性は表示用のラベルというだけではありません。他のフィールドと同様に検索可能なデータなので、Detection Rule はこれを直接クエリ条件として使えます。例えば @threat_intel.category:(malware OR tor) に一致するルールを書けば、「接続先自体が既知の悪意あるソースである」イベントに絞って signal を生成でき、自分で IP ブラックリストを保守する必要がありません。よくあるカテゴリ：malware（マルウェア）、cryptomining（暗号資産マイニング）、tor（Tor 匿名ネットワーク）、residential proxy（住宅用プロキシサーバー。一般家庭のネットワークに見せかけて悪意のあるトラフィックを隠すのによく使われます）、scanner（スキャンツール）。

組み込みのキュレーション済み feed

IPinfo、GreyNoise などのパートナーから提供され、すべての log に自動的に適用されます。設定は一切不要です。

自前の feed（Bring your own）

商用ベンダー、業界の情報共有組織であるISAC（Information Sharing and Analysis Center，情報共有分析センター。同業界の企業同士で脅威インテリジェンスを交換する組織）、あるいは社内のパイプラインから取り込み、reference table として保存します。CSV（Comma-Separated Values，カンマ区切り値）ファイルを手動でアップロードするか、クラウドストレージから定期的に自動更新できます。

見落としがちな詳細：指標タイプごとに 1 つの表 指標のタイプごとに、それぞれ独立した reference table が 1 つ必要です。例えば IP アドレス用に 1 つの表、ドメイン用に別の表というように、異なるタイプの指標を同じ表に混ぜてアップロードすることはできません。現在サポートされているカスタム IOC の取り込み方法は「CSV を Reference Table に取り込む」という 1 つの経路だけで、JSON を直接送信できる独立した Threat Intelligence API は存在せず、STIX（Structured Threat Information eXpression，構造化脅威情報表現）/TAXII（Trusted Automated Exchange of Intelligence Information，信頼できる自動化された情報交換）を経由するものでもありません。これらは業界の別の脅威インテリジェンス交換の標準プロトコルであり、Datadog がカスタム IOC を取り込む方式ではありません。
Chapter 06 · Metrics & Continuous Improvement

どう測定し、継続的に改善するか

検知と調査は半分にすぎません。もう半分は、運用全体を追跡可能で、上司に報告でき、コンプライアンスの証拠として使えるものに数値化することです。そしてそれが継続的に良くなっていくループを形成します。

1 つの signal のライフライン：MTTD / MTTA / MTTR

3 つの指標はすべて「Mean Time to ___（あることを成し遂げるのに平均でどれだけ時間がかかるか）」の略で、それぞれライフラインの異なる区間を測定します。

  • MTTD の正式名称は Mean Time to Detect（平均検知時間）
  • MTTA の正式名称は Mean Time to Acknowledge（平均確認時間）
  • MTTR の正式名称は Mean Time to Resolve（平均解決時間）
STAGE 1
log が送信される
ルール条件に一致する log が ingestion に入る
STAGE 2 · MTTD
signal 生成
Mean Time to Detect：time_to_detect、log の送信から signal 生成までの時間
STAGE 3 · MTTA
Under Review
Mean Time to Acknowledge：time_to_acknowledge、signal 生成からアナリストが確認マークを付けるまでの時間
STAGE 4 · MTTR
Archived
Mean Time to Resolve：time_to_resolve、signal 生成からアーカイブまでの総解決時間
推論の例MTTD は低いのに MTTA が上がり続けている場合、検知パイプラインは正常に機能していることを示しており、問題はアナリストのトリアージが十分速くないことにあります。やるべきことは通知のルーティングを調整するか、Bits AI を活用して初期トリアージを自動化することであり、検知ルールを変更することではありません。

ダッシュボードと週次ダイジェスト：数字を見える化する

Cloud SIEM Overview ページには次のものが表示されます。重要な signal、高リスクの実体、Content Pack の健全性とオンボーディング状況、地理/MITRE tactic 別の上位 signal、MTTD と誤検知率、最新の Security Research Feed。

OOTB ダッシュボード（例えば CloudTrail ダッシュボード）は複製してカスタマイズできます。対象読者に応じて、経営層向け、検知エンジニア向け、運用チーム向けのダッシュボードも作成できます。

週次ダイジェスト：過去 7 日間のアラート量、対応時間、重要な新しい問題をまとめたものです。各ユーザーが個別に購読する必要があり、security_monitoring_signals_read 権限が必要です。

QUESTION 1 OF 10

After creating a custom log detection rule for identifying privilege escalation attempts, the rule does not appear on the MITRE ATT&CK Map despite being enabled. What is the most likely cause?

AThe rule uses a log detection type, which is incompatible with the MITRE ATT&CK Map visualization.
BThe rule is missing the required tactic: and technique: tags paired with the security:attack tag.
CThe rule must be converted from a custom rule to an out-of-the-box rule to appear on the map.

正解は B。MITRE への対応はルール上の tag によって行われます（第 4 章参照）が、tactic:/technique: を追加するだけでは不十分で、ルールには同時に security:attack という tag も必要です。この 3 つが揃って初めて、MITRE ATT&CK Map にこのルールが可視化されます。

A は誤り：log detection type（Threshold、New Value などの検知方法で書かれたルール）は問題なく MITRE Map に対応でき、両者は矛盾しません。C は誤り：カスタムルールはもともとマップに表示され得るもので、OOTB ルールに変換する必要も、変換できるわけでもありません。tag さえ揃えれば十分です。

QUESTION 2 OF 10

Custom threat intelligence indicators need to be imported into Cloud SIEM for log enrichment. Which format is supported for uploading custom Indicators of Compromise?

ASTIX 2.0 bundles uploaded through a TAXII server integration.
BCSV files uploaded to or imported into Datadog Reference Tables.
CJSON objects submitted directly through the Threat Intelligence API.

正解は B。第 5 章の脅威インテリジェンスの仕組みに対応しています。自前の feed は Reference Table として保存され、CSV ファイルを手動でアップロードできます。補足：指標のタイプ（IP、ドメインなど）ごとにそれぞれ独立した reference table が必要で、同じ表に混在させることはできません。

A は誤り：STIX/TAXII は業界の別の脅威インテリジェンス交換標準プロトコルであり、Datadog Cloud SIEM がカスタム IOC を取り込む方式ではありません。C は誤り：現状 JSON を直接送信できる独立した Threat Intelligence API はなく、取り込みは Reference Table の経路のみです。

QUESTION 3 OF 10

Which statement accurately describes how SOAR workflow blueprints function in Datadog?

ABlueprints provide customizable starting templates that can be modified to match team-specific processes.

QUESTION 4 OF 10

After launching the Datadog CloudFormation StackSet to onboard AWS accounts under an Organization, the deployment fails before creating IAM roles in any target account. The Organization has trusted access enabled and service-managed permissions configured. Which configuration error causes this failure?

AThe Execution configuration option was set to Active for parallel operations.
BThe Deployment targets were set to the full Organization instead of an OU.
CMultiple AWS regions were selected under the Specify regions setting.

正解は C。この問題は第 1 章の AWS Org StackSet の補足では明示していなかった内容です。IAM は AWS のグローバルサービスでリージョンに依存しませんが、StackSet は「アカウント × リージョン」ごとに stack instance を作成します。Specify regions で複数リージョンを選択すると、テンプレートは複数のリージョンでそれぞれ同名の IAM role を作成しようとして衝突が発生し、どのアカウントでも IAM role を作り終える前にデプロイ全体が失敗します。

Architecture Overview · One Log, Start to Finish

アーキテクチャ全体像：1 件の log を追って、raw log から脅威判定までをたどる

これが Cloud SIEM の完全なアーキテクチャ図です。抽象的な概念のリストではなく、実際の 1 件の log を最後まで追いかけ、各ステーションで実際にどう変化し、どんな判断を経るのかを見ていきます。シナリオ：攻撃者が IAM ユーザー admin に対してブルートフォース攻撃を仕掛け、最終的にアナリストによって実際の攻撃であると確認されます。各「関門」の横には分岐ボックスで「もう 1 つの可能性」が描かれています。

STEP 01 · Raw log の到着

攻撃者が 5 分間のうちに IAM ユーザー admin に対して繰り返しログイン失敗を送信しており、これが 12 回目です。log が Datadog に届いた直後は、まだ非構造化テキストの連なりです。

2026-07-23 03:14:02 aws console login failed by admin from 203.0.113.44

チームはすでに AWS CloudTrail Content Pack を有効化しており、このソースはもともと OOTB pipeline とログイン失敗検知ルールに対応済みなので、その場で接続作業をする必要はありません。

STEP 02 · Grok Processor による解析

Grok があらかじめ定義されたパターンを使って、非構造化テキストを検索可能なフィールドに分解します。

{
  "usr.id": "admin",
  "evt.category": "authentication",
  "evt.name": "aws console login",
  "evt.outcome": "failure",
  "network.client.ip": "203.0.113.44"
}

STEP 03 · OCSF Processor による正規化

ソース固有のフィールドを、ソースをまたいで統一された標準フィールドに remap します。

{
  "actor.user.name": "admin",
  "class_uid": "Authentication",
  "activity_id": "Logon",
  "status_id": "Failure",
  "src_endpoint.ip": "203.0.113.44"
}

今後このソースが CloudTrail から Okta や他のシステムに変わったとしても、この標準フィールドに対応してさえいれば、同じルールで捕捉できます。

203.0.113.44 を IP 地理データベースで調べ、地理位置を補完します。

{

  "country": "海外、admin がこれまで一度もログインしたことのない地域",

STEP 05 · 脅威インテリジェンス照合

Cloud SIEM がこの IP を既知の IOC feed（malware / tor / residential proxy など）と照合します。

✓ 今回はヒットなし、属性は付与されず、log はそのまま次へ進みます ▼
⇢
✗ もう 1 つの可能性：既知の IOC にヒットlog に threat_intel.category（例えば tor、malware）が付与され、以降ルールはこの属性をそのままクエリ条件として使えますが、この log 自体の進行には影響しません。

STEP 06 · SIEM Index Filter

Filter の条件は source:(cloudtrail OR okta OR github OR guardduty) で、この log の source は cloudtrail です。

✓ 条件に合致、SIEM index への通過を許可 ▼
⇢
✗ もう 1 つの可能性：通過しなかった場合この log は SIEM index にまったく入らず、以降のすべてのステップは発生しません。この攻撃はまるごと見逃され、どのルールにも捕捉されません。

STEP 07 · SIEM Index への保存

Standard indexing（直近のホットデータ、いつでも検索可能）に保存されます。30 日を超えると保持ポリシーに従って Flex Logs に移され、最長 15 か月保持できますが、このステップはリアルタイム分析には影響しません。リアルタイム分析はすでに直前の ingestion 時点で行われています。

STEP 08 · Detection Rule による照合：Threshold にヒット

「5 分間で 10 回を超えるログイン失敗」というルールは Threshold 検知方法を使っています。これが 12 回目の失敗です。

✓ 閾値を超え、ルールロジックが「ここで signal を生成する」と判定 ▼
⇢
✗ もう 1 つの可能性：まだ閾値に達していない場合ルールは失敗回数を累積し続けるだけで、何のアクションも起きません。累積が 10 回を超えるか時間ウィンドウがリセットされるまで、このルールは静かに背後でカウントを続けます。

STEP 09 · Data Exclusion Query の確認

このルールに admin を除外する設定はあるか？

✓ ない（admin は既知の定期実行ボットアカウントではない）ので、そのまま進みます ▼
⇢
✗ もう 1 つの可能性：admin が除外設定されている場合このデータはこのルールにとって最初から存在しないことになり、回数の累積にも数えられず、以降のステップは発生しません。ただし他のルールには影響せず、log 自体は引き続き SIEM index に残ります。

STEP 10 · MITRE ATT&CK Tag の付与

このルール自体にあらかじめ対応するタグが設定されています。

tactic:credential-access
technique:brute-force
security:attack

3 つの tag がセットで現れ、これから生成される signal にはこれらのタグがそのまま付与され、MITRE ATT&CK Map のヒートマップにも集計されます。

STEP 11 · Suppression Query の確認

この signal をミュートする suppression rule はあるか？

✓ ない、そのまま生成 ▼
⇢
✗ もう 1 つの可能性：suppression にヒット例えばこの IP がたまたま既知の社内ペネトレーションテストの送信元だった場合、signal はミュートされ Signal Explorer には表示されませんが、元の log はまったく手を加えられておらず、後からでも遡って調査できます。

STEP 13 · アナリストによるトリアージ

アナリストが Signals Explorer でこの High severity の signal を確認し、severity が高く credential-access の攻撃手法であることから優先対応と判断、状態を Open から Under Review に変更し、正式に調査を開始します。この反応時間こそが MTTA が測定しているものです。

STEP 14 · 詳細調査

  • Investigator を使って admin というアイデンティティが他に何をしたか、どのサービスとやり取りしたかを追跡し、攻撃者がログインに成功していないことを確認します。
  • Risk Insights では、この事件によって IAM ユーザー admin のリスクスコアが大きく上昇していることが表示されます。
  • Bits AI の分析結果は SUSPICIOUS。主要な証拠として、過去 24 時間で同じ送信元 IP が他のアカウントに対しても試行していたことが挙げられます（Signal Correlation と呼応）。

Bits AI はこのステップの初期評価を加速するだけであり、最終判断はあくまでアナリスト自身が行います。

STEP 15 · 判定と対応：実際の攻撃と確認

証拠を総合し、アナリストはこれが誤検知ではない、実際のブルートフォース攻撃であると判定します。Workflow Automation（SOAR）を発動して admin の認証情報を無効化し、関連アクセスを隔離します。同時に Notification rule が severity=High に基づいてこの signal をすでに PagerDuty にルーティングしており、当番担当者に通知が届いています。

STEP 16 · クローズと測定

対応完了、signal は Archived とマークされます。この一連の時間は 3 つの指標として記録されます。MTTD（log の取り込みから signal 生成まで）、MTTA（signal 生成から Under Review まで）、MTTR（生成から Archived まで）で、週報や Cloud SIEM Overview ダッシュボードに表示され、SOC 2 / PCI DSS といったコンプライアンス監査が求める「インシデントが追跡・解決されたか」の証拠にもなります。

STEP 17 · フィードバックが継続的改善サイクルへ

この事件は次回の継続的改善の入力になります。アナリストはこれを機に既知のペネトレーションテスト送信元を除外する Suppression rule を追加したり、MITRE ATT&CK Map を見直して credential-access というテクニックのルール網羅性が十分かを確認したりするかもしれません。これはまさに STEP 08 から STEP 11 までの判断ゲートに影響を及ぼします。
