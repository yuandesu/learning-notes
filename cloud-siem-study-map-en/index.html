Chapter 01 · Foundation

Why You Need a SIEM

This chapter answers one question: what does the cloud provider actually protect for you, and what gaps are left for you to fill yourself? The answer determines which data you must collect yourself, and that data is exactly the raw material for the entire Cloud SIEM pipeline.

Let's start with the full name: what exactly is Cloud SIEM

SIEM stands for Security Information and Event Management, a category of system that has existed in the security field for a long time. Its core job is to centralize logs/events scattered across systems, run correlation analysis, and surface possible threats. Datadog's Cloud SIEM is this type of system implemented natively on the Datadog platform: it reuses the logs you're already sending into Datadog and analyzes them in real time, with no need to bolt on a separate, standalone security system.

Analogy Think of feeding all the scattered surveillance camera feeds across a company (logs from each system) into a single monitoring room (SIEM), watched by the same team using the same set of rules, instead of every department watching its own footage and independently judging whether something looks off.

Shared Responsibility Model

Public cloud security is never "the provider handles everything" or "the customer handles everything." It's divided by service type, and the dividing line shifts toward the provider as the service becomes more "managed."

Analogy The apartment building you rent has access control, cameras, and a fire system (the provider's responsibility), but whether you lock your own door, where you keep valuables, and who has a spare key: those are always your own responsibility. The building manager won't handle that for you.

IaaS · e.g. AWS EC2

IaaS stands for Infrastructure as a Service: the virtual machine level. The customer manages the operating system, applications, and network rules; the provider only manages the physical facility, hardware, and virtualization layer. The customer carries the largest share of responsibility.

PaaS / Fully Managed · e.g. RDS, Lambda

PaaS stands for Platform as a Service: the provider covers the operating system, patching, and underlying operations, and the customer only needs to manage their own data and access settings.

No matter the service type, this never changes

Data, identity, and access policy are always the customer's responsibility. The provider will never manage whether your employees' account permissions are configured correctly.

Practical implication for monitoring The provider generates a large volume of security telemetry (audit logs, traffic logs, threat detection results), but will not proactively send it to your SIEM for you. You have to decide yourself which sources to collect, where to send them, and how long to retain them. That's the answer to "why you need a SIEM": the provider gives you raw material, and you need a tool to centralize, normalize, and analyze that raw material.

Five key categories of log sources

For Cloud SIEM to be effective, it must have visibility into your entire environment. Expand each category to see examples.

Cloud audit logs▸

Examples: AWS CloudTrail, GCP Audit Logs, Azure Activity Logs. These record "who made what API (Application Programming Interface, the interface systems use to talk to each other and issue commands) call, or performed what administrative action" against the cloud environment. This is the bedrock of cloud security monitoring.
Example: someone uses an IAM (Identity and Access Management) user's credentials to call the DeleteBucket API. CloudTrail records who did it, when, and from which IP.

Identity and authentication logs▸

Examples: Okta, Auth0, Azure AD. These track login events, MFA (Multi-Factor Authentication) challenges, and account activity.
Key term: Impossible Travel: the same account logs in from two locations far apart within a short window (e.g., logging in from Taipei, then from New York, 10 minutes later). It's physically impossible to travel that fast, which suggests the account may be compromised.

Network flow logs▸

Examples: AWS VPC (Virtual Private Cloud) Flow Logs, Azure NSG (Network Security Group) Flow Logs, GCP VPC Flow Logs. These only record connection metadata (who connected to whom, which port, how much traffic), not the packet contents themselves.
Example: an internal host suddenly transfers a large volume of data to an unfamiliar external IP, which could indicate data exfiltration; unusual lateral connections between internal hosts could indicate lateral movement, where an attacker who has compromised one machine uses it as a stepping stone to attack other internal machines.

SaaS and collaboration tool logs▸

SaaS stands for Software as a Service: cloud software you can use just by logging in through a browser, with no installation or maintenance required. Examples: Microsoft 365, Google Workspace, Slack, GitHub. These track user activity on collaboration platforms and developer tools.

Endpoint and third-party security tool logs▸

Examples: CrowdStrike, SentinelOne, Amazon GuardDuty. These forward alerts and findings that specialized security tools have already generated, so Cloud SIEM can fold those existing judgments into its correlation analysis as well.

Content Pack: turning "start from scratch" into "plug and play"

A Content Pack is a pre-packaged bundle of security content built for a specific log source: Detection Rules, Dashboards, Investigator widgets, Workflow Automation / SOAR blueprints (SOAR = Security Orchestration, Automation and Response), and sometimes a parser as well.

You have to build it all yourselfFind and connect the data source yourself, write the Detection Rule yourself, build the Dashboard yourself, build the Workflow yourself. Every single piece takes time to validate for correctness.
Example: AWS CloudTrail Content PackOnce enabled and connected to CloudTrail logs, you immediately get: a Detection Rule that flags anomalous AssumeRole behavior (role assumption anomalies, common in privilege escalation attacks), a CloudTrail activity dashboard, investigation views scoped to IAM user / IP, and workflows for automatic notification or automatic response.

Another example, oriented more toward threat intelligence integration: the Recorded Future Content Pack, which provides prebuilt detection rules, log enrichment, and an integrated dashboard.

Exam focus
  • Frequently tested: "which data sources does this Content Pack depend on."
  • Enabling a Content Pack automatically updates the SIEM Index Filter (it automatically adds the log sources the Content Pack needs into the filter, see Chapter 2), no manual configuration needed.
  • The core value of a Content Pack is shortening time-to-value (the time from installation to actually generating value).

Note: connecting an AWS Org account (CloudFormation StackSet)

To connect multiple accounts under an entire AWS Organization to Cloud SIEM in one go, Datadog provides a CloudFormation StackSet. It relies on the Organization's trusted access and service-managed permissions so the management account automatically deploys the necessary IAM role into every member account.

Common cause of deployment failure In the deployment settings, the Specify regions step allows only a single region to be selected. IAM is a global AWS service that isn't region-specific, but the StackSet deployment mechanism creates stack instances per "account x region." If multiple regions are selected, Datadog's template will try to create an IAM role with the same name in each region independently, causing a conflict, which makes the entire deployment fail before an IAM role has been created for any account.

Settings that are easy to confuse with the cause but are not the cause: setting Execution configuration to Active (parallel execution) only affects deployment speed/concurrency; setting Deployment targets to the entire Organization instead of a specific OU (Organizational Unit) is only a setting for deployment scope. Neither of these directly causes the whole deployment to fail, only the "multi-region selection" does.

Where Cloud SIEM sits within Datadog's Security product line

Cloud SIEM is just one piece of Datadog's Security product line, each piece responsible for a different layer of the security stack:

Cloud Security (security posture)▸

Focuses on the infrastructure's "security posture", meaning whether the configuration itself is secure. That's a different layer of concern from Cloud SIEM's focus on "is an attack happening." It breaks down into three parts:

  • Misconfigurations: continuously audits resource configurations against checklists defined by compliance frameworks such as CIS (Center for Internet Security) and PCI DSS (Payment Card Industry Data Security Standard).
    ExampleAn S3 bucket is configured as "publicly readable by anyone." That's a misconfiguration. No one needs to actually steal data for this to be a risk, the configuration itself is already a risk, and Misconfigurations flags it directly.
  • Identity Risks: detects risks related to IAM (Identity and Access Management).
    ExampleAn IAM role has been granted "admin"-level permissions but hasn't been used at all in the past 90 days. This is a combination of "excessive permissions" plus "unused credentials." If this credential set is ever leaked, the attacker would gain far more access than actually needed.
  • Vulnerabilities: scans containers and hosts to find known security vulnerabilities.
    ExampleA version of an open source package running on an EC2 host is found to correspond to a CVE (Common Vulnerabilities and Exposures, the industry's unified numbering system for known security vulnerabilities). Vulnerabilities will list this host as having that weakness, even if it hasn't been exploited yet.
Workload Protection▸

Monitors file, network, and process activity on hosts and containers, catching threats that occur at runtime (the moment the program is actually executing).

App and API Protection▸

Detects and blocks application-layer attacks, such as SSRF (Server-Side Request Forgery), where an attacker tricks a server into making a request on their behalf to reach internal resources it couldn't otherwise access, and SQL (Structured Query Language) Injection, where malicious SQL syntax is smuggled into an input field to manipulate a database query. It also provides API discovery and posture management.

Code Security▸

Finds vulnerabilities in your own code and open source dependencies during the development lifecycle.

How the products add value to each other Cloud SIEM can enrich its own detection results with information from other security products. For example, Risk Insights, covered in Chapter 5, combines Cloud SIEM's signals with Cloud Security's Misconfigurations and Identity Risks data to compute a single unified "entity risk score", so you see not just "what happened" but also "how dangerous this entity itself is."
Chapter 02 · Pipeline

How Data Gets Cleaned

Just having logs come in isn't enough. This chapter breaks down which processing stations a log passes through before it becomes clean data that rules can understand and query against. We'll follow the same log through the entire pipeline, step by step, and see what it looks like at each stage.

First, understand the relationship between Pipeline and Processor

In Datadog's Log Management, a Pipeline is a set of Processors that run in sequence, configured under Logs → Configuration → Pipelines. Each processor is responsible for one small task, and the output from the previous station passes through untouched to the next, just like a factory production line: the raw log is the raw material, each processor is a processing station, and the final output is a standardized log ready for SIEM analysis.

Below, we follow the same log through all 5 steps of the pipeline, step by step, to see what it actually looks like and which processor is used at each step.

Before the Grok Processor, a log is usually just a string of unstructured text, and rules can't match against specific fields.

Raw log2020-01-01 12:00:01 google oauth login success by John Doe from 1.2.3.4

Grok Processor: extracts the fields you need from an unstructured string, like breaking a jumbled sentence apart into usable, individual fields.

Where the name comes from The word Grok comes from the 1961 science fiction novel Stranger in a Strange Land, where author Robert Heinlein coined the term to mean "to understand something so thoroughly and intuitively that you fully absorb its essence," not just knowing it on the surface, but truly internalizing it. The log processing world (Logstash used it first, and Splunk and Datadog later adopted the same convention) borrowed this word because what this processor does is exactly "read a once-jumbled piece of text and understand what each part means," hence the name Grok.

In practice, Grok uses predefined patterns (essentially wrapped regular expressions, or regex) to match against text. Any fragment that matches a pattern gets extracted and labeled with a field name.

Raw log against a Grok pattern (illustrative)
%{date("yyyy-MM-dd HH:mm:ss"):timestamp} %{word:evt.name} login %{word:evt.outcome} by %{data:usr.id} from %{ip:network.client.ip}
Applying the pattern above to the raw text parses it into: 
{
  "usr.id": "John Doe",
  "evt.category": "authentication",
  "evt.name": "google oauth",
  "evt.outcome": "success",
  "network.client.ip": "1.2.3.4"
}
With these fields in place, a rule can now query conditions like evt.outcome:failure. Without Grok parsing, the whole sentence would just be a string of unstructured text to a rule, with no way to match against "was the outcome a failure" specifically.

OCSF Processor: remaps source-specific fields into standard fields that are consistent across sources.

Background OCSF (Open Cybersecurity Schema Framework) is a security event data "schema" standard, co-launched in 2022 by AWS and Splunk and donated to the open source community. Since then, over a hundred security vendors, including Datadog, CrowdStrike, and IBM, have adopted it. In plain terms, a Schema is "a spec sheet that defines what the data should look like": it specifies which fields a "login event" should have, what those fields should be named, and what type the values should be, so every vendor ships against the same spec sheet instead of each speaking its own dialect.

OCSF sorts events into different classes, such as the Authentication, API Activity, and Account Change classes mentioned in Chapter 1, and each class defines a set of standard attribute names. Here we demonstrate the "user" attribute: its standard name in OCSF is actor.user.name. Regardless of whether the source is CloudTrail, Okta, or, as here, a Google OAuth log, the Processor maps each source's own field over to it:

Without OCSF, you'd need to write a separate set of rules and track a separate set of field names for each of these three sources. With OCSF, one rule works across all three. This is an extremely high-frequency exam topic.

GeoIP Processor: adds geographic location information based on the IP address.

How the location lookup actually works Behind the GeoIP Processor is a database mapping IP addresses to geographic blocks (for example, the industry-common MaxMind GeoLite2, which Datadog maintains internally), recording "which range of IPs is assigned to which country/city's network provider." When the processor receives an IP, it looks up which range it falls into and returns the corresponding country, city, and coordinates. This works the same way as looking up "which city does this phone number's area code belong to": it's not a real-time query to someone, it's a lookup against a known reference table.
Fields added after enrichment
{
  "network.client.ip": "1.2.3.4",
  "country": "Japan",
  "city": "Tokyo"
}
Uses: Impossible Travel detection (you need each login's geographic location first to calculate the distance between two locations), new-country login detection, and mapping attack sources visually.

The SIEM Index Filter decides whether this already-cleaned log gets sent into the Cloud SIEM index.

What "passing the filter" actually means A SIEM Index Filter is essentially a query expression (the same syntax you'd normally use to search logs in Datadog), configured under Logs → Configuration → Indexes → the SIEM index → Index filter. "Passing the filter" means: the fields/tags this log carries satisfy that query condition.
Example: what an actual filter query might look like 
source:(cloudtrail OR okta OR github OR guardduty)
This filter means: as long as the log's source tag is one of CloudTrail, Okta, GitHub, or GuardDuty, it "passes" and is let through into the SIEM index. If a log has source:my-custom-app and that source isn't in the filter, this log will not enter the SIEM index, and no Detection Rule will ever see it.
Processed log
carrying source, tag, and other attributes
→
Matched against the SIEM Index Filter's query condition
→
Attributes satisfy the condition: passed into the SIEM index, handed to Detection Rules for evaluation

How to make a log "pass": (1) Manually go to the Logs Index Configuration page and add that source's source (or another custom tag) into the filter's query condition; (2) A simpler approach is to enable the corresponding Content Pack (see Chapter 1). Datadog will automatically add the sources that Content Pack needs into this filter, no manual query editing required.

As long as a log passes the filter, it gets stored in the SIEM index, even if it never triggers any Detection Rule, it's still retained for later investigation. A log that doesn't match the filter will never be seen by any Detection Rule at all.

The OOTB Pipeline is a read-only starting point

OOTB (Out-Of-The-Box): Datadog has already built default pipelines for common sources, such as the AWS CloudTrail pipeline and the AWS GuardDuty pipeline, which automatically parse common fields (eventName, sourceIPAddress, userIdentity).

Important detailThese OOTB pipelines are typically read-only and can't be edited directly, but you can chain custom processing after them to add your organization's specific parsing needs.

Log retention tiers

Think of this as a "temperature tiering" of data, driven by the tension between query speed and storage cost: the faster a tier can be queried, the more expensive it is, so you wouldn't keep all logs indefinitely in the most expensive tier.

TierUse caseQuery speed
Standard indexingFrequently queried hot data that can absorb more compute costFastest
Flex LogsNot queried often, but needs to be retained and searchable, up to 15 monthsMedium
Log ArchivesCompliance / long-term storage, rarely queriedSlowest (needs to be restored first)
Example: a typical tiering strategy Logs from the last 30 days go into Standard indexing (analysts query it every day, needs to be fast); logs from 30 days to 15 months are moved into Flex Logs (occasionally queried for compliance or after-the-fact forensics, but doesn't need to be real time); logs older than 15 months, kept only to satisfy regulatory retention requirements, are moved into Log Archives (almost never queried, and restoring takes time when it is). These three tiers are configured per index under Logs → Configuration → Indexes, with retention days / rehydration rules.

No matter which tier is chosen, Cloud SIEM analyzes data in real time as it comes in. Threat detection isn't delayed just because a cheaper storage tier was chosen: real-time analysis happens the moment the log arrives, and which tier it's later archived into is purely an "after-the-fact storage" decision. These are two separate things. Security Signals themselves are retained for 15 months.

Flex Logs limitations (an easily overlooked exam point)

Flex Logs does not support Log Monitors, and Datadog has stated it will not support this, for two reasons: (1) query speed is slower, while Monitors need near-real-time scanning, and Flex's latency would make alerts not timely; (2) it would consume Flex's compute resources (Query Pool) heavily, since a Monitor running repeated queries continuously would burn through the quota. Watchdog also does not support Flex Logs (it likewise requires continuous scanning).

Workaround: use Metrics from Logs first to turn the pattern you want to monitor into a metric, then set a Monitor on that metric. One-line takeaway: Flex Logs is good for "keeping it around to query later," not for "watching it in real time for alerts."

Index ordering: the SIEM index must be ranked first

After a log passes through the pipeline, it needs to be assigned to an index. An account usually has several indexes set up (for example, an index for general application logs, an index for auditing), and Cloud SIEM has its own dedicated index too (e.g. cloud-siem-xxxx). These indexes have a defined order on the configuration page.

Why order affects whether a log gets received at all Each index has its own filter conditions, daily quota, and sampling rules. Logs are checked against indexes in order, and if an earlier index has used up its quota or has an exclusion rule configured, it may intercept or drop certain logs early, meaning an index further down the list (including the SIEM index) never gets a chance to see that log at all.
Exam focusThe Cloud SIEM index must be ranked first, to guarantee it always gets priority access to matching logs and doesn't get preempted by another index's quota or exclusion rules. You may see a warning that says "The Cloud SIEM index is not in the first [position]." If you see it, know that it means the index ordering is misconfigured, and you need to go to Logs → Configuration → Indexes and manually drag the SIEM index to the top (reorder).
Chapter 03 · Rule Basics

Rule Basics: Types, Components, and Eight Detection Methods

Now that the data is clean, the actual decision logic happens here: what a signal is, how many types of rules there are, what the shared components are, and what methods are used to determine "this is an anomaly." These are the foundation for the next chapter's MITRE mapping and advanced tuning.

A Signal is not the same as a raw log

A Detection Rule defines what logic Cloud SIEM applies to incoming logs in real time, and when the conditions match, it generates a Security Signal.

AnalogyThe log is the raw evidence, the rule is the detective's reasoning logic, and the signal is the "there's a problem here" report the detective writes after cracking the case.

Three rule types

Real-time rules
Monitors continuously as logs arrive; generates a signal the moment conditions are met
Example: a rule is counting "the number of failed logins within 5 minutes." This tally and monitoring runs in real time.
Scheduled rules
Runs a query at a fixed interval; good for catching threats that unfold over a long time
Examples: DNS (Domain Name System) tunneling (hiding exfiltrated data inside DNS queries), low-and-slow brute force (deliberately slowing down attempts to spread them out and stay under short-window thresholds). These kinds of attacks require reviewing a long time range periodically to catch.
Historical jobs
Runs a one-time query against historical data, not continuous monitoring
Use case: backtesting a new rule, asking "if this rule had existed two months ago, would it have caught a known incident," to validate whether a rule under- or over-fires.

Cloud SIEM ships with several hundred OOTB rules, continuously maintained by the Datadog Security Research team, with new rules automatically imported into the account. The Rules List can be filtered by source to check coverage.

The relationship between OOTB rules and custom rules (an easily misunderstood detail)
  • OOTB rules are continuously developed by Datadog and updates are imported automatically into the account; custom rules are created and maintained by the user themselves, and do not receive automatic updates from Datadog, they can only be adjusted manually.
  • The two are independent rules, with no "which one overrides the other" priority mechanism. Even if a custom rule and an OOTB rule target the same kind of activity, both rules are evaluated independently and may each generate their own signal. A custom rule does not automatically replace or override an OOTB rule.
  • Creating a custom rule with similar functionality does not cause the corresponding OOTB rule to be automatically removed. Both will keep running together unless the user manually disables one of them.

Five shared components of a rule

Detection method▸

Defines how Cloud SIEM evaluates logs. There are 8 methods in total, covered in the section below.

Search queries▸

Specifies which log conditions must be matched.

Conditions▸

Determines when a signal should be generated, and its severity level.

Playbook▸

Contains the rule name, investigation notes, and tags, including MITRE ATT&CK mapping tags (see the start of the next chapter).

Suppressions▸

Defines under what conditions a signal should not be generated, used to exclude known false positives and reduce alert fatigue. What gets suppressed is at the "signal" layer, the underlying log itself is never deleted and can still be queried afterward.

Query typeMatches againstWhen it applies
Suppression queryAttributes of the signalAfter the signal has already been prepared for generation because the rule condition matched
Data exclusion queryAttributes of the raw data (log/event)Before the rule has evaluated this data at all

Both use the same query syntax, the difference is purely what they match against. Both also only take effect for this one rule, unrelated to whether they can apply across multiple rules.

Eight detection methods

Expand each card to see an example.

Threshold
Count exceeds a limit
Example: more than 10 failed logins within 5 minutes. Everyone shares the same fixed threshold line.
New Value
A value that has never appeared before
Example: a user logs in from a country they've never logged in from before, for the first time.
Anomaly
Dynamic threshold, compared against its own history
Example: normally 50 API calls per hour suddenly jumps to 500. Each entity has its own baseline, unlike Threshold's fixed limit.
Content Anomaly
Content is unusual, not the count
Example: an API call's parameter pattern is usually consistent, but its content structure is suddenly very different this time, even though the call count hasn't increased.
Impossible Travel
Geographic location doesn't make sense
The same account's access events happen in two locations whose distance apart makes human travel impossible within the elapsed time.
Third Party
Forwards an external tool's alert
For example, an alert already generated by Amazon GuardDuty is forwarded into Datadog and presented as a signal.
Signal Correlation
Multiple signals merged into one
Example: "new device login" and "large volume of file downloads" are each only low-severity alerts on their own, but correlating them together yields much higher confidence.
Sequence
An ordered chain of events
Example: assume role → privilege escalation → data access. Only when these happen in order and within a reasonable time window is it judged to be a complete attack sequence.
Chapter 04 · MITRE & Advanced Tuning

MITRE ATT&CK and Advanced Tuning

Now that rule basics are clear, this chapter looks at how rules map to the industry's shared attack-technique vocabulary (MITRE ATT&CK), then covers three easily confused "blocking" mechanisms, and finishes with rule tuning and version comparison.

Where MITRE ATT&CK comes from and what problem it solves

MITRE ATT&CK stands for Adversarial Tactics, Techniques, and Common Knowledge.

Background The MITRE Corporation is a US nonprofit research organization that has long run defense and security-related R&D centers for the US government. In 2013, an internal MITRE research project called FMX began systematically cataloguing "what real attackers actually do," by analyzing large volumes of real intrusion incidents and activity records from APTs (Advanced Persistent Threat groups), grouping the observed techniques into categories. This was publicly released as the ATT&CK framework in 2015. The problem it solves: the security field long lacked a shared vocabulary. The same attack technique might be described in completely different terms by different vendors and different analysts, which meant experience couldn't accumulate and rules couldn't interoperate. After ATT&CK, "T1110 is brute force" became industry consensus. No matter which company's analyst you are, seeing this code tells you exactly what's being discussed.

The framework has two layers:

  • Tactic: the attacker's high-level goal, i.e. "why" they're doing something. The Enterprise Matrix is roughly ordered along the attack lifecycle, and includes over a dozen tactics such as Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Exfiltration, and Impact.
  • Technique: the specific method used to achieve that tactic's goal, i.e. "how" it's done. Each technique has a fixed identifier in the format T####, with finer-grained sub-techniques as T####.###.

You can think of Tactic as a chapter title and Technique as the specific moves under that chapter. A single Tactic usually maps to several Techniques.

Example: how a complete attack maps to multiple Tactics A single Technique is just one step in the attack chain. A real attack usually spans several Tactics, and stringing them together tells the complete story:

This also echoes the Sequence detection method introduced in the previous chapter: a sequence rule for assume role → privilege escalation → data access is, at its core, detecting an attacker moving down this exact Tactic chain.

How Cloud SIEM uses it: mapped through tags, not a separate module

Key exam trap The mapping between a Detection Rule and MITRE ATT&CK is done by adding tags to the rule, not through a separate standalone module: 
tactic:credential-access
technique:brute-force
security:attack
When a signal is generated, these tags carried on the rule are displayed directly on the signal. If a question asks "how is MITRE mapping implemented," the correct answer is "through the Detection Rule's tags."
Easily overlooked detail: three tags must appear together Adding tactic: and technique: alone isn't enough. The rule must also carry the security:attack tag for the MITRE ATT&CK Map to include this rule in its visualization. If a custom rule only sets tactic:/technique: but is missing security:attack, the rule itself will still run normally and generate signals as expected, it just won't show up on the map. This has nothing to do with whether the rule is OOTB or which detection method it uses, it's purely a missing tag.

The MITRE ATT&CK Map plots all the detection rules in your account as a heatmap with tactic (x-axis) / technique (y-axis, or vice versa) as coordinates. Darker colors mean more rules map to that technique, i.e. denser coverage; lighter or blank cells mean "if an attacker actually used this technique, you might have no rule that would fire at all." Illustrated below (for illustration only, not real data):

Low coverage (a gap, consider adding a custom rule)Medium coverageHigh coverage

The key question this chart answers is "if an attacker used technique X, do I have a rule that could catch it?" It's used to find coverage gaps and decide which custom rules to prioritize writing to fill them, which connects directly to the continuous improvement loop taught in Chapter 6: periodically reviewing this chart is one concrete way to "stay current."

This shared industry vocabulary is placed after detection methods because the three rule types, five shared components, and eight detection methods from the previous chapter ultimately all get labeled with the tactic/technique tags covered here. Cross-referencing back to the previous chapter is how you understand which attack technique each detection method is actually defending against.

Three easily confused mechanisms: Filter / Rule / Suppression

These three are often turned into scenario-judgment questions that test whether you can tell "which mechanism is actually at work here":

MechanismWhen it appliesScopeEffect
SIEM Index FilterBefore the log enters the SIEM indexAccount / index level, affects all rulesA non-matching log is never evaluated by any rule at all
Detection Rule's Data Exclusion QueryLog is already in the SIEM index, before this rule evaluates itSingle rule levelThis data effectively doesn't exist for "this rule"
Suppression QueryThe moment a signal is about to be generatedSingle rule levelThe signal is muted; the underlying log is completely untouched
MnemonicFilter controls "whether it can get into the SIEM at all." Rule (including Data Exclusion) controls "whether this rule can see it." Suppression controls "whether to bother you once conditions are met."

Timeline: the same log passes through these three checkpoints in order

CHECKPOINT 1
SIEM Index Filter
Account-level checkpoint. Matches the log's source/tags.
Fails → the log never enters the SIEM index at all, never reaches the next two checkpoints, and no rule ever sees it.
CHECKPOINT 2
Data Exclusion Query
A single rule's checkpoint. Matches attributes of the incoming raw data.
Fails → this rule skips this piece of data entirely, not even counting it toward any tally, but the log stays in the SIEM index and other rules can still see it normally.
CHECKPOINT 3
Suppression Query
A single rule's final checkpoint. Matches attributes of the signal about to be generated.
Matches → the signal is muted and never enters Signals Explorer; doesn't match → the signal is generated normally.
Example: the same "known false positive," handled at different checkpoints, with very different outcomes Scenario: the service account backup-bot runs a scheduled backup every day, and it always fails its first login attempt before succeeding on retry, a known false-positive source for the team. The rule is a Threshold rule for "more than 10 failed logins within 5 minutes."

If a Data Exclusion Query is set on the rule

Set -usr.id:backup-bot. backup-bot's failed login logs don't exist for "this rule" from the very start, and are never counted toward the tally at all. Even if it fails to log in 100 times in a day, this rule will never be triggered because of it. Other rules (e.g. Impossible Travel) are unaffected and still evaluate this log normally.

If a Suppression Query is set instead

Set it to match the signal attribute usr.id:backup-bot. The rule still tallies the count normally, and once the 10-count threshold is reached, the rule logic determines "a signal should be generated here." It's only intercepted at the last moment by the Suppression Query, so this signal never appears in Signals Explorer. The underlying log and the "almost triggered" process are completely unaffected and can still be queried later.

Both approaches end with the same result, "the user doesn't see an alert," but they happen at completely different stages: Data Exclusion makes the rule treat this data as nonexistent from start to finish; Suppression lets the rule run through its entire evaluation, actually decide to fire an alert, and only then blocks it right before the finish line.

Rule tuning, custom rules, and version comparison

Once you understand the detection methods, the next step is shaping rules to fit your own environment: OOTB rules are a great starting point, but usually need tuning for your environment. You can add suppressions for known false positives directly on OOTB rules, adjust the severity level, or update the playbook with organization-specific investigation guidance. For threats not covered by OOTB rules but specific to your organization, you can build fully custom rules using the same set of components and detection methods. Because of OCSF normalization, a custom rule written against OCSF attributes can apply to multiple log sources at once, so a single well-written custom rule can provide very broad coverage.

Rule Version History: comparing configuration differences between rule versions The rule editor has built-in version history. After tuning a rule (for example, expanding the query scope from a single environment to multiple environments), you can use the Open Version Comparison option to compare the current version's configuration side by side with a previous version, with color-coded differences (red for removed settings, green for added settings).

This differs from the Datadog Audit Trail mentioned in Chapter 6: Audit Trail records platform-level operational events like "who changed a rule and when," whereas Rule Version History is the tool inside the rule editor for directly comparing configuration differences between two versions.
Chapter 05 · Investigation

How to Investigate After a Signal Is Generated

Once a rule fires, what you get isn't a pile of scattered logs, it's an already-organized signal. This chapter covers how four tools take you from "what happened" all the way to "how dangerous is this entity."

A signal is not a raw log

AnalogyLogs are scattered fragments of evidence; a signal is the case file that has already assembled the fragments and attached the detective's notes.

Basic generation flow: log comes in → passes the SIEM Index Filter → a Detection Rule is applied → conditions match → a signal is generated.

A signal has two key status fields: Severity (Critical / High / Medium / Low / Info) and a triage status:

Open→ Under Review→ Archived

It can be assigned to a specific user as the owner, and is retained for 15 months. Clicking any signal opens a side panel:

SIGNAL DETAIL PANEL

Playbook

Shows the raw logs that matched the rule's query condition and actually triggered this signal, including timestamps and relevant attributes. Check here to see "which logs triggered this signal."
Related Signals

Four investigation tools, from shallow to deep

Signals Explorer▸

The interface for viewing, searching, filtering, and correlating signals, filterable by severity, source, rule, tag, time range, or any attribute. This is the starting point for investigation.

Investigator▸

A graphical interface that tracks relationships between entities and the Attack Path: the full path an attacker takes from an initial foothold, through a chain of actions, to their eventual goal. It answers: "what did this identity do? which services did it interact with? what happened after the role was assumed? did it succeed?" It supports AWS, GCP, Azure, Datadog, and Kubernetes.

Risk Insights▸

Rolls up security data into a unified risk profile per "individual entity" (IAM user, S3 bucket, EC2 instance, GitHub repo, etc). The risk score is calculated from the severity and frequency of related signals over the past 14 days for that entity, and if Cloud Security is also enabled, Misconfigurations and Identity Risks are factored into the score too. It answers: "which entities in my environment are riskiest right now?"

Bits AI Security Analyst▸

Automated AI-driven initial triage: analyzes the triggering logs and their context, summarizes key evidence, explains its reasoning for judging "benign vs. suspicious," and suggests next steps. It's grounded in MITRE ATT&CK, can pivot across multiple IOCs, and query historical data. It does not replace analyst judgment, it speeds up initial assessment, and the practical benefit is a faster MTTA.
Example: for an Amazon SNS enumeration signal, Bits AI judged it SUSPICIOUS, with evidence including account takeover indicators, anonymizing proxy infrastructure, and systematic AWS service reconnaissance.

Threat Intelligence and IOCs

IOC (Indicators of Compromise): observable, concrete artifacts, such as an IP, domain, file hash, or URL, that suggest a system may already be compromised or targeted for attack.

First, understand what a Feed is Think of a Feed as a continuously updated subscription to a "known bad actors" list: security research organizations and vendors constantly observe attack activity worldwide, compile the malicious IPs and domains they find into a list, and continuously deliver it to you via subscription, so your system can match it against your own data. Like subscribing to a news feed, the value of a threat feed lies in "continuous updates," not a static list you check once and are done with.
How it works: what the threat_intel attribute is

When an IP or domain in an incoming log matches a known IOC in the feed, Cloud SIEM attaches an additional threat_intel attribute directly onto the log itself, writing the verdict of "this IP is a known threat, and which category it belongs to" directly into the data:

{
  "network.client.ip": "185.220.101.42",
  "threat_intel": {
    "category": "residential_proxy"
  }
}

This attribute isn't just a display-only label. Because it's queryable data just like any other field, a Detection Rule can use it directly as a query condition. For example, you could write a rule matching @threat_intel.category:(malware OR tor) to generate a signal only for events where the connection target is itself a known malicious source, without maintaining your own IP blocklist. Common categories: malware, cryptomining, tor (the Tor anonymity network), residential proxy (residential proxy servers, often used to disguise malicious traffic as ordinary home network traffic), and scanner (scanning tools).

Built-in curated feeds

Sourced from partners like IPinfo and GreyNoise, automatically applied to all logs, requiring no configuration at all.

Bring your own feed

Sourced from commercial vendors, industry intelligence-sharing organizations called ISACs (Information Sharing and Analysis Centers, organizations where companies in the same industry exchange threat intelligence with each other), or internal pipelines, stored as a reference table. It can be uploaded manually as a CSV (Comma-Separated Values) file, or updated automatically on a schedule from cloud storage.

Easily overlooked detail: one table per indicator type Each indicator type needs its own separate reference table, for example, one table for IP addresses and another for domains. You can't upload different indicator types mixed into the same table. The currently supported path for importing custom IOCs is exactly "CSV into a Reference Table." There is no separate Threat Intelligence API for submitting JSON directly, and it does not go through STIX (Structured Threat Information eXpression) / TAXII (Trusted Automated Exchange of Intelligence Information), which is a different, separate industry standard protocol for threat intel exchange, not the method Datadog uses to import custom IOCs.
Chapter 06 · Metrics & Continuous Improvement

How to Measure and Continuously Improve

Detection and investigation are only half the story. The other half is quantifying the whole operation into something you can track, report to leadership, and use as compliance evidence, and turning it into a loop that keeps getting better.

The lifeline of a signal: MTTD / MTTA / MTTR

All three metrics are abbreviations of "Mean Time to ___", each measuring a different segment of that lifeline:

  • MTTD stands for Mean Time to Detect
  • MTTA stands for Mean Time to Acknowledge
  • MTTR stands for Mean Time to Resolve
STAGE 1

STAGE 2 · MTTD
Signal is generated

STAGE 3 · MTTA

STAGE 4 · MTTR

Example of reasoningIf MTTD is very low but MTTA keeps rising, that means the detection pipeline is working well and the problem is that analyst triage isn't fast enough. What you should do is adjust notification routing, or make better use of Bits AI's automatic initial triage, not change the detection rules.

Dashboards and weekly reports: making the numbers visible

The Cloud SIEM Overview page presents: important signals, high-risk entities, Content Pack health and onboarding progress, top signals by geography/MITRE tactic, MTTD and false-positive rate, and the latest Security Research Feed.

OOTB dashboards (e.g. the CloudTrail dashboard) can be cloned and customized; you can also build dashboards tailored for leadership, detection engineers, or operations, depending on the audience.

Weekly digest: rolls up the past seven days' alert volume, response times, and important new issues. Each user must subscribe individually, requiring the security_monitoring_signals_read permission.

Notification Rules and Workflow Automation (SOAR)

Notification rules route signals to the right place based on severity / tag / attributes:

Workflow Automation is Cloud SIEM's SOAR layer, capable of revoking credentials, isolating resources, creating tickets, and enriching signals. Datadog provides prebuilt workflow blueprints, and each Content Pack also ships with blueprints for its specific integrations.

It does not automatically change its configuration based on signal content, and it's not something you can drop straight into production. That's exactly what the word "blueprint" means literally: a starting point, not a finished product.

Practice Questions

QUESTION 1 OF 10

After creating a custom log detection rule for identifying privilege escalation attempts, the rule does not appear on the MITRE ATT&CK Map despite being enabled. What is the most likely cause?

AThe rule uses a log detection type, which is incompatible with the MITRE ATT&CK Map visualization.
BThe rule is missing the required tactic: and technique: tags paired with the security:attack tag.
CThe rule must be converted from a custom rule to an out-of-the-box rule to appear on the map.

The correct answer is B. MITRE mapping relies on tags on the rule (see Chapter 4), but adding tactic:/technique: alone isn't enough. The rule must also carry the security:attack tag. Only when all three appear together does the MITRE ATT&CK Map include this rule in its visualization.

A is wrong: a log detection type (a rule written using detection methods like Threshold or New Value) maps to the MITRE Map perfectly normally, there's no conflict between the two. C is wrong: a custom rule can absolutely appear on the map as is; it doesn't need to be, and can't be, converted to an OOTB rule, it just needs the missing tags added.

QUESTION 2 OF 10

Custom threat intelligence indicators need to be imported into Cloud SIEM for log enrichment. Which format is supported for uploading custom Indicators of Compromise?

ASTIX 2.0 bundles uploaded through a TAXII server integration.
BCSV files uploaded to or imported into Datadog Reference Tables.
CJSON objects submitted directly through the Threat Intelligence API.

The correct answer is B. This echoes Chapter 5's threat intel mechanism: a bring-your-own feed is stored as a Reference Table, uploadable manually as a CSV file. Additional detail: each indicator type (IP, domain, etc) needs its own separate reference table, they can't be mixed into the same table.

A is wrong: STIX/TAXII is a different, separate industry standard protocol for threat intel exchange, not how Datadog Cloud SIEM imports custom IOCs. C is wrong: there is currently no separate Threat Intelligence API for submitting JSON directly, import can only go through the Reference Table path.

QUESTION 3 OF 10

Which statement accurately describes how SOAR workflow blueprints function in Datadog?

ABlueprints provide customizable starting templates that can be modified to match team-specific processes.
BBlueprints automatically adapt their configuration based on the security signals that trigger them.
CBlueprints generate fully configured workflows that are immediately ready for production deployment.

The correct answer is A. The word "Blueprint" itself is the key: a blueprint is a customizable starting template, not a finished product. It needs to be adapted to a team's process before it can truly go live (see Chapter 6).

B is wrong: it mistakes "a workflow taking different branches at runtime depending on the signal" for "the blueprint itself automatically changing its configuration." C is wrong: this contradicts "requires customization." Something that can go live directly wouldn't be called a blueprint.

QUESTION 4 OF 10

After launching the Datadog CloudFormation StackSet to onboard AWS accounts under an Organization, the deployment fails before creating IAM roles in any target account. The Organization has trusted access enabled and service-managed permissions configured. Which configuration error causes this failure?

CMultiple AWS regions were selected under the Specify regions setting.

The correct answer is C. This question adds new detail beyond the Chapter 1 note on the AWS Org StackSet: IAM is a global AWS service, not region-specific, but a StackSet creates stack instances per "account x region." If Specify regions has multiple regions selected, the template will try to create an IAM role with the same name in each region independently, causing a conflict, which makes the whole deployment fail before an IAM role has been created in any account.

A is wrong: setting Execution configuration to Active (parallel execution) only affects deployment speed/concurrency. B is wrong: setting Deployment targets to the entire Organization instead of a specific OU is only a deployment scope setting, and doesn't cause the whole deployment to fail.

During investigation of a credential stuffing security signal, an analyst needs to identify other signals that originated from the same source IP address or involved the same user identity. Which capability within the signal's investigation panel surfaces these connections?

This echoes the Related Signals field in the signal side panel from Chapter 5: it finds related signals by matching whether fields/attribute values are the same (e.g. source IP, user identity), letting an analyst start from one signal and surface other activity involving the same attacker.

A is wrong: What Happened (i.e. Related Logs) shows the logs that this signal itself triggered on, not connections between other signals. C is wrong: the Workflows tab shows automated response processes, unrelated to finding related signals.

QUESTION 6 OF 10

Which statement accurately describes the relationship between OOTB detection rules and custom detection rules in Cloud SIEM?

BCustom rules automatically take priority over OOTB rules targeting the same log activity.

The correct answer is A. OOTB rules are continuously developed by Datadog and updates are automatically imported into the account; custom rules are created and maintained by the user themselves, and don't receive automatic updates (see Chapter 3).

QUESTION 8 OF 10

Cloud SIEM suppression rules support two query types: a suppression query and a data exclusion query. What distinguishes these two query types?

AThe suppression query matches signal attributes while the data exclusion query matches input data attributes.
BThe suppression query applies to a single detection rule while the data exclusion query applies across multiple rules.
CThe suppression query uses log search syntax while the data exclusion query uses signal explorer syntax.

The correct answer is A. The suppression query matches the signal's attributes, while the data exclusion query matches attributes of the incoming raw data (see the comparison table in Chapter 4).

B is wrong: both query types only take effect for "this one" rule, unrelated to single-rule vs. multi-rule scope. C is wrong: both use the same query syntax, the difference is what they match against, not different syntax systems.

QUESTION 10 OF 10

An organization subject to industry regulations needs to retain security logs for 15 months while maintaining the ability to immediately search and analyze those logs within Datadog. What is the BEST approach to meet this requirement cost-effectively?

AEnable Flex Logs with 15-month retention on security log indexes.
BConfigure Log Archives to forward logs to customer-owned cloud storage buckets.
CConfigure standard indexes with 15-month retention and apply exclusion filters.

The correct answer is A. This maps directly to Chapter 2's "Log retention tiers": Flex Logs can retain data for up to 15 months while staying searchable (no rehydration needed), positioned exactly as "queryable, retained long-term" while still being cheaper than Standard indexing.

B is wrong: Log Archives moves data into the customer's own cloud storage, requiring rehydration before it can be queried, which doesn't satisfy the "immediate search" requirement. STEP 01 · Raw log arrives

An attacker repeatedly sends failed logins against the IAM user admin within 5 minutes; this is attempt number 12. When the log first arrives at Datadog, it's a string of unstructured text:

2026-07-23 03:14:02 aws console login failed by admin from 203.0.113.44

The team has already enabled the AWS CloudTrail Content Pack, so this source already has an OOTB pipeline and a failed-login detection rule mapped to it, no need to connect anything on the fly.

STEP 02 · Grok Processor parsing

Grok uses predefined patterns to break the unstructured text into queryable fields:

{
  "usr.id": "admin",
  "evt.category": "authentication",
  "evt.name": "aws console login",
  "evt.outcome": "failure",
  "network.client.ip": "203.0.113.44"
}

STEP 03 · OCSF Processor normalization

Remaps source-specific fields into standard fields consistent across sources:

{
  "actor.user.name": "admin",
  "class_uid": "Authentication",
  "activity_id": "Logon",
  "status_id": "Failure",
  "src_endpoint.ip": "203.0.113.44"
}

No matter whether this source later switches to CloudTrail, Okta, or some other system, as long as it maps to these same standard fields, the same rule can catch it.

STEP 04 · GeoIP Processor enrichment

Looks up 203.0.113.44 in the IP geolocation database and adds the location:

{

  "country": "Overseas, a region admin has never logged in from",
  "city": "Unknown"
}

STEP 13 · Analyst triage

An analyst sees this High-severity signal in Signals Explorer. Because the severity is high and the attack technique is credential-access, they decide to prioritize it, marking the status from Open to Under Review, formally starting the investigation. STEP 14 · Deeper investigation

STEP 15 · Verdict and response: confirmed as a real attack

STEP 16 · Case closure and measurement

Once handled, the signal is marked Archived. The entire timeline is recorded as three metrics: MTTD (log ingestion to signal generation), MTTA (signal generation to Under Review), and MTTR (generation to Archived). These appear in the weekly digest and the Cloud SIEM Overview dashboard, and also serve as evidence for compliance audits such as SOC 2 / PCI DSS that require proof of whether an incident was tracked to resolution.
